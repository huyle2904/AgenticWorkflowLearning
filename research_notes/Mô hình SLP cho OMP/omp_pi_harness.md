## 1. What OMP is, how it relates to Pi, and what it adds

### Takeaway
OMP (`omp`) is a Bun/TypeScript + Rust fork of Mario Zechner's Pi coding agent, built by Stencil Labs, that ships in-core most of what Pi deliberately leaves to extensions: a `task` subagent tool with isolation and structured results, Agent Hub, advisor/watchdog, `/vibe` director mode, `/collab` live sharing, LSP/DAP, memory, browser/computer use, plan mode, and a much larger RPC surface. Pi itself has moved to the Earendil org and now ships an experimental durable server/client stack that OMP has not merged.

### Inferences
- For an SLP design, OMP is the more capable substrate (in-core subagents, Agent Hub, RPC subagent frames, session-status derivation), while Pi is the better-documented minimal substrate with a `--session-id`/`--name` flag pair OMP lacks.
- Because OMP froze its Pi sync at March 2026, any recommendation that depends on a Pi-only feature must be checked against OMP source before use.

### Gaps
- OMP's first-party blog posts (`blog.can.ac`) were unreachable; the OMP author's design philosophy is taken only from README/docs, not from posts.
- No verified list of which Pi packages actually run under OMP's compat shim.

## 2. Programmatic / non-interactive modes: print, JSON, RPC, SDK, servers

### Takeaway
Both harnesses offer four wrappers: interactive TUI, print/JSON one-shot, a JSONL RPC mode over stdio, and an in-process SDK (`createAgentSession`). OMP's RPC is a strict superset with an incompatible lifecycle dialect (`prompt_result` + `session_settled` instead of Pi's `agent_settled`) and adds `open_session`, subagent frames, host tools and protocol-v2 chunking. Neither ships a supported multi-session daemon: Pi has an experimental source-only server/client; OMP only has a local Collab-host registry and `omp ps` for background services.

### Cited Findings

Print and JSON modes
- OMP: `omp -p "prompt"` (headless), `omp -p --mode json` (structured JSON event stream), non-TTY stdin is read as the prompt, `--max-time`, `--no-title`, `--print-thoughts`; running `omp "prompt"` with no terminal on stdin now behaves like `-p` (18.4.3). `--mode` values: `text | json | rpc | acp | rpc-ui`. — [docs/cli-reference.md](https://github.com/can1357/oh-my-pi/blob/main/docs/cli-reference.md), [CHANGELOG](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/CHANGELOG.md)
- OMP JSON printing strips `message_update` snapshots and `providerPayload` so transcripts grow linearly. — [print-mode.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/modes/print-mode.ts)
- Pi: `pi -p`, `pi --mode json "prompt"` (writes a session header, then events, then exits), `pi --mode rpc`. Events end with `agent_end` then `agent_settled`. — [docs/cli.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/cli.md), [docs/json.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/json.md)

### Inferences
- The OMP RPC surface already contains every primitive a supervisor host needs for programmatic Leads: idempotent-by-`id` commands, `prompt_result` completion, `get_state` polling for todo/context/queue, subagent frames for Peer visibility, host tools for Supervisor-to-host calls, and `open_session` for deterministic resume. roboomp proves the pattern at scale inside the OMP repo.
- Pi's RPC would also work but lacks subagent frames (Pi has no built-in subagents) and `open_session`; Pi's `--session-id` is the closest equivalent for deterministic identity.

### Gaps
- No documented, supported daemon/socket API for driving an already-running interactive TUI session other than the Collab relay path (section 4).
- The exact TypeScript export path of OMP's `RpcClient` for consumers of the npm package was not verified (docs mention `@oh-my-pi/pi-coding-agent/modes/rpc/rpc-frame` explicitly, but not `rpc-client`).

## 3. Sessions: storage, IDs, resume, tree, export, and reading a live session from outside

### Takeaway
Both store sessions as append-only JSONL trees (`id`/`parentId` + a leaf pointer) under the agent dir, grouped by working directory. OMP adds a fixed-width 256-byte title slot, blob externalization, lifecycle crash markers (`session_exit`, `tool_execution_start`), and an SDK helper that derives a coarse `SessionStatus` from the file tail, so an external process can read the file to infer "last assistant text / running tool / todo / interrupted", but it cannot tell whether the owning process is alive without another channel.

### Cited Findings
- OMP location: `~/.omp/agent/sessions/<encoded-cwd>/<timestamp>_<sessionId>.jsonl`; blobs in `~/.omp/agent/blobs/<sha256>`; terminal breadcrumbs `~/.omp/agent/terminal-sessions/<terminal-id>`; prompt history in SQLite `~/.omp/agent/history.db`. `--session-dir` overrides. — [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md)
- Pi location: `~/.pi/agent/sessions/--<path>--/<timestamp>_<session-id>.jsonl`; UUID ids by default, custom id via SDK or `--session-id`; `--session-dir`, `PI_CODING_AGENT_SESSION_DIR`, `sessionDir` setting. — [docs/session-format.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/session-format.md), [docs/sessions.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/sessions.md)
- OMP format: JSONL; physical first line is a 256-byte `type:"title"` slot then the `type:"session"` header (`version:3`, `id`, `timestamp`, `cwd`, `title`, `titleSource`, `additionalDirectories`, `previousSessionFiles`, `parentSession`), then entries with `id` (8 chars), `parentId`, `timestamp`. Entry types: `message`, `thinking_level_change`, `model_change`, `service_tier_change`, `compaction`, `branch_summary`, `reset_boundary`, `custom`, `custom_message`, `label`, `title_change`, `ttsr_injection`, `credential_pin`, `session_init`, `mode_change`. Persisted `message.role` values are camelCase (`user`, `assistant`, `toolResult`, `bashExecution`, ...); tool calls are `toolCall` content blocks inside assistant messages. — [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md)
- OMP `custom` entries reserved for core: `tool_execution_start` (`{toolCallId,toolName,startedAt,args?,intent?}` written immediately before a tool runs), `session_exit` (`{reason,kind: normal|signal|fatal|process_exit,recordedAt,pendingToolCalls?}`, written with `flushSync()`), `user_todo_edit` (full todo phase snapshot), `vibe-session-lifecycle`, `autoresearch-control`. On resume a `session_exit` after a non-terminal tail appends a synthetic aborted assistant message. — [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md)
- Extension state entries: `pi.appendEntry(customType, data)` (namespaced `customType` required; core-reserved names must not be reused); extension messages via `pi.sendMessage` persist as `custom_message` and reconstruct as role `custom`. — [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md), [docs/extensions.md](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md)
- Write behavior: a new session stays memory-only until it has an assistant message (or `ensureOnDisk()`); afterwards completed entries are appended incrementally, no `fsync`; streaming partial text is not persisted until the completed message; atomic full rewrites (migration, rename, move) use a cross-process publish lock (`.<file>.lock` + `.lock.os` sidecar) and detect conflicting writers via `SessionWriteConflictError`/`SessionLockError`. Long strings > 500,000 chars are truncated and images are externalized to the blob store. — [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md), [session-storage.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/session/session-storage.ts)
- Tree/leaf: append-only entries, `branch(entryId)` moves only the leaf pointer; `buildSessionContext` walks leaf to root and applies latest compaction or `reset_boundary`. — [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md)
- Discovery helpers: `SessionManager.list(cwd)` / `listAll()` / `continueRecent(cwd)` / `open(path)`; recent scans read a 4 KiB prefix, full lists add a bounded 32 KiB tail to derive `SessionStatus = "complete" | "interrupted" | "aborted" | "error" | "pending" | "unknown"` from the last persisted message; `SessionInfo` has `path,id,cwd,title,parentSessionPath,created,modified,messageCount,assistantTurns,size,firstMessage,status`. Resume matching accepts session-id prefixes, filename prefixes and id suffix. — [session-listing.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/session/session-listing.ts), [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md)
- OMP CLI: `--continue/-c`, `--resume [id]/-r/--session [id]` (id prefix, path, or picker), `--fork <session>`, `--session-dir <dir>`, `--no-session`, `--export <session>` (HTML), `--from-claude`, `--from-codex`, `--no-title`, `--cwd`, `--add-dir`, `--profile`, `--config <file>`, `omp share`. There is NO `--session-id` and NO `--name` flag (checked in `cli/flag-tables.ts`); a session is named via `/rename`, RPC `set_session_name`, or extension `pi.setSessionName`, and its id is generated. — [docs/cli-reference.md](https://github.com/can1357/oh-my-pi/blob/main/docs/cli-reference.md), [cli/flag-tables.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/cli/flag-tables.ts), [docs/session-operations-export-share-fork-resume.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session-operations-export-share-fork-resume.md)
- Pi CLI: `-c`, `-r`, `--session <path|id>`, `--session-id <id>` ("opens the exact project session ID or creates it if absent", letters/numbers/`.`/`_`/`-`), `--fork <path|id>` (combinable with `--session-id` to choose the new id), `--session-dir`, `--no-session`, `-n/--name <name>`; interactive `/tree`, `/fork`, `/clone`, `/compact`, `/export`, `/share`. — [docs/cli.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/cli.md), [docs/sessions.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/sessions.md)
- Identity can change inside one process: `/new`, `/fork`, `/resume`, `/delete` (interactive) and RPC `new_session`, `switch_session`, `branch` replace the active session; `/new` and `/fork` assign a new transcript path, `/clear` keeps identity and file and appends a `reset_boundary`, `/fresh` only resets provider-side state, `/restart` relaunches `omp` with the original launch flags and resumes the same session. `switchSession()` emits `session_before_switch` (cancellable; reasons `new|fork|resume`) then `session_switch` with `previousSessionFile`, and returns `false` if a hook or cwd policy cancels; `/fork` is blocked while streaming. A supervisor that caches `sessionFile` must refresh it on `session_switch`/`new_session` responses. — [docs/session-operations-export-share-fork-resume.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session-operations-export-share-fork-resume.md)
- `/handoff` (RPC `handoff`, refused while streaming) generates a handoff document through a side request and commits it as a compaction entry inside the same session; it does not create a new session file. — [docs/handoff-generation-pipeline.md](https://github.com/can1357/oh-my-pi/blob/main/docs/handoff-generation-pipeline.md)
- Compaction: OMP `compact` RPC command, `set_auto_compaction`, extension events `session_before_compact`, `session.compacting`, `session_compact`, RPC events `auto_compaction_start/end`; `compaction` entries keep `firstKeptEntryId`, `summary`, `tokensBefore`; original entries are never deleted. Pi: `compact`, `set_auto_compaction`, `compaction_start/end`. — [docs/compaction.md](https://github.com/can1357/oh-my-pi/blob/main/docs/compaction.md), [docs/compaction.md (Pi)](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/compaction.md)
- OMP subagent persistence: with a persisted parent, each subagent writes `<id>.jsonl` (session history) and `<id>.md` (final output) into the parent's artifacts tree; `history://<id>` renders a concise transcript for live or parked agents; `agent://<id>` resolves the saved final output, `agent://<id>/<json-path>` extracts a field from JSON output; nested ids are dot-qualified (`<id>.<child>`); advisor transcripts `__advisor*.jsonl` are observability-only. — [docs/tools/task.md](https://github.com/can1357/oh-my-pi/blob/main/docs/tools/task.md), [docs/agent-hub.md](https://github.com/can1357/oh-my-pi/blob/main/docs/agent-hub.md)
- Reading a live file: OMP itself lists sessions without locks (`listSessionsReadOnly`, `SessionManager.peekSessionInit` is "lock-free") and Agent Hub's viewer "incrementally tails the file-backed transcript"; the lenient JSONL parser tolerates non-parseable lines; RPC `get_entries{since}` returns entries strictly after a durable entry id (`unknown_since` error otherwise) and `get_subagent_messages{fromByte}` gives byte-offset tailing with a `reset` flag. — [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md), [docs/agent-hub.md](https://github.com/can1357/oh-my-pi/blob/main/docs/agent-hub.md), [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md), [session-manager.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/session/session-manager.ts)
- OMP todo state: `todo` tool ops `init/start/done/drop/block/unblock/rm/append/view`, statuses `pending|in_progress|completed|abandoned|blocked` with optional `blocker` text; persisted in tool-result `details.phases` and in `user_todo_edit`; RPC `get_state.todoPhases` and `set_todos`; extension event `todo_reminder`. — [docs/tools/todo.md](https://github.com/can1357/oh-my-pi/blob/main/docs/tools/todo.md), [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md)
- OMP goal mode: `/goal` slash command (`goal.enabled` default true) tracks a per-session `Goal{id, objective, status: active|paused|budget-limited|complete|dropped, tokenBudget?, tokensUsed, timeUsedSeconds, createdAt, updatedAt}` through a hidden `goal` tool (ops `create|get|complete|resume|drop`); changes are broadcast as the `goal_updated` event (also in RPC) and `goal_continuation_requested` triggers auto-continuation; `goal.continuationModes` defaults to `["interactive"]`, so goals do not auto-continue in RPC unless that setting is extended. Useful as a structured per-Lead objective/budget/status record. — [goals/state.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/goals/state.ts), [goals/settings.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/goals/settings.ts), [tui/src/tools/goal.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/tui/src/tools/goal.ts), [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md)
- Session tail semantics for status: the file tail plus `session_exit` gives "what happened last"; a fresh crash leaves a trailing `tool_execution_start` with no matching `toolResult`, which is what "interrupted" means. — [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md), [session-listing.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/session/session-listing.ts)

### Inferences
- A read-only "status probe" that opens `<session-dir>/*.jsonl`, reads the last ~32 KiB, and reports (last assistant text, `toolResult`-less `tool_execution_start`, latest `user_todo_edit`/`todo` details, `SessionStatus`) is supported by the documented format and by OMP's own listing code. It is eventually consistent (no fsync, streaming text not persisted until message end) and cannot distinguish "idle" from "process dead"; combine with a liveness signal (child PID for RPC Leads, `omp collab list --json` for TUI Leads).
- Deterministic Lead identity on OMP has to be built outside the CLI: one `--session-dir <root>/<lead-id>/` per Lead plus `open_session`/`--continue`, and a supervisor-side registry mapping `lead-id -> {pid, sessionId, sessionFile, cwd}` verified from `get_state` on every (re)connect. On Pi, `--session-id <lead-id> --name <lead-id>` does this natively.

### Gaps
- No documented guarantee that a reader can never observe a torn last line while OMP appends (the loader is lenient, but an external reader must handle a partial trailing line itself).
- The relation between the `.omp/agent/sessions` bucket encoding and profiles for multi-profile setups was not exercised.

## 4. Injecting messages into a running session from outside; steering vs follow-up semantics

### Takeaway
Inside a process the queue semantics are clear and well documented (`steer` lands after the current turn's tool calls; `followUp` after the run; OMP adds `aside` and `nextTurn` and an `interruptMode`). From outside a process the only first-class channels are RPC stdin (for Leads the supervisor spawned), the Collab relay guest protocol (requires the hosted or local relay), MCP push notifications bridged by an extension, and any custom file/socket watcher written as an extension; there is no built-in "send to session X by id" IPC.

### Cited Findings
- Pi: `steer` = "delivered after the current assistant turn finishes executing its tool calls, before the next LLM call"; `follow_up` = delivered only "when agent stops"; `prompt` during streaming needs `streamingBehavior`; queue modes `set_steering_mode`/`set_follow_up_mode` (`all` | `one-at-a-time`); `clear_queue` returns queued text; `abort` "continues queued messages when they remain". — [docs/rpc-commands.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/rpc-commands.md)
- OMP defaults: `steeringMode`, `followUpMode` = `one-at-a-time`, `interruptMode` = `immediate` (tool execution checks steering between tool calls; pending steering can abort the remaining tool calls in the turn; `wait` defers steering until turn completion). `abort_and_prompt` aborts then prompts atomically. — [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md)
- OMP extension delivery API: `pi.sendMessage(message, {deliverAs: "steer" (default) | "followUp" | "nextTurn" | "aside", triggerTurn})`; `pi.sendUserMessage(content, {deliverAs, attribution: "user" | "agent"})`. `aside` = "injected at the next agent step boundary without interrupting the current tool batch; when idle it starts a turn". Use `attribution:"agent"` for text relayed from another agent so the transcript distinguishes it. — [docs/extensions.md](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md), [docs/sdk.md](https://github.com/can1357/oh-my-pi/blob/main/docs/sdk.md)
- Pi extension delivery API: `pi.sendMessage(..., {triggerTurn, deliverAs: "steer" | "followUp" | "nextTurn"})`, `pi.sendUserMessage(content, {deliverAs: "steer" | "followUp"})`. Examples in the repo: `examples/extensions/send-user-message.ts`, `file-trigger.ts` (an extension watches `/tmp/agent-trigger.txt` with `fs.watch` and calls `pi.sendMessage({customType:"file-trigger",...},{triggerTurn:true})`; header says "Useful for external systems to send messages to the agent"), `event-bus.ts` (`pi.events`). — [types.ts](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/src/core/extensions/types.ts), [file-trigger.ts](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/examples/extensions/file-trigger.ts), [send-user-message.ts](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/examples/extensions/send-user-message.ts), [event-bus.ts](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/examples/extensions/event-bus.ts)
- OMP MCP-push bridge (documented recipe): an MCP server sends `notifications/peer_message`; an extension handles the `mcp_notification` event (`{server,method,params}`, buffered up to 100 before the first listener) and calls `pi.sendUserMessage("[from X] text",{deliverAs:"steer",attribution:"agent"})`. — [docs/extensions.md](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md)
- OMP `ctx.runEphemeralTurn(...)` runs a `/btw`-style side turn on the current conversation snapshot without appending to history and while the main turn is active; the docs mention a Synadia/NATS bridge that answers another agent's question this way (consent, authentication and audit are the extension's job). — [docs/extensions.md](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md)
- OMP intra-process peer messaging: `write agent://<id>` sends a peer message to a subagent (steers if running, prompts if idle, revives if parked), `write agent://all` broadcasts to visible live peers, `read history://` lists transcripts, `wait` blocks for the next job result / peer message; implemented by `IrcBus.global()` (process-global mailbox bus, `MAILBOX_CAP=100`, receipts `injected|woken|revived|failed`); messages appear as `irc_message` events. Availability is derived: it needs `write` in the caller's toolset and either a session able to spawn subagents or a subagent. The bus is per process, so it cannot reach another OMP process. — [docs/tools/wait.md](https://github.com/can1357/oh-my-pi/blob/main/docs/tools/wait.md), [irc/bus.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/irc/bus.ts), [irc/messaging.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/irc/messaging.ts), [docs/agent-hub.md](https://github.com/can1357/oh-my-pi/blob/main/docs/agent-hub.md)
- OMP Collab as an external control channel: `/collab` (full control) or `/collab view` publishes the live session to a relay (default `wss://my.omp.sh`, setting `collab.relayUrl`); a guest with the full link can prompt, interrupt (Esc), use Agent Hub (chat = steer the host's subagent, kill, revive) and answer host `select`/`editor` requests; view links are read-only. All payloads are AES-256-GCM sealed client-side. Wire frames guest to host: `hello`, `prompt`, `abort`, `agent-cmd`, `fetch-transcript`, `ui-response`; host to guest: `welcome`, `snapshot-chunk`, `entry`, `event`, `state`, `bus`, `agents`, `ui-request`. `collab.autoStart: view|control` hosts every interactive session automatically. The production relay is not self-hostable; a WebSocket-only stand-in exists at `packages/collab-web/scripts/local-relay.ts` (`ws://localhost:7466`). — [docs/collab.md](https://github.com/can1357/oh-my-pi/blob/main/docs/collab.md)
- OMP local Collab host registry (works across terminals, projects and profiles): each connected host publishes a private Unix domain socket (Windows named pipe) with newline-delimited JSON and a per-request bearer token; metadata under `~/.omp/run/collab-hosts` (owner-only). `omp collab list [--json]` returns per host `{instanceId, generation, pid, sessionId, sessionName, cwd, model{provider,id}, startedAt, participants, relayConnected, inputRequired, busy (true|false|null), access (view|control)}`; `omp collab link <instanceId|pid> [--view] [--json]` prints a join URL bound to the observed `generation` (`stale_generation` error if the room rotated). Only two IPC operations exist: `snapshot` and `link`. `busy` is `true` for the whole turn and falls to `false` when the turn ends but "reads false during scheduling pauses (queued follow-ups, async-job waits, compaction)". The socket is published "once its relay connection succeeds". — [docs/collab.md](https://github.com/can1357/oh-my-pi/blob/main/docs/collab.md), [collab/registry.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/collab/registry.ts), [commands/collab.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/commands/collab.ts)
- OMP `ask` tool is only registered when the session has a UI (`sessionOptions.hasUI = isInteractive || mode === "rpc-ui"` in `main.ts`); in `--mode rpc` and `--no-ui` runs it does not exist, and `--mode rpc-ui` is what routes it (and other tool dialogs) to the host as `extension_ui_request` (extension dialogs already flow through `extension_ui_request` in plain `--mode rpc` unless `--no-ui`) (`select`, `confirm`, `input`, `editor`, ...). Answer with `extension_ui_response{id,value|confirmed|cancelled}`. — [docs/tools/ask.md](https://github.com/can1357/oh-my-pi/blob/main/docs/tools/ask.md), [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md), [main.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/main.ts), [rpc-mode.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/modes/rpc/rpc-mode.ts)
- OMP session hooks that fire when a run stops: `session_stop` (main-session stop hook, awaited before settle; can return `{continue:true, additionalContext}` up to 8 times or `{decision:"block", reason}`; not fired for task/subagent sessions; waits until agent-owned background jobs are idle), plus `agent_end`, `turn_end`, and RPC `session_settled`. — [docs/extensions.md](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md)

- tmux path: Pi's stance is to run additional pi instances inside tmux ("Use tmux. ### Inferences
- For Leads that the Supervisor spawns as RPC children, `steer`/`follow_up`/`abort_and_prompt` on stdin is the reliable, ack'd, id-correlated path. Choose `steer` for "change course now" (may skip remaining tools of the current turn under `interruptMode: immediate`), `follow_up` for "after you finish", and `aside` (extension side) for non-disruptive notes.
- For interactive TUI Leads, a Lead-side extension that owns an inbox (file watcher like `file-trigger.ts` or a Unix socket like pi-intercom) is the only documented-API route that does not depend on tmux keystrokes or the relay.

### Gaps
- No documented "prompt" operation on the local Collab registry socket (only `snapshot`, `link`); driving a TUI Lead through Collab requires joining the relay as a guest, which was not tested here.
- Behavior of `steer` while an OMP Lead is inside a long `task` batch (parent turn blocked on synchronous subagents) was not verified end to end.

## 5. Extension system: authoring, loading, hooks/events, tools, commands, UI, event bus

### Takeaway
Both harnesses load TypeScript extension modules that export `default function (pi: ExtensionAPI)` and get in-process, unsandboxed access to events, tools, commands, session control, message injection and a shared `pi.events` bus. - Because handlers run in the Supervisor's process, all child-process supervision (spawn, stdout parsing, timers) belongs behind `ctx.setInterval`/try-catch and idempotent `session_shutdown` cleanup; an uncaught exception in a stdout parser would take the whole Supervisor session down.
- `ctx.agent.kind` lets one extension package behave differently in the Supervisor (register tools) versus a Lead (register reporting hooks) versus a Peer (do nothing).

### Gaps
- Hot-reload semantics (`/reload-plugins`) for a long-running child registry were not tested; `ctx.reload()` replaces the extension runtime so child handles must live outside the extension closure (module-level singleton or external process).

## 6. Subagents: Pi's stance, Pi's example extension, and OMP's `task`/`/vibe` implementation

### Takeaway
Pi deliberately has no subagent primitive ("No sub-agents ... Spawn pi instances via tmux, or build your own with extensions") and ships one example extension that runs each subagent as a separate `pi --mode json -p --no-session` child process. OMP builds subagents into the core as in-process child `AgentSession`s (not OS subprocesses) with an agent registry, async jobs, IRC-style peer messaging, worktree isolation, structured `yield` results, a live Agent Hub, and RPC frames for observation; depth is capped by `task.maxRecursionDepth` (default 2).

### Inferences
- OMP's Peer layer (task subagents) maps directly onto the "Peer" role of SLP and needs no extra machinery: each Lead just runs normal `task` calls. What OMP does not give is a Lead layer above a full OMP process: the IRC bus, `AgentRegistry`, async job manager and `proc://` handles are all process-scoped, so Peers die with their Lead process (they can be revived from JSONL only inside a process that reopens the session).
- `/vibe` is the closest built-in analogue to "one director, many persistent workers", but its workers are in-process subagents (depth 1), TUI-only, and killed when the mode exits, so it cannot supervise independent OMP sessions on different repos; it is useful as design inspiration for the tool set (`spawn/send/wait/kill/list`).
- `task.maxRecursionDepth` (default 2) is not a constraint for the SLP mapping if Leads are top-level sessions (depth 0) and Peers are depth 1; a vibe-style worker acting as a Lead would leave only one more level.

### Gaps
- Mario's full blog rationale for "no sub-agents" could not be read; only the README one-liner and a secondary summary are cited.
- The exact tools/approval behavior for a top-level RPC Lead running `task` with `tools.approvalMode` unspecified follows the default `yolo`; effects of RPC `protocolDefault` on `task.*` were read from settings source but not run.

## 7. Community extensions and packages for multi-agent orchestration / inter-session communication

### Takeaway
The Pi ecosystem has hundreds of `pi-package` extensions for subagents, swarms, messengers and tmux; the most credible for a Supervisor design are pi-subagents (3.8k stars, foreground in-process children plus detached background runner, fleet inspector), pi-intercom (Unix-socket broker, `intercom` tool with `list/send/ask/reply`), pi-messenger (file-based mesh, `pi.sendMessage` steering), pi-agent-teams (leader/worker with mailboxes + RPC + worktrees) and tmux-based tools. OMP-specific options are fewer and young: `@bloodf/oh-my-agent` (local daemon with rooms and parentage), `omp-fabric`, `@genee/omp-whip`, `ompweb`, `omp-telegram`. `pi-paseo-orchestration` literally names a "Supervisor - Lead - Peer" model but targets Pi + Paseo, not OMP.

## 8. Design philosophy and known limitations to design around

### Takeaway
Pi's philosophy (Mario Zechner) is minimal core, no built-in subagents/plan mode/todos/background bash, orchestrate by spawning more Pi instances (ideally in tmux for observability) or via extensions; OMP's philosophy is "batteries included, tuned by real-world use, configurable rather than hidden". The design must work around: process-scoped subagent/registry/IRC state, no `--session-id`/`--name` in OMP, an unsandboxed in-process extension model, headless removal of the `ask` tool, opaque relay dependence for Collab, and OMP's frozen upstream sync.

### Cited Findings
- Pi README "Philosophy" list (verified in the npm readme of `@mariozechner/pi-coding-agent@0.73.1`, published 2026-05-07): by default the model gets four tools (`read`, `write`, `edit`, `bash`); "No MCP", "No sub-agents. ... Spawn pi instances via tmux, or build your own with extensions, or install a package that does it your way", "No permission popups. Run in a container", "No plan mode. Write plans to files", "No built-in to-dos. They confuse models. Use a TODO.md file", "No background bash. Use tmux. Full observability, direct interaction". — [npm readme @mariozechner/pi-coding-agent 0.73.1](https://registry.npmjs.org/@mariozechner/pi-coding-agent)
- Secondary summary of Mario's blog (web-search snippets, not read first-hand): design principle "if I don't need it, it won't be built"; system prompt under ~1,000 tokens; sub-agents treated as a black box inside a black box, with the alternative of a new Pi instance in tmux for full observability. — search results citing [Mario Zechner on X](https://x.com/badlogicgames/status/2001088673698189732) and mariozechner.at (unverified, secondary)
- Pi explicitly has no built-in permission system: "By default, it runs with the permissions of the user and process that launched it"; recommends Docker/OpenShell/Gondolin. — [pi-mono README.md](https://github.com/badlogic/pi-mono/blob/main/README.md), [docs/containerization.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/containerization.md)
- Pi's docs call out that extensions run in-process with the user's OS permissions and can read prompts, files, credentials and session history. — [docs/extensions.md (Pi)](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/extensions.md)
- Pi's forward direction: durable Session/Agent Harness, Chord services and an experimental server/client, "RFCs" at https://rfc.earendil.com/keyword/pi/, and a separate `earendil-works/pi-chat` for Slack/chat automation. — [pi-mono README.md](https://github.com/badlogic/pi-mono/blob/main/README.md)
- OMP philosophy (README): "Keep interactive terminal-first UX for real coding work; include practical built-ins (tools, sessions, branching, subagents, extensibility); make advanced behavior configurable rather than hidden"; extension primitives are the same as built-ins ("Nothing is reserved"); "Ask omp to write the piece you're missing, then `/reload-plugins`". — [README.md](https://github.com/can1357/oh-my-pi/blob/main/README.md)
- OMP's own worker-tier guidance (vibe): "Workers start blank and never see the director's conversation" - the director must write self-contained briefs; "worker completion means the turn settled, not that its claims are correct" - verify by reading files. The same brief discipline applies to Supervisor-to-Lead prompts. — [docs/vibe-mode.md](https://github.com/can1357/oh-my-pi/blob/main/docs/vibe-mode.md)
- Child sessions "do not inherit conversation history"; carry-over is workspace tree, skills, context files, shared `local://` root and approved plan reference. — [docs/tools/task.md](https://github.com/can1357/oh-my-pi/blob/main/docs/tools/task.md)
- Known limitations recorded in the docs/source: (1) `AgentRegistry`, `IrcBus`, `AsyncJobManager`, `proc://` are process-scoped; the SDK says multiple top-level sessions in one process need private registries; (2) yield vs settled - `prompt_result` is not "session done" because async jobs can wake it, use `session_settled`/`isSettled`; (3) `session_stop` and `cache_warming_decision` never fire in subagent sessions; (4) plan mode restricts subagents to read-only tools; (5) `ask` only exists with a UI; (6) `--mode rpc` forbids `@file` args; (7) RPC message pagination can fail with `session_busy`/`stale_cursor`; (8) frames above 64 MiB reassembly cap fail; (9) advisor rows cannot be messaged, revived or killed; (10) Collab relay is hosted, not self-hostable, and `busy` is null on older hosts. — [docs/sdk.md](https://github.com/can1357/oh-my-pi/blob/main/docs/sdk.md), [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md), [docs/extensions.md](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md), [docs/agent-hub.md](https://github.com/can1357/oh-my-pi/blob/main/docs/agent-hub.md), [docs/collab.md](https://github.com/can1357/oh-my-pi/blob/main/docs/collab.md), [docs/tools/ask.md](https://github.com/can1357/oh-my-pi/blob/main/docs/tools/ask.md)
- Approval default: OMP `tools.approvalMode` defaults to `yolo`; headless subagents are forced to `yolo`; user `tools.approval.<tool>: deny|allow|prompt` still applies. — [docs/approval-mode.md](https://github.com/can1357/oh-my-pi/blob/main/docs/approval-mode.md)
- Secondary reporting of Pi's philosophy exists in several blog posts (for example the "Slop, Speed, and Discipline" and "Pi: A Better AI Coding Tool, Locked Out" pieces surfaced in search) but were not opened. — search results only

### Inferences
- Pi's "spawn Pi via tmux/bash" recommendation and OMP's in-process subagents are not competing for the Lead layer: use in-process `task` for Peers (cheap, structured, observable through RPC frames) and separate processes for Leads (independent repos/contexts/failure domains).
- Mario's "no background bash / no todos" stance means Pi-only Leads offer less state to report; OMP's `todo` phases (with `blocked` + `blocker`) and `ask` are direct status/blocked signals, so Leads should be OMP.

### Gaps
- No first-hand read of the 2025-11-30 Mario Zechner post, the "Thoughts on slowing the fuck down" post, or any OMP-author writing about orchestrating many sessions.
- No community war-stories (Reddit/HN) on running many OMP sessions in parallel could be retrieved.

## 9. Building blocks for a Supervisor on OMP

### Takeaway
Best-supported today: a Supervisor process that owns a durable Lead registry and drives each Lead as a child `omp --mode rpc` (`--mode rpc-ui` if `ask` must reach the human), using `--session-dir <root>/<lead-id>` + `open_session`/`--continue` for identity and resume, `get_state`/`prompt_result`/`session_settled`/subagent frames for monitoring, and either OMP host tools (`set_host_tools`) or an OMP extension/MCP server to expose `spawn_lead`/`send_to_lead`/`get_lead_status`/`list_leads` to the Supervisor LLM. roboomp in the OMP repo is a working reference for this pattern (queue, worker pool, per-task worktree + session dir, resume, audit table). tmux-driven interactive Leads are the fallback when the human must be able to attach to each Lead.

### Cited Findings (option A to F, each with what the code/docs support)

**Option A: Supervisor session = OMP interactive session + Supervisor extension that spawns child RPC Leads**
- Support: extension `registerTool` (tools `spawn_lead`, `send_to_lead`, `get_lead_status`, `list_leads`, `wait_leads`, `kill_lead`), `pi.exec`/`Bun.spawn`, managed timers `ctx.setInterval`, `pi.sendUserMessage(...,{deliverAs:"aside"|"followUp"|"steer", attribution:"agent"})` for "Lead finished/blocked" notices, `pi.appendEntry` for persisted registry, widgets/status (`ctx.ui.setStatus`, `setWidget`) for a fleet HUD, `session_start`/`session_shutdown` for lifecycle. Child protocol: `omp --mode rpc --no-ui --session-dir <dir> --append-system-prompt "<lead-id contract>" --config <lead.yml> --cwd <repo>`; commands `prompt`, `steer`, `follow_up`, `abort`, `get_state`, `get_last_assistant_text`, `get_entries{since}`, `set_subagent_subscription`, `set_session_name`. — [docs/extensions.md](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md), [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md), [docs/cli-reference.md](https://github.com/can1357/oh-my-pi/blob/main/docs/cli-reference.md)
- Pros: user talks to one normal OMP TUI session; Supervisor keeps OMP's own features (todo, memory, Agent Hub for its own Peers, `wait`); notices arrive as first-class messages; structural session isolation because every Lead has a private stdio pipe and session dir.
- Cons: in-process extension with no isolation (a throw takes down the Supervisor session); Leads exit when the Supervisor exits (RPC docs: when stdin closes the process drains accepted commands, disposes the session and exits 0; stdio pipes cannot be re-attached), so recovery is respawn + `--continue`/`open_session`, which restores the transcript but not an in-flight turn (a turn cut off by process exit is closed with a synthetic aborted assistant message on resume when a `session_exit` marker was written; after SIGKILL no marker exists and the file tail just reads as `interrupted`); Leads are invisible to the user unless the extension mirrors output; extension state must survive `ctx.reload()`; `ask` needs `rpc-ui` and a host UI-bridge.

**Option B: External host process (Python `omp_rpc` or Bun) owns Leads AND the Supervisor is one more `omp --mode rpc` whose tools are host tools**
- Support: `set_host_tools` + `host_tool_call/host_tool_result` (Python `host_tool(...)` helper) so the Supervisor LLM calls host-implemented `spawn_lead` etc.; host uses `RpcClient` per Lead (README: use separate instances for concurrency), SQLite registry, `WorkerPool`, restart recovery via `--continue`, audit log of every tool call - exactly what `python/robomp` does. Human interface can be anything (CLI, web such as ompweb, Telegram such as omp-telegram, or attach the Supervisor to a TUI via ACP/collab). — [python/omp-rpc/README.md](https://github.com/can1357/oh-my-pi/blob/main/python/omp-rpc/README.md), [python/robomp/AGENTS.md](https://github.com/can1357/oh-my-pi/blob/main/python/robomp/AGENTS.md), [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md)
- Pros: strongest isolation and durability (host can outlive every agent), deterministic registry and audit, host controls resources/queues, no extension crash risk; typed client already exists; works headless on a server.
- Cons: more code (a host service), the Supervisor "chat" surface must be built or bridged (no TUI unless bridged), `omp-rpc` client is synchronous/thread-based, single-flight per client, RPC-mode defaults differ from interactive defaults (pin settings with `--config`).

**Option C: SDK host (Bun/TypeScript), Leads as in-process `createAgentSession` instances**
- Support: `createAgentSession({cwd, sessionManager: SessionManager.create(cwd, dir), settings: Settings.isolated({...}), agentRegistry: new AgentRegistry()})` (option `agentRegistry?: AgentRegistry` in `CreateAgentSessionOptions`, default `AgentRegistry.global()`), `session.subscribe`, `prompt/steer/followUp/abort/dispose`, extension inline factories; the SDK doc explicitly says private `AgentRegistry` per top-level session. — [docs/sdk.md](https://github.com/can1357/oh-my-pi/blob/main/docs/sdk.md), [sdk.ts](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/sdk.ts)
- Pros: zero IPC, richest event access (`AgentSessionEvent`, `eventBus`), can share `AuthStorage`/`ModelRegistry`.
- Cons: single Bun process = shared failure domain and process-wide state (settings holder, natives), Bun-only, memory growth across N sessions, no crash isolation; less battle-tested than RPC (docs steer non-Node consumers and isolation needs to RPC).

**Option D: tmux-driven interactive Leads (Pi's upstream philosophy) with an OMP-native observation channel**
- Support: Pi documents tmux use (`docs/tmux.md`, extended-keys setup; OMP has no dedicated tmux doc, but its TUI is an ordinary terminal app - not verified here); `tmux new-window "omp --session-dir ... "`, `tmux send-keys`, `tmux capture-pane`; liveness/status via `omp collab list --json` (needs `collab.autoStart: view|control` and a relay connection: fields `sessionId`, `cwd`, `model`, `busy`, `inputRequired`, `pid`) plus session JSONL tailing (`SessionManager.list` statuses, todo phases, `tool_execution_start`/`session_exit` markers). Community references: pi-side-agents, pi-interactive-subagents, pi-suba, pi-tmux-orchestrator. — [docs/collab.md](https://github.com/can1357/oh-my-pi/blob/main/docs/collab.md), [docs/session.md](https://github.com/can1357/oh-my-pi/blob/main/docs/session.md)
- Pros: the human can attach to any Lead and see the real TUI (Agent Hub, cards); matches upstream guidance; no host protocol to maintain.
- Cons: input via send-keys is unacknowledged and racy (typing into an editor while a turn is running becomes steer/queue depending on TUI state), output must be scraped or read from JSONL, `busy` from the registry depends on the relay connection (`relayConnected`) and is `false` during scheduling pauses, `busy: null` on old hosts, and no documented programmatic prompt API for a TUI session other than a relay guest; identity confusion risk is the highest of all options (pane names vs sessions).

**Option E: File/mailbox + Lead-side reporting extension (works with TUI or RPC Leads)**
- Support: a small extension loaded into every Lead (`-e reporter.ts` or `.omp/extensions/`) subscribes to `session_start`, `agent_start`, `agent_end`/`session_stop`, `turn_end`, `tool_execution_start/end`, `todo_reminder`, `auto_compaction_*`, `goal_updated` and atomically writes `status.json` plus append-only `events.jsonl` under `~/.omp/supervisor/<lead-id>/`; an inbox watcher (`fs.watch`, as in Pi's `file-trigger.ts`) turns `inbox/*.json` into `pi.sendUserMessage(text,{deliverAs,attribution:"agent"})`; `ctx.agent.kind` limits it to main sessions; `pi.appendEntry("com.slp.lead", {...})` embeds the Lead identity into the JSONL itself. Community precedent: pi-messenger, pi-relay, pi-suba, oh-my-agent. — [docs/extensions.md](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md), [file-trigger.ts](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/examples/extensions/file-trigger.ts)
- Pros: transport-agnostic, survives restarts and crashes (files), inspectable, cheap; supervisor can answer "progress of task C?" by reading `status.json` without waking the Lead; identity is written by the Lead itself, defeating registry drift.
- Cons: eventual consistency and file-race handling are yours; extension runs unisolated in every Lead; status is only as truthful as the extension's hooks; polling/`fs.watch` quirks; needs a writer-side atomic-rename discipline; no ack semantics unless you add them.

**Option F: adopt an existing community package**
- `@bloodf/oh-my-agent` (OMP plugin, local daemon, rooms/DMs, parentage, TUI/CLI/browser clients, budget parking) is the closest OMP-native "many long-lived agents" product but models agents as daemon-owned workers rather than full OMP sessions per task; `omp-fabric` (mesh/actors); `pi-intercom` (needs compat verification on OMP); `pi-paseo-orchestration` (SLP semantics, Pi + Paseo). Maturity: young (created Sep 2026), single-maintainer, low star counts. — [npm readme oh-my-agent](https://registry.npmjs.org/@bloodf/oh-my-agent), [omp-fabric](https://github.com/tickernelz/omp-fabric), [pi-intercom](https://github.com/nicobailon/pi-intercom), [pi-paseo-orchestration](https://github.com/duongvm57/pi-paseo-orchestration)

**Cross-cutting mechanisms that make the design robust (all grounded above)**
- Never-confuse-sessions guard: (1) one child process and one `--session-dir` per Lead, so RPC stdio is a private channel and cross-talk is structurally impossible; (2) on every (re)connect call `get_state` and assert `sessionId`/`sessionFile` against the registry; (3) tag each Lead with an immutable id in three places: `--append-system-prompt`, `set_session_name`, and a namespaced `pi.appendEntry` entry; (4) correlate every command by `id` and every turn by `prompt_result.id`; (5) wrap every Lead message relayed into the Supervisor with `attribution:"agent"` and a `[lead:<id>]` prefix. On Pi use `--session-id <lead-id> --name <lead-id>` for a native stable id.
- Accurate progress answers: combine live `get_state` (`isStreaming`, `isSettled`, `hasPendingAsyncWork`, `todoPhases`, `contextUsage`, `queuedMessageCount`), `set_subagent_subscription` `progress` frames (`currentTool`, `lastIntent`, `cost`, `tokens`), `get_last_assistant_text`, `get_session_stats`, and (when the Lead is not attached) the JSONL tail (`SessionStatus`, last assistant message, `todo` details). Prefer `session_settled` over `agent_end` to decide "done".
- "Blocked" signals available without custom code: `extension_ui_request` (from `ask` in `--mode rpc-ui`), `todo` status `blocked` with `blocker`, `prompt_result.status: "error"` with `error.retryable`, `notice`, `auto_retry_*`/`retry_fallback_*`, `credential_disabled`, `tool_approval_requested`, `extension_error`, `subagent_lifecycle.status: failed|aborted`.
- Per-Lead configuration: pass `--config <lead.yml>` overlays (settings such as `task.maxConcurrency`, `task.maxRecursionDepth`, `task.isolation.enabled`, `tools.approvalMode`, `task.agentModelOverrides`), `--tools`, `--model`, `--thinking`, `--max-time`, `--cwd`, `--add-dir`, `--profile` (isolated auth/sessions/settings), and pre-seed the plan with `set_todos`. RPC hosts otherwise start from neutral `protocolDefault` values, not the human's interactive preferences. — [docs/rpc.md](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md), [docs/cli-reference.md](https://github.com/can1357/oh-my-pi/blob/main/docs/cli-reference.md)

### Inferences
- Recommended stack for the stated SLP need: Option B or Option A as the control plane, Option E's reporting hooks as an optional add-on for Leads that a human also attaches to, and OMP's built-in `task` as the Peer layer. Option D only when "watch the real TUI" outweighs reliability.
- The Supervisor tool set can mirror OMP's own `/vibe` verbs: `lead_spawn`, `lead_send` (steer vs follow_up flag), `lead_wait` (first settled of N, with timeout, acknowledging results), `lead_kill`, `lead_list`, plus `lead_status` (structured JSON built from `get_state` + progress frames) and `lead_history` (paged `get_entries`/`get_messages_page`).
- Design decision to make explicitly: whether Peers should be able to escalate to the human. In headless RPC Leads the `ask` tool disappears; escalation must go through `rpc-ui` dialogs, a host tool (`escalate`), or the `todo` `blocked` status.

### Gaps
- No end-to-end test of any option was run in this session; feasibility statements are from source/docs only.
- The two documented ways to drive a TUI session from outside (tmux keystrokes, Collab relay guest) have no verified programmatic prompt path; pi-intercom-style Lead-side sockets would need to be built and tested on OMP.
- Concurrency ceilings (how many `omp --mode rpc` processes a laptop sustains, memory per session with LSP/eval kernels) were not measured; `async.maxJobs` default 100 and `task.maxConcurrency` are per-process limits only.
