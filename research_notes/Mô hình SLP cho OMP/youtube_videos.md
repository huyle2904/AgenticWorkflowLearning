## 2. What orchestration pattern is demonstrated, and how does it map to Supervisor / Lead / Peer?

### Takeaway
The pattern (as documented in the firstmate repo and described by third parties for the talk) is a three-tier hierarchy: Captain (human) -> First mate (single always-on supervisor; the only agent the human talks to) -> Secondmates (optional persistent per-domain sub-supervisors) and Crewmates (ephemeral one-task worker agents, each a full harness session in its own tmux window/Herdr tab and git worktree). It maps almost one-to-one onto Supervisor -> Lead, with one important difference: firstmate has no "Peer subagents inside a session" tier; the crewmate itself is the executing agent.

### Cited Findings
- Kun's own org-chart post (search snippet, x.com blocked): "with Sonnet 5 introduced, here's the latest complete org chart of my agents. this is my real setup and how i get work done every day, not gimmicks 1. i mainly talk to just one agent - the firstmate. i always use the intelligent model with max reasoning here, because this model hand[les] ..." — [Kun Chen on X](https://x.com/kunchenguid/status/2072102019729613181) (A; tweet id decodes to 2026-06-30). The rest of the post as summarized by the search tool (secondary): firstmate manages some secondmates and some crewmates via tmux; secondmates have a persistent charter (project ABC -> secondmate 1, project D -> secondmate 2); crewmates are ephemeral, one per task, killed when done; when the first mate or a secondmate dispatches a crewmate it picks the harness, model and reasoning effort; occasionally he talks directly to secondmates. This full text was not readable directly.
- Firstmate README: "You talk to a single agent - the first mate - and it runs the crew for you: spawning autonomous agents in a visible session backend, giving each a clean git worktree, supervising them to completion, and handing you finished PRs, approved local merges, or standalone investigation reports." "firstmate is not a model, not a harness, not a skill, not an MCP server, and not a CLI ... an agent distro" (the cloned repo, `AGENTS.md`, skills and scripts; launching a supported harness inside it makes that agent the first mate) — [firstmate README](https://github.com/kunchenguid/firstmate) (C).
- Roles: "You are the first mate. The user is the captain. This file [AGENTS.md] is your entire job description." Hard rules: never write to a project (crewmates do), never merge a PR without the captain's explicit word, never tear down unlanded work, "Crewmates never address the captain. All crewmate communication flows through firstmate", report outcomes faithfully — [firstmate AGENTS.md](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md) (C).
- Secondmates: "A secondmate is a crewmate with an isolated firstmate home and a charter, not a second architecture." Each has its own `FM_HOME`, state, backlog, projects and session lock; routed via `data/secondmates.md` (natural-language scopes); idle by default; can run a different harness than crewmates; can be local or on an SSH host — [AGENTS.md](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md), [architecture.md](https://github.com/kunchenguid/firstmate/blob/main/docs/architecture.md) (C).
- Two task shapes: ship (delivers an authorized change via PR/local merge) and scout (investigation; report at `data/<id>/report.md`, never a PR) — [README](https://github.com/kunchenguid/firstmate) (C).
- Per-task dispatch profile: the first mate resolves harness/model/effort per task from `config/crew-dispatch.json` and `quota-axi` quota data — [AGENTS.md section 4](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md); [combo-chen issue #264 describing it](https://github.com/thellmwhisperer/combo-chen/issues/264) (B/C).
- Kun's rule of thumb (LLM-distilled from his X/Substack/YouTube transcripts, secondary): "by default he suggests one firstmate that absorbs everything until it is overloaded, then spawning second mates, including per-project second mates he can talk to directly"; "flat orchestration stops scaling once many agents run at once, so useful systems need layered roles, escalation paths, and durable project ownership"; he prefers "persistent, independent, observable sessions instead of brittle in-process subagents"; and "direct leaf-node steering ... higher-fidelity but non-scaling" versus an orchestrator that "scales attention at the cost of occasional misalignment" — [kun/OPINIONS.md](https://github.com/kunchenguid/kun/blob/main/OPINIONS.md) (C, machine-generated digest of his public statements; not verbatim).
- The VISION doc caps depth: "The command structure stays flat: every layer between the captain's intent and the acting agent costs fidelity and tokens, so depth is capped, not grown." It also says the first mate "stays free to command by never doing the work itself: even the smallest change is a worker's job" — [VISION.md](https://github.com/kunchenguid/firstmate/blob/main/VISION.md) (C).
- Supported harnesses for the first mate: Claude Code, Grok, Pi (co-primary), plus Oh My Pi (`omp`), Codex, OpenCode, Cursor Agent CLI. "Oh My Pi (`omp`), a Pi fork, is verified as a primary with the same extension-owned watcher model as Pi and a stronger turn-end guard: its blocking `session_stop` hook compels a continuation instead of requesting one." Start `omp` with the firstmate checkout as cwd so it auto-discovers `.omp/extensions/*.ts` with no trust dialog — [README](https://github.com/kunchenguid/firstmate) (C). Crewmates/scouts can additionally use gemini, rovo, agy, devin, muse ([AGENTS.md section 4](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md)).
- Session backends: tmux (reference default), Herdr, experimental Zellij/Orca/cmux; every crewmate is a visible tmux window / Herdr tab the human can watch or type into; typing into a crewmate window is treated as authoritative direct captain intervention — [README](https://github.com/kunchenguid/firstmate), [tmux-backend.md](https://github.com/kunchenguid/firstmate/blob/main/docs/tmux-backend.md) (C).

Mapping table (my inference, based on the above):

| SLP role | firstmate analogue | Notes |
|---|---|---|
| Human | Captain | talks only to the supervisor; may still type into any worker window (authoritative) |
| Supervisor | First mate | read-only over projects; never does project work; holds intent, backlog, decisions; only reaches the human for decisions/outcomes |
| Lead (long-lived, per domain) | Secondmate | persistent charter, own home/state/backlog/lock, routed replies via status/doc pointers |
| Lead (one task per session) | Crewmate (ship/scout) | ephemeral; own worktree; reports only via status file |
| Peer (subagent inside Lead's session) | no direct analogue | firstmate deliberately does not manage in-process subagents; the crewmate is the worker |

### Inferences
- The user's "session 1 = Lead for task A" matches a firstmate crewmate (per-task) or secondmate (per-domain). If Leads are OMP main agents that use OMP's own subagents as Peers, that lowest tier is outside firstmate's model and must be designed separately (or left entirely to OMP's built-in task/subagent mechanism).
- firstmate's own guidance (cap depth, prefer observable persistent sessions over in-process subagents for the top levels) argues for keeping the Supervisor -> Lead link out-of-process (separate OMP sessions) and using in-process subagents only below the Lead.
- Because firstmate lists `omp` as a verified primary and already ships `.omp/extensions/*.ts`, the Supervisor could plausibly be firstmate itself run under OMP, rather than a from-scratch build. Whether it fits the user's Lead/Peer design is a design decision for the report writer.

## 3. What mechanisms prevent confusion between parallel sessions?

### Takeaway
firstmate never relies on conversation memory or pane text to know "which session is which". It keys everything to a task id (tmux window `fm-<id>`, `state/<id>.status`, `state/<id>.meta`, `FM_TASK_ID` env var in the pane, branch `fm/<id>`, one worktree per task), keeps durable append-only records on disk, derives "current state" by a deterministic script from authoritative sources (never from the last status line), and treats unknown state as unknown. This is directly reusable for a Supervisor that must answer "what is the progress of task C?" accurately.

### Cited Findings
- Identity per task: "Each task window is named `fm-<id>`" ([tmux-backend.md](https://github.com/kunchenguid/firstmate/blob/main/docs/tmux-backend.md)); `bin/fm-spawn.sh` "exports the task id as `FM_TASK_ID` into every ship and scout pane"; ship branch `fm/<id>` by default; scout report `data/<id>/report.md`; per-task records `state/<id>.status` and `state/<id>.meta` ([architecture.md](https://github.com/kunchenguid/firstmate/blob/main/docs/architecture.md), [AGENTS.md](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md)) (C).
- Isolation: every task runs in its own disposable git worktree (pooled by `treehouse`); the spawn "must resolve a genuine isolated task worktree distinct from the primary checkout; a failed isolation assertion stops the task"; briefs make the worker verify `pwd -P` / `git rev-parse --show-toplevel` and stop with `blocked` if it landed in the primary checkout — [AGENTS.md section 7](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md), [architecture.md](https://github.com/kunchenguid/firstmate/blob/main/docs/architecture.md) (C). The PR study adds the caveat "A worktree isolates files; shared databases, credentials, and deployment targets need their own controls" (B).
- Steering messages are durable records, not raw keystrokes: `fm-send` writes the message to the task's steering inbox and the worker's terminal "receives only a constant doorbell line", with the watcher re-ringing an unacknowledged message and escalating a stuck one; `fm-send` "fails closed unless `FM_HOME` is explicit, so a steer cannot silently resolve against another home"; lifecycle control (interrupt/exit/relaunch) goes through a separate `fm-control.sh <task-id> ...` plane, never through the text path — [AGENTS.md sections 2 and 7](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md) (C).
- Request/response correlation with secondmates: marked requests carry a `corr=<id>` token that the secondmate must echo in its status reply; the parent "guards every reply-bearing marked request against a missing correlated report without reading the secondmate conversation"; the first mate must not read a secondmate's chat — [architecture.md "Optional secondmates"](https://github.com/kunchenguid/firstmate/blob/main/docs/architecture.md), [fm-brief.sh](https://github.com/kunchenguid/firstmate/blob/main/bin/fm-brief.sh) (C).
- Worker status protocol: a worker appends one line `state [at=<epoch>] [key=<slug>]: text` to its status file with states `working`, `needs-decision`, `blocked`, `paused`, `done`, `failed` (plus `resolved`); only sparse, supervisor-actionable events are appended, "Never append `working:` merely to acknowledge receipt"; a decision/blocker "stays open until a `resolved` line carrying its exact key lands" — [fm-brief.sh](https://github.com/kunchenguid/firstmate/blob/main/bin/fm-brief.sh) (C).
- Truth vs. event log: "state/<id>.status is an append-only, best-effort EVENT LOG ... `tail -1` of that log reports the last EVENT, not the current STATE." `bin/fm-crew-state.sh` prints one deterministic line `state: <working|parked|done|blocked|paused|failed|unknown> · source: <run-step|pane|status-log|remote-endpoint|none> · <detail>`, reads the authoritative source (validation-pipeline run step, else pane busy signature) and reconciles the possibly stale log against it; it is "no heuristics and no LLM"; an unreadable PR identity yields "an honest unknown, never an optimistic merged claim" — [fm-crew-state.sh header](https://github.com/kunchenguid/firstmate/blob/main/bin/fm-crew-state.sh) (C). AGENTS.md repeats: "A status line is a wake event, not current state; use `bin/fm-crew-state.sh` when current state matters."
- Busy/idle is semantic, per harness adapter: omp reports "through its extension's `agent_start` and `agent_end` without `willContinue`"; Pi via `agent_start`/`agent_settled` confirmed by `ctx.isIdle()`; "Missing, malformed, stale, untrusted, or unverified semantic state is unknown, never idle, and unknown is never promoted to busy either"; each record is bound to an "incarnation token" so events from a superseded incarnation are rejected; child processes, CPU and file mtimes are not state signals — [architecture.md "Busy state is semantic, per adapter"](https://github.com/kunchenguid/firstmate/blob/main/docs/architecture.md) (C).
- Evidence layering (as described by an outside adopter): "run records > pane busy signature > status log", where "a dead pane without a run reports unknown instead of trusting a stale log" — [combo-chen issue #264](https://github.com/thellmwhisperer/combo-chen/issues/264) (B).
- Supervision loop: a zero-token bash watcher `fm-watch.sh` sleeps on the fleet and wakes the model only for `signal:` (worker status), `stale:` (quiet pane not provably working), `check:` (PR merge, inbox notes...) and `heartbeat:` events; wakes go into a durable queue that the model must drain first and acknowledge after handling with the printed `--ack-through` command; "No turn ends blind while work is under way" (turn-end guard) — [AGENTS.md section 8](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md), [architecture.md](https://github.com/kunchenguid/firstmate/blob/main/docs/architecture.md) (C). A quiet pane is not proof of a stuck worker (declared `paused:` waits defer stale escalations).
- Durable ledger: opt-in `state/fleet-ledger.jsonl` (append-only JSON Lines: `task.dispatched`, `task.status`, `task.pr_ready`, `task.merged`, `task.cleaned_up`, each with `v`, `ts`, `event`, `task`) "that outside tools can read" — [docs/fleet-ledger.md](https://github.com/kunchenguid/firstmate/blob/main/docs/fleet-ledger.md) (C).
- Answering "what is going on": `/bearings` runs one deterministic snapshot command (`bin/fm-bearings-snapshot.sh --json`) and renders four sections: Captain's Call (open decisions, PRs ready with full URLs, credentials), Recently Landed, Underway (each live direct report with current state), Charted Next (queued/gated work); it is read-only and forbids scraping status tails or conversation history; `/ahoy` recaps events and open decisions since the last real captain message — [bearings SKILL.md](https://github.com/kunchenguid/firstmate/blob/main/.agents/skills/bearings/SKILL.md), [README](https://github.com/kunchenguid/firstmate) (C).
- Backlog: a durable queue (`data/backlog.md` by default, `tasks-axi` backend) tracks work items only; "A decision is simply a task held for the captain" — [AGENTS.md section 10](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md) (C).
- Restart-proofing: "Everything that matters survives the death of any conversation: work in flight, promises made, decisions pending ... live in durable records, never in chat memory. The fleet reconciles from disk and from live session state, so killing any session, including the first mate's own, loses nothing" — [VISION.md](https://github.com/kunchenguid/firstmate/blob/main/VISION.md) (C). Session start runs `bin/fm-session-start.sh` once, takes a session lock (a lock-refused session stays read-only), and prints a recovery digest ([AGENTS.md section 3](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md)).
- Deterministic scripts vs. judgment: "Logic that can be exact lives in deterministic scripts; work that requires understanding lives in an agent; the two never mix." — [VISION.md](https://github.com/kunchenguid/firstmate/blob/main/VISION.md) (C).
- Third-party lesson attributed to the talk (video 2): "Count dispatched tasks against your ask. In the talk, one of three requested prototypes was never dispatched, and nobody noticed for most of the session." and "Feedback that bypasses the liaison leaves its records stale until the worker reports, so reconcile them." — [PR study (raw HTML)](https://raw.githubusercontent.com/KrishRVH/random-scripts/main/misc/AI%20Product%20Engineer/AI%20Product%20Engineer%20Plan.html) (B; AI-assisted summary, unverifiable without the video).

### Inferences
- The minimum "never confuse sessions" kit visible here: (1) one stable task/session id used as the primary key in every artifact (window/session name, env var, branch, worktree, status file, ledger row, inbox message); (2) an explicit home/namespace argument that scripts refuse to guess; (3) a correlation id on every supervisor->lead request that must be echoed in the reply; (4) status as an append-only event log plus a separate deterministic "current state" resolver with an explicit `unknown`; (5) an incarnation/generation token so stale events from a replaced session are ignored (relevant to OMP `/new`, `/resume`, `/fork`, which firstmate's OMP extension handles with generation ownership).
- A Supervisor that answers "progress of task C?" should answer from the resolver + ledger/backlog for id C and cite evidence and freshness, not from its own chat memory or the last message it saw; and it should reconcile "asked vs. dispatched" lists to catch silently dropped tasks (the missed prototype).

## 4. What worked, what did not, and practical tips

### Takeaway
Claimed results are self-reported (throughput, quota use, 1k -> 3k stars, "changed their lives"); no independent measurement was found. Documented caveats: firstmate's brain is a very large LLM-interpreted instruction file subject to compaction, it lacks forensics/journal and a reviewer verdict contract (per an outside adopter), a supervisor can silently drop a requested task (seen in the talk per a third party), and Kun himself advises not adopting it until juggling sessions is clearly painful.

### Cited Findings
- Claimed throughput/attention (video 2, third-party summary): 36 projects, 7+ parallel workers from one session; "His binding constraint is attention, not tokens" — [PR study](https://github.com/KrishRVH/random-scripts/pull/1) (B).
- Claimed cost efficiency (video 3): whole full-stack app built with `gpt-5.6-luna` alone using 4% of a weekly quota — [Kun Chen on X](https://x.com/kunchenguid/status/2082882994109620683) (A, self-reported).
- Adoption claims (self-reported): "firstmate just crossed 1k stars" (tweet id decodes to 2026-07-12) and "3k stars ... the first project where i repeatedly heard people say it 'changed their lives'" (2026-08-10) — [1k tweet](https://x.com/kunchenguid/status/2076101905869414785), [3k tweet / Substack note](https://substack.com/@kunchenguid/note/c-311919739) (A). The GitHub profile page read on 2026-09-29 listed firstmate at 7.3k stars ([kunchenguid profile](https://github.com/kunchenguid)) (via WebFetch summarizer).

## 6. Takeaways for building Supervisor -> Lead -> Peer on OMP

### Takeaway
firstmate is a working, public precedent for "Supervisor over many parallel sessions" that already supports OMP as its supervisor harness; the transferable design is: one thin, contract-driven supervisor; one session per task/domain with a stable id; a file-based status/decision/inbox protocol; a deterministic state resolver; a zero-token watcher that wakes the supervisor only on events; and explicit authority rules. Where the user's design goes beyond it (Peers as in-process subagents inside each Lead), firstmate offers no pattern.

### Cited Findings
- OMP integration points that firstmate already uses (all read from source): project-local `.omp/extensions/*.ts` auto-discovered from cwd with no trust dialog; an extension registers a tool `fm_watch_arm_omp` and a command `/fm-watch-arm-omp`; a long-lived child process (the bash watcher) closes when something is actionable and the extension injects a wake as a follow-up user message via `pi.sendUserMessage(content, { deliverAs: "followUp" })`; hooks used: `session_start`, `before_agent_start`, `message_start`, blocking `session_stop` (guard returns 2 -> one forced continuation, bounded by `stop_hook_active`), and busy-state events `agent_start` / `agent_end` with `willContinue`; verified against "omp 18.1.11" per the extension's header comment — [fm-primary-omp-watch.ts](https://github.com/kunchenguid/firstmate/blob/main/.omp/extensions/fm-primary-omp-watch.ts), [OMP supervision protocol](https://github.com/kunchenguid/firstmate/blob/main/docs/supervision-protocols/omp.md) (C).
- Limits on omp: Pi's in-process "supervision branch" does not run on omp (every actionable wake goes to the main conversation unless a `config/supervision-host` process is configured); `pi.sendUserMessage` is synchronous in omp; omp emits no shutdown reason — [fm-primary-omp-watch.ts header](https://github.com/kunchenguid/firstmate/blob/main/.omp/extensions/fm-primary-omp-watch.ts), [OMP protocol](https://github.com/kunchenguid/firstmate/blob/main/docs/supervision-protocols/omp.md) (C).
- The design rationale from the first mate's own contract: the supervisor "reads projects but does not change them", never does work itself, escalates only decisions, and translates internal state into outcomes; workers never talk to the human ([AGENTS.md](https://github.com/kunchenguid/firstmate/blob/main/AGENTS.md), C).

### Inferences (my synthesis; not stated by the sources)
1. Option A (reuse): run firstmate under `omp` as the Supervisor; each OMP Lead = a crewmate/secondmate session (`fm-<id>` tmux window + treehouse worktree); Peers = OMP's own subagents inside each Lead, invisible to firstmate. Least new code, but inherits firstmate's opinions (git-worktree-per-task, PR-centric ship/scout tasks, nautical persona, very large AGENTS.md).
2. Option B (borrow the mechanisms): build a thinner Supervisor using the same primitives: task-id namespace; `state/<id>.status` append-only event log with keys and `corr` ids; a deterministic `crew-state`-style resolver that prefers OMP-native lifecycle events (`agent_start`/`agent_end`) over pane scraping and returns `unknown` rather than guessing; a zero-token watcher + OMP extension that wakes the Supervisor via a follow-up message; a durable inbox/doorbell for supervisor->lead steering; a digest command answering "status of task X" from disk; an "asked vs. dispatched" reconciliation.
3. To avoid session confusion in either option: make the Lead's identity a machine-readable file (id, cwd/worktree, session file, incarnation token) written at spawn; have every Lead tool/extension stamp its id into status lines; have the Supervisor resolve "task C" -> id -> records only via that registry, never via chat memory.
4. Keep the Supervisor's always-loaded instructions small (firstmate itself sets a 9,000-word ceiling and an outside reviewer criticizes a 108KB instruction file subject to compaction), keep state on disk, and let a script, not the LLM, classify worker state.
5. Keep depth flat (Supervisor -> Lead -> Peer only) and consider persistent domain Leads (secondmate-like) only when one Supervisor becomes the bottleneck — the same advice firstmate gives.

- No evidence about Peer-level (in-session subagent) supervision patterns from these videos.
