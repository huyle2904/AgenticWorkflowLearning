# Community and official tools for "one human -> one orchestrator -> many per-task agent sessions" (SLP-style), plus parallel-session managers

Research date: 2026-09-29. Star/fork/commit counts come from GitHub repo pages fetched with WebFetch on that date (GitHub rounds them; treat as approximate). Release dates come from raw files, Atom feeds or the repo page where stated. "OMP" = Oh My Pi (`omp`), "Pi" = badlogic/pi-mono coding agent. Everything under "Inferences" is my own reasoning, not a sourced fact.

Headline discovery for the OMP use case: at least seven third-party orchestrators/managers already list first-class `omp` support (AWS CAO, Gas Town, ntm, agent-deck, Herdr, Superset, Untrivial AO), and three more support Pi only (Overstory/Warren, Sculptor). Details in KQ5.

---

## KQ1. Which tools implement the exact pattern "human talks to ONE supervisor agent that dispatches to and monitors per-task sessions"? How, concretely?

### Takeaway
The closest matches are Gas Town / Gas City (Mayor), AWS CLI Agent Orchestrator (supervisor with `assign`/`handoff`/`send_message` MCP tools), agent-deck's "Conductor", Untrivial-ai Agent Orchestrator (per-project orchestrator agent + kanban), multi-agent-shogun (Shogun -> Karo -> Ashigaru), Tmux-Orchestrator (Orchestrator -> PM -> Engineer, the simplest original) and the now-archived Overstory (coordinator -> lead -> workers). Anthropic's own Agent Teams, Agent View, cross-session messaging and Projects are official but Claude-only. Most use tmux plus a durable store (beads, YAML, SQLite, JSON files) so the supervisor's answers come from state on disk rather than from chat memory.

### Cited Findings

#### 1. Gas Town (Steve Yegge) - most complete hierarchical system; has native `omp` and `pi` presets
- Repo now lives at `gastownhall/gastown` (README still references `steveyegge/gastown`); 18.2k stars, 1.7k forks, MIT, not archived, ~7,770 commits — [gastownhall/gastown](https://github.com/gastownhall/gastown), [steveyegge/gastown](https://github.com/steveyegge/gastown)
- Latest release in the Atom feed: v1.2.1 published 2026-06-06 (the feed returned a single entry; I could not confirm whether newer tags exist) — [releases.atom](https://github.com/steveyegge/gastown/releases.atom)
- Human interface is the Mayor: "The Mayor is a Claude Code instance with full context about your workspace, projects, and agents. Start here - just tell the Mayor what you want to accomplish." The Mayor creates convoys of beads and slings them to agents — [README](https://raw.githubusercontent.com/steveyegge/gastown/main/README.md)
- Roles: Mayor (town coordinator, persistent), Deacon (daemon beacon running patrol cycles), Dogs (Deacon's maintenance workers), Boot (a Dog that checks the Deacon every 5 minutes), Witness (per-rig, monitors polecats, nudges/recovers), Refinery (per-rig Bors-style bisecting merge queue), Polecats (workers: "persistent identity but ephemeral sessions", git worktrees), Crew (long-lived human workspaces) — [glossary](https://raw.githubusercontent.com/steveyegge/gastown/main/docs/glossary.md), [architecture](https://raw.githubusercontent.com/steveyegge/gastown/main/docs/design/architecture.md)
- Work model: beads (Git-backed issues stored in Dolt), convoys (bundles of beads that give the Mayor a progress view), hooks (a pinned bead per agent = its work queue), `gt sling <bead> <rig>` assigns; GUPP principle: "If there is work on your Hook, YOU MUST RUN IT." — [glossary](https://raw.githubusercontent.com/steveyegge/gastown/main/docs/glossary.md)
- Progress questions are answered from `gt convoy list/status`, `gt agents`, `gt feed` (TUI, `--problems` view for stuck agents), and the Mayor "summarizes results" — [README](https://raw.githubusercontent.com/steveyegge/gastown/main/README.md), [reference](https://raw.githubusercontent.com/steveyegge/gastown/main/docs/reference.md)
- README pitch table: "4-10 agents become chaotic" vs. "Scale comfortably to 20-30 agents" (a vendor claim, not independently verified) — [README](https://raw.githubusercontent.com/steveyegge/gastown/main/README.md)
- Built-in agent presets: `claude, gemini, codex, kiro, cursor, auggie, amp, opencode, copilot, pi, omp`; override per sling (`gt sling <bead> <rig> --agent cursor`) or for the Mayor (`gt mayor start --agent auggie`) — [README](https://raw.githubusercontent.com/steveyegge/gastown/main/README.md)
- `AgentOmp` preset: comment "Oh My Pi (OMP) — Pi fork with hook-based lifecycle. Inspired by github.com/ProbabilityEngineer/pi-mono gastown integration"; Command `omp`, Args `--hook .omp/hooks/gastown-hook.ts`, SessionIDEnv `OMP_SESSION_ID`, NonInteractive PromptFlag `--prompt`, SupportsForkSession false. `AgentPi`: command `pi`, Args `-e .pi/extensions/gastown-hooks.js`, `PI_SESSION_ID`, ReadyDelayMs 8000 because "Pi's Node.js TUI takes several seconds to initialize before it can receive tmux input" — [agents.go](https://raw.githubusercontent.com/steveyegge/gastown/main/internal/config/agents.go)
- The OMP hook file (136 lines) maps OMP events to Gas Town: `session_start` -> `gt prime --hook`; `before_agent_start` -> inject prime context and `gt mail check --inject` (throttled to once per 30 s; skipped for witness/refinery/deacon/boot roles); `session_compact` -> re-prime; `tool_call` -> `gt tap guard pr-workflow` on `git push`/`gh pr create`/`git checkout -b` (can `block`); `session_shutdown` -> `gt costs record`. It reads `GT_ROLE` from the environment — [gastown-hook.ts](https://raw.githubusercontent.com/steveyegge/gastown/main/internal/hooks/templates/omp/gastown-hook.ts)
- Integration tiers in the provider guide: Tier 0 "Any CLI that runs in a terminal works in Gas Town with zero changes" (tmux `send-keys`, `capture-pane`, liveness via `pane_current_command`; "timing-sensitive and has no delivery confirmation"); Tier 1 preset JSON (~15 minutes); Tier 2 hooks; Tier 3 deep (non-interactive mode, session fork, wrapper) — [agent-provider-integration.md](https://raw.githubusercontent.com/steveyegge/gastown/main/docs/agent-provider-integration.md)
- Design principle in that guide: "Gas Town orchestrates agents through tmux and environment variables. It does not import agent libraries... Integration is configuration, not compilation." — [agent-provider-integration.md](https://raw.githubusercontent.com/steveyegge/gastown/main/docs/agent-provider-integration.md)
- Requires tmux 3.0+, Dolt, `bd`; Docker option exists; native Windows source builds need ICU/MSYS2 — [README](https://raw.githubusercontent.com/steveyegge/gastown/main/README.md)
- Yegge's launch essay "Welcome to Gas Town" (Medium, 2026-01-14 per search listing) is followed by "Gas Town Emergency User Manual" 12 days later and by third-party critiques — [Medium essay](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04), [Emergency manual](https://steve-yegge.medium.com/gas-town-emergency-user-manual-cf0e4556d74b), [search listing with critiques](https://www.todayintabs.com/p/all-gas-town-no-brakes-town). (I could not fetch these pages; only the search listing.)

#### 3. AWS CLI Agent Orchestrator (CAO, awslabs) - supervisor/worker over tmux + MCP; first-class OMP provider
- 1.4k stars, 279 forks, Apache-2.0, ~442 commits, not archived — [repo](https://github.com/awslabs/cli-agent-orchestrator)
- "CAO runs a local `cao-server`, starts provider CLIs in isolated terminal sessions, and gives a supervisor tools for coordinating workers. The agents remain full CLI processes with their native authentication and capabilities." — [README](https://raw.githubusercontent.com/awslabs/cli-agent-orchestrator/main/README.md)
- Supported providers: Kiro CLI, Claude Code, Codex CLI, Antigravity CLI, Hermes, Kimi CLI, MiniMax Code, GitHub Copilot CLI, OpenCode CLI, Oh My Pi (OMP) CLI, Cursor CLI, Grok Build CLI — [README](https://raw.githubusercontent.com/awslabs/cli-agent-orchestrator/main/README.md)
- In-session MCP tools for the supervisor: `assign(agent_profile, message)` (async, returns immediately), `handoff(agent_profile, message)` (blocks until worker finishes), `send_message(message, receiver_id=None)`. "Your own terminal ID is available in the `CAO_TERMINAL_ID` environment variable. CAO appends it to assigned task messages and records it on worker terminals automatically" — callback routing is automatic — [supervisor-protocols skill](https://raw.githubusercontent.com/awslabs/cli-agent-orchestrator/main/skills/cao-supervisor-protocols/SKILL.md)
- State in SQLite (sessions, terminals, inbox); workers in separate tmux windows identified by terminal IDs — [CODEBASE.md](https://raw.githubusercontent.com/awslabs/cli-agent-orchestrator/main/CODEBASE.md), [README summary via WebFetch](https://github.com/awslabs/cli-agent-orchestrator)
- Inbox delivery: messages are queued in the DB and pasted into the target terminal (bracketed paste) only when the terminal status is IDLE or COMPLETED; a 5 s `PollingObserver` watches terminal log files for idle patterns; an opt-in "eager delivery" exists only for providers that buffer input (currently Claude Code) — [inbox-delivery.md](https://raw.githubusercontent.com/awslabs/cli-agent-orchestrator/main/docs/inbox-delivery.md)
- Human/operator surfaces: browser Web UI (port 9889), `cao session` CLI, `cao-ops-mcp` (external MCP-capable agent can manage the fleet: a "supervisor of supervisors" entry point), `cao fleet` for remote pods, event plugins for notifications — [control-planes.md](https://raw.githubusercontent.com/awslabs/cli-agent-orchestrator/main/docs/control-planes.md)
- OMP provider doc: works with OMP 17.2.10; starts the user's normal interactive OMP and adds CAO role context via `--append-system-prompt` (per-terminal file `$CAO_HOME_DIR/tmp/omp/<terminal-id>/context.md`, never `--system-prompt`) and profile MCP servers via a generated `--extension <dir>` containing `.mcp.json`; `CAO_TERMINAL_ID` is injected into stdio MCP servers; status detection from OMP TUI markers (`Working… ⟨esc⟩` = PROCESSING, `Allow tool: <name>` = WAITING_USER_ANSWER, error frame = ERROR, ready frame + `in: … out: … t: … tok/s` status line = IDLE/COMPLETED); tool restrictions are "advisory" for OMP; a documented supervisor + worker example runs on OMP — [omp-cli.md](https://raw.githubusercontent.com/awslabs/cli-agent-orchestrator/main/docs/omp-cli.md)

#### 4. agent-deck "Conductor" (asheshgoplani/agent-deck) - conductor session + parent/child sessions + heartbeat + Telegram/Slack
- 970 stars (WebFetch) / ~4,083 commits, MIT, latest release v1.16.5+, not archived — [repo](https://github.com/asheshgoplani/agent-deck)
- "A conductor is one persistent AI session whose job is to supervise all your other agent-deck sessions... you send instructions to the foreman, the foreman assigns them to workers (child sessions)." Implemented as a `claude` (or `codex`, `hermes`, `pi`) process in a named tmux session, registered in agent-deck's registry with `is_conductor: true` — [conductor README](https://raw.githubusercontent.com/asheshgoplani/agent-deck/main/docs/conductor/README.md)
- Per-conductor state dir: `CLAUDE.md` (startup checklist), `POLICY.md` (auto-respond vs escalate rules), `LEARNINGS.md`, `state.json` ("working memory across Claude compactions": summaries of each child session, goal, handoff notes), `task-log.md` (append-only) — [conductor README](https://raw.githubusercontent.com/asheshgoplani/agent-deck/main/docs/conductor/README.md)
- The conductor drives children with `agent-deck session send <name> "msg"` and `agent-deck session output <name>` (ANSI-stripped, capped ~25k tokens); launches children with `agent-deck launch . -t "child-task" -c claude -m "Do task"`, auto-parented when `AGENT_DECK_SESSION_ID` is set; `agent-deck session children` lists a conductor's fleet; guidance: "Don't encode dispatch relationships in a group name... that's what parent linkage is for." — [README](https://raw.githubusercontent.com/asheshgoplani/agent-deck/main/README.md)
- Push + pull monitoring: `agent-deck notify-daemon` watches status transitions and nudges the parent when a child moves `running -> waiting|error|idle` (can be disabled per session); 15-minute heartbeat "as a secondary safety net"; conductor replies containing `NEED:` are forwarded to Telegram/Slack; Telegram/Slack messages route with a `name: message` prefix, one bot per conductor — [README](https://raw.githubusercontent.com/asheshgoplani/agent-deck/main/README.md)
- Harness matrix: Claude Code full; Codex, Gemini, OpenCode; `pi` "Status detection (hook-driven), organization, launch, resume, fork" (via `agent-deck pi-hooks install`, an extension in Pi's extension dir; "Without the extension a pi session's status is read from the pane, which is slower and occasionally wrong"); `Oh My Pi (omp)`: "Status detection, organization, launch, restart, resume, fork, project skills"; custom tools via `[tools.*]` config — [README](https://raw.githubusercontent.com/asheshgoplani/agent-deck/main/README.md)
- Known limits: no native Windows; the conductor's `--agent` values listed are claude|codex|hermes|pi (omp not listed for conductors); permission prompts can stall an automated conductor (needs dangerous mode) — [conductor README](https://raw.githubusercontent.com/asheshgoplani/agent-deck/main/docs/conductor/README.md), [README](https://raw.githubusercontent.com/asheshgoplani/agent-deck/main/README.md)

#### 9. Claude Code (official) - Agent Teams, Agent View, cross-session messaging, Projects
- Anthropic's own comparison lists five approaches: subagents, agent view, agent teams, dynamic workflows, projects. "In every approach the workers are Claude sessions. To involve a different tool, expose it to Claude as an MCP server." — [Run agents in parallel](https://code.claude.com/docs/en/agents)
- Agent Teams (experimental, off by default, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`): team lead + teammates + shared task list + mailbox; mailbox is a JSON file `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`; team config `~/.claude/teams/{team}/config.json` stores session IDs and tmux pane IDs; task list in `~/.claude/tasks/{team-name}/`; task claiming uses file locking; hooks `TeammateIdle`, `TaskCreated`, `TaskCompleted`; idle teammates auto-notify the lead with their final answer ("The lead doesn't need to poll"); you can message any teammate directly (Enter on panel row, or click tmux pane) — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Agent Teams limits: no session resumption with in-process teammates; task status can lag; one team per session; no nested teams; lead is fixed; "Letting a team run unattended for too long increases the risk of wasted effort"; "Two teammates editing the same file leads to overwrites" (no worktree isolation for teammates) — [Agent teams](https://code.claude.com/docs/en/agent-teams), [agents overview](https://code.claude.com/docs/en/agents)
- Agent View (research preview, v2.1.140+): `claude agents` shows every background session with state (Working / Needs input / Idle / Completed / Failed / Stopped); `claude --bg "task"` dispatches; a supervisor process hosts sessions; registry at `~/.claude/daemon/roster.json`, per-session `~/.claude/jobs/<id>/state.json`, `claude agents --json`, `claude logs <id>`, `claude attach <id>`, `claude respawn`; each background session moves into its own git worktree under `.claude/worktrees/` before editing; local only; "10 sessions is about 10x quota" — [Agent view](https://code.claude.com/docs/en/agent-view)
- Cross-session messaging (v2.1.224+): Claude discovers sessions with `ListAgents` and sends with `SendMessage`; sessions answer to a name set by `/rename` or `--name`, duplicates get a short ID; delivered over a per-session Unix socket (`CLAUDE_CODE_MESSAGING_SOCKET`, token `CLAUDE_CODE_MESSAGING_TOKEN`) never through Anthropic servers on the same machine; `notify_when_idle` subscription (12 h expiry) gives a one-shot notice when another session goes idle; plain text only; inbound controls `crossSessionInbound` accept/hold/refuse; a message can't approve permissions or change config; loop throttling — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Projects (public beta on Pro/Max): one coordinating conversation starts "threads" (mostly cloud sessions), each on its own branch/PR; Overview pane groups threads Ready for review / Waiting on you / Working / Landing / Idle / Resolved; "It sees what threads report back, not every step they take."; cannot adopt a session you started yourself; not available in the terminal CLI or via Bedrock/Vertex/Foundry — [Projects](https://code.claude.com/docs/en/claude-projects)

### Inferences
- Nobody implements a literal three-level "Supervisor - Lead - Peer" where the Lead is a full session that itself owns subagents. What exists: supervisor -> worker session (Gas Town, CAO, agent-deck, AO, shogun), or supervisor -> lead -> workers where all are separate processes (Overstory). In every case the per-task session is a black box to the supervisor. For SLP that is convenient: the OMP session can keep its own Task/subagent Peers internally and the external Supervisor only sees the Lead. (ntm even treats an OMP ` Subagents` panel as "working" — see KQ5.)
- The recurring recipe is: (1) durable task record with a stable ID, (2) one worktree/branch per task, (3) supervisor is a normal agent session with a role prompt plus a CLI/MCP toolset, (4) messages travel through a store (YAML/SQLite/JSON/beads) with only a tmux "nudge" to wake the receiver, (5) a wake-up path from worker to supervisor (hook, notify daemon, idle notification), (6) human reads a board/dashboard file or asks the supervisor.
- AO issues #4951 and #5597 show two concrete failure modes for a naive supervisor: it never wakes up when nobody types, and it cannot read what workers produced. Any SLP design needs an explicit wake-up channel and an explicit "read worker output/state" tool.

- No independent verification of Gas Town's "20-30 agents" scaling claim or of ruflo's benchmark claims.

## KQ3. Communication and coordination layers (mail, task boards, shared stores)

### Takeaway
Three families: (a) message stores with identities and threads (MCP Agent Mail, Gas Town mail, CAO inbox, Overstory SQLite mail, Claude Code mailboxes, shogun YAML), (b) task/issue graphs with stable IDs and atomic claim (Beads, Backlog.md, Claude task list, ntm's Beads triage), (c) thin tmux/PTY "nudge" transports that only wake the receiver. Every robust design puts the payload in the store and uses the terminal only to ping.

### Cited Findings
- **MCP Agent Mail (Dicklesworthstone)**: 2.2k stars, 228 forks, ~869 commits, active. "A mail-like coordination layer for coding agents, exposed as an HTTP-only FastMCP server... memorable identities, an inbox/outbox, searchable message history, and voluntary file reservation 'leases'"; backed by Git (auditable artifacts) and SQLite (index). - A task ID minted by the supervisor and reused as branch name, worktree name, message thread ID and progress-record key is the cheapest anti-confusion mechanism seen (explicitly recommended in MCP Agent Mail's Beads pairing and implicit in Gas Town's bead IDs).
- None of the surveyed transports gives strict delivery confirmation over a TUI; the reliable ones (CAO, Gas Town, shogun) queue in a store and deliver only when the receiver is idle or via a hook that injects mail at the next prompt.

## KQ4. How do they identify sessions, avoid mixing them up, and report status (push vs pull, heartbeats, hooks)?

### Takeaway
Identity is created by the orchestrator at spawn time and propagated through environment variables and names (GT_ROLE/BD_ACTOR, CAO_TERMINAL_ID, AGENT_DECK_SESSION_ID, tmux pane titles, per-agent YAML files). Status comes from three sources: agent hooks/extensions (most reliable, push), TUI/pane parsing (fallback, fragile), and git/PR/CI facts. Wake-up of the supervisor needs an explicit push path plus a heartbeat safety net; when it is missing (AO #4951) the supervisor silently stalls.

### Inferences
- The strongest "never confuse sessions" pattern is a chain of the same ID across four layers: task/bead ID -> branch/worktree name -> session identity env var (set by the orchestrator, not chosen by the agent) -> message thread/mail subject. Gas Town, CAO and MCP Agent Mail each implement two or three of these.
- Status accuracy improves when the source of truth is not the agent's own claim: AO derives the board from PR/CI/review facts, Gas Town from beads/convoy state, Claude Agent View from `state.json`. Pane scraping is the fallback everywhere (Gas Town Tier 0, agent-deck without extension, CAO, ntm) and its own docs call it slower or occasionally wrong.
- For "what is the progress of task C?", the supervisor needs a read path that combines (a) the durable task record, (b) the session's mechanical status (idle/working/blocked + last event time), (c) git facts on that task's branch, and (d) an on-demand "ask the lead for a summary" message. No single surveyed tool documents all four in one command; Gas Town's `convoy status` + `peek`, agent-deck's `session output` + `state.json`, and Overstory's `ov status` + typed mail come closest.

### Gaps

## KQ5. Which are harness-agnostic enough to drive OMP, what would it take, and which design ideas transfer? (comparison table)

### Takeaway
Several orchestrators already support `omp` as a first-class harness, so no OMP-specific work is needed to try the pattern: AWS CAO (cleanest supervisor/worker model with MCP tools and OMP-tested TUI markers), Gas Town (most complete, heaviest; ships OMP hooks), agent-deck (conductor + OMP status/resume/fork; conductor on OMP unverified), ntm (deepest OMP TUI knowledge, human-driven with a coordinator), Herdr (OMP lifecycle events; substrate for other tools) and Superset (GUI). Anything else works at "Tier 0" if it is a terminal program. All of them drive OMP through tmux/TUI or hooks/extensions; none of the docs I read mention OMP's RPC or SDK.

### Inferences
- Fastest way to try SLP with OMP today, without writing code: (1) CAO with `--provider omp` for a supervisor + workers model, or (2) agent-deck conductor + OMP sessions (check whether the conductor itself can be `omp`; README lists claude|codex|hermes|pi), or (3) Gas Town with `gt mayor` and `omp` polecats if the heavy Dolt/beads stack is acceptable. All three add orchestration over tmux and rely on TUI parsing plus hooks, not OMP RPC.
- What a custom Supervisor for `omp` would need, by analogy with the adapters above: a launch template (`omp --hook/--extension`, `--append-system-prompt` for role text, `--resume <id>` for restarts), an orchestrator-set identity env var per session, a hook/extension that injects mail/context at `before_agent_start` and after `session_compact` and reports idle/working/blocked events (Gas Town's 136-line hook and Herdr's extension are ready-made templates), a status fallback that parses the OMP composer (ntm and CAO have documented marker lists: `Working…`, `Allow tool:`, error frame, `Steering · N`, ` Subagents`), and Esc-to-interrupt semantics.
- Worth copying (ranked by leverage for a single-human, N-session setup):
  1. Supervisor is a normal long-lived session with a role prompt plus a small CLI/MCP toolset (`send`, `output`, `list`, `spawn`) — agent-deck conductor, CAO supervisor, Overstory coordinator.
  2. Durable state owned by the supervisor outside its context window: `state.json` + `task-log.md` + `POLICY.md` + `LEARNINGS.md` (agent-deck) or beads/convoys (Gas Town); answer "progress of task C" from this record plus a fresh probe of the session.
  3. Orchestrator-assigned identity propagated by env var and included in every message (CAO auto-appends the caller terminal ID; agent-deck auto-parents by `AGENT_DECK_SESSION_ID`).
  4. Message payload in a store, tmux only for a short nudge; deliver only when idle or at next prompt via hook (shogun, CAO, Gas Town).
  5. Two-way wake-up: worker->supervisor push on transitions (agent-deck notify-daemon, Claude `notify_when_idle`, CAO callbacks) plus a heartbeat safety net (agent-deck 15 min); avoid the AO #4951 failure.
  6. Read-only supervisor and single-writer dashboard (Overstory read-only roles, shogun's Karo as sole writer) so the supervisor cannot silently edit worker code.
  7. One worktree/branch per task and hooks that guard risky git ops (Gas Town `gt tap guard`, Overstory guards).
  8. Escalation grammar and human interface on a channel the human already uses (agent-deck `NEED:` + Telegram/Slack `name: message` routing; shogun ntfy; Claude Projects "Waiting on you" group).
  9. Capacity governor and concurrency caps (Gas Town `scheduler.max_polecats`, ntm `omp_max_concurrent`) to avoid rate-limit storms.
  10. Tiered watchdog: mechanical liveness first, AI triage only on failure (Overstory Tier 0/1/2, Gas Town Witness/Deacon/Boot).
- Risks to plan for: vendor claims of scaling (Gas Town 20-30 agents) are unverified; Overstory's author warns compounding errors and cost amplification are "the normal case"; Anthropic warns that "Letting a team run unattended for too long increases the risk of wasted effort"; many projects in this space were wound down in 2026, so keep the integration layer thin.
