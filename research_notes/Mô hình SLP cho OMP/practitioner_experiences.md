## 1. How do practitioners describe the "I am the bottleneck / constant context-switching" problem with many parallel agents, and what do they do about it?

### Takeaway
Practitioners converge on the same diagnosis: agents parallelize *generation*, but review, decision-making and holding N task contexts in your head stay single-threaded, so the sustainable number of *foreground* sessions is small (about 2-5; a few people report 5-8 with heavy tooling). The mitigations that keep recurring are: a single conversational front-end that fans out to workers (Gas Town's Mayor, Claude Code "Projects", claude-team), a board/inbox that shows "needs you / working / ready for review", push notifications, back-loaded batch review with proof-of-work and automated verification, and simply running fewer things at once. A vocal minority (Ronacher, Zechner, Tuddenham) argues that the whole direction is over-hyped and that discipline/slowing down beats more parallelism.

### Cited Findings

**How the problem is described (diagnosis)**
- Simon Willison (5 Oct 2025): he can only focus on reviewing and landing *one significant change at a time*; the parallel tasks that work best add little cognitive load, e.g. research/PoC tasks that do not modify code you intend to keep. [S] — [Willison, "Embracing the parallel coding agent lifestyle"](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- Willison, as quoted in a June 2026 newsletter: he can fire four agents in parallel but "by 11am" he is wiped out for the day. [S, second-hand] — [Claude Code for Non-Coders, "Your Agents Can Run Parallel. You Can't." (18 Jun 2026)](https://claudecodefornoncoders.substack.com/p/your-agents-can-run-parallel-you); see also his tag page [simonwillison.net/tags/agentic-engineering](https://simonwillison.net/tags/agentic-engineering/)
- Addy Osmani, "Your parallel Agent limit": cognitive bandwidth does not parallelize — the agent generates but *you* still evaluate, decide, trust and integrate, all single-threaded; start with two agents, add more, and by noon "you're not reviewing anything carefully anymore, you're just accepting output"; the limit depends on task complexity, spec quality and session length. [S] — [Osmani](https://addyosmani.com/blog/cognitive-parallel-agents/)
- Pragmatic Engineer (2025): "the only people heard using parallel agents successfully are senior+ engineers"; Armin Ronacher said he kicks off parallel agents less than he used to: "it's only so much my mind can review!" [S] — [Pragmatic Engineer](https://blog.pragmaticengineer.com/new-trend-programming-by-kicking-off-parallel-ai-agents/)
- Armin Ronacher, "Agent Psychosis: Are We Going Insane?" (18 Jan 2026): "when I watch someone at 3am, running their tenth parallel agent session, telling me they've never been more productive — in that moment I don't see productivity"; agents are "amazing" but also "massive slop machines if you turn off your brain". [S] — [Ronacher](https://lucumr.pocoo.org/2026/1/18/agent-psychosis/)
- Mario Zechner, "Thoughts on slowing the fuck down" (25 Mar 2026): agents compound small errors at a rate humans never could because a human is a natural bottleneck; recommendation is to limit daily agent output to what you can actually review and keep writing architecture by hand. A secondary summary adds that one agent already produces ~10x the code a human can competently review (~1,500 lines/day) — that specific figure is the summarizer's, not verified. [S] — [Zechner](https://mariozechner.at/posts/2026-03-25-thoughts-on-slowing-the-fuck-down/), [Willison's link post](https://simonwillison.net/2026/Mar/25/thoughts-on-slowing-the-fuck-down/)
- Axios (4 Apr 2026): power users say agents "operate like slot machines"; peak productivity is described as running as many agents as possible in parallel, which "requires near-constant context switching, which humans aren't great at". [S] — [Axios](https://www.axios.com/2026/04/04/ai-agents-burnout-addiction-claude-code-openclaw)
- Steve Yegge on Gas Town: it "churns through implementation plans so quickly that you have to do a LOT of design and planning to keep the engine fed"; Maggie Appleton's takeaway is that design/planning (not coding) becomes the bottleneck once agents write the code. [S: secondary summaries; the OpenAI page itself was blocked] — [MindStudio summary of Symphony](https://www.mindstudio.ai/blog/500-percent-more-merged-prs-4-lessons-openai-symphony-agentic-coding), [OpenAI announcement](https://openai.com/index/open-source-codex-orchestration-symphony/)

[S] — [HN 46368739](https://news.ycombinator.com/item?id=46368739)

- Contrarian: Josh Tuddenham ("Stop Multitasking. **Sustainable number of parallel sessions (WIP limits) as reported**
- Kilo Code write-up: "2-4 agents in the foreground, a handful in the background, and a strong verification loop on top"; frames it as the bottleneck moving from writing to verifying code. **Vendor/blog anecdote.** [S] — [Kilo blog](https://blog.kilo.ai/p/how-7-kilo-code-engineers-run-up)
- Steinberger ("Just talk to it", Oct 2025): 3-8 parallel Codex instances in a 3x3 terminal grid, mostly in the *same folder* (no worktrees), short prompts, ~20% of time spent on agent-run refactoring. **Anecdote.** [S] — [steipete.me](https://steipete.me/posts/just-talk-to-it)
- Boris Cherny (Claude Code): 5 numbered terminal tabs + 5-10 sessions on claude.ai/code; "Spin up 3-5 git worktrees at once ... the single biggest productivity unlock, and the top tip from the team". **Anecdote (creator of the tool).** [S] — [Cherny on X](https://x.com/bcherny/status/2017742743125299476)
- Anthropic's own agent-teams docs: "Start with 3-5 teammates for most workflows"; 5-6 tasks per teammate. [F] — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- Generic sizing guides (low rigor, SEO-style): "2-4 is the sweet spot"; "the trouble starts at the fourth agent - you no longer know which one is waiting for review, which finished, which crashed"; beyond ~8 review dominates even with a board. [S] — [AgentsRoom guide](https://agentsroom.dev/blog/run-coding-agents-in-parallel)
- Measured-ish field report (Kilo): 7 engineers running "up to 20" agents, but only 2-4 in the foreground. **Anecdote.** [S] — [Kilo blog](https://blog.kilo.ai/p/how-7-kilo-code-engineers-run-up)

**What people do about it**
1. *Single conversational front-end (supervisor)* — see Section 2. DoltHub's Gas Town write-up: "dealing with the Mayor was the right abstraction", the author never left the Mayor's Claude Code session and only used tmux to scroll. [S] — [DoltHub, A Week in Gas Town (24 Mar 2026)](https://www.dolthub.com/blog/2026-03-24-a-week-in-gas-town/)
2. *Board / kanban / inbox that tells you what needs you.* Claude Code's `claude agents` "agent view" groups sessions as Needs input / Working / Idle / Completed / Failed, puts "Needs input" and "Ready for review" on top, shows a one-line LLM-generated summary per row (Haiku-class model, refreshed at most every 15 s), and lets you peek and reply inline; the tab title shows "2 awaiting input". [F] — [Claude Code docs: agent view](https://code.claude.com/docs/en/agent-view). Pi-agent-hub uses NEEDS YOU / HEALTH / ACTIVE / QUIET and explicitly warns "Waiting alone does not mean an agent needs an answer" — explicit requests need an extension that reports them. [F] — [pi-agent-hub](https://github.com/masta-g3/pi-agent-hub). pi-command-centre keeps a fixed <=3-line status light ("needs-you 1 - in-flight 2 - queue 0") and escalates to Needs You "only for merge approval, scope questions, or genuine blockers". [F] — [pi-command-centre](https://github.com/ananth99/pi-command-centre). Vibe Kanban (a kanban front-end for agents) was reported as sunsetting after its maker bloop shut down on 10 Apr 2026 and continuing as community-maintained OSS. [S] — [Nimbalyst comparison](https://nimbalyst.com/compare/nimbalyst-vs-conductor-vs-vibe-kanban/)
3. *Notifications.* Cherny uses iTerm2 system notifications when a tab finishes or needs input [S] ([X](https://x.com/bcherny/status/2017742743125299476)); DIY hooks push Allow/Deny prompts to the phone via ntfy/Tailscale/Pushover [S] ([claude-ntfy-hook](https://github.com/nickknissen/claude-ntfy-hook), [felipeelias.github.io](https://felipeelias.github.io/2026/02/25/claude-code-notifications.html)); Claude Code "Projects" gives desktop notifications when a thread errors or needs input and a "Waiting on you" group [F] ([docs](https://code.claude.com/docs/en/claude-projects)).
4. *Async / back-loaded review.* Osmani's "conductor vs orchestrator" framing: for an orchestrator, effort is front-loaded (spec/context) and back-loaded (review), "not much is needed in the middle". [S] — [O'Reilly Radar / Osmani](https://www.oreilly.com/radar/conductors-to-orchestrators-the-future-of-agentic-coding/). Symphony makes agents attach "proof of work" (CI status, PR review feedback, complexity analysis, walkthrough video) so the human accepts/rejects instead of watching. [F] — [openai/symphony](https://github.com/openai/symphony). Steinberger: "queue up continue messages if you wanna go away and just see it done". [S] — [steipete.me](https://steipete.me/posts/just-talk-to-it)
5. *Cloud/mobile so work continues away from the desk.* Claude Code "Projects" (public beta, Pro/Max): one ongoing conversation that starts cloud "threads", shows which finished / which PRs are ready / which are "waiting on you", available in the Claude mobile app; a walk-away-and-come-back workflow. [F] — [Claude Code docs: Projects](https://code.claude.com/docs/en/claude-projects). Remote Control lets you continue a local session from phone/browser with push for permission prompts. [S] — [builder.io](https://www.builder.io/blog/claude-code-mobile-phone)
6. *Voice.* I found only tool-marketing/how-to content (Wispr Flow, Superwhisper dictation for prompts; "voice is most valuable for the initial high-level task description, once sub-tasks run it's y/n approvals") and one Show HN title about voice-controlling local/remote agents via tmux; no substantive practitioner report about voice as a *bottleneck fix for many sessions*. [S] — [Developers Digest](https://www.developersdigest.tech/blog/wispr-flow-voice-prompts-coding-agents), [HN 46968740](https://news.ycombinator.com/item?id=46968740)
7. *Fewer sessions / slow down.* Zechner, Ronacher, Tuddenham above; Kilo's "2-4 foreground".

### Inferences
- The strongest common denominator is that the human must be able to answer three questions per session without opening it: *what is it doing, does it need me, is its output verified.* Every successful UI (agent view, pi-agent-hub, pi-command-centre, Projects overview) is built around exactly those three states — which is the information an SLP Supervisor must maintain accurately.
- A supervisor reduces *routing* cost (which session, what did it say) but does not remove *judgment* cost (review/design). Yegge/Appleton, Osmani and Symphony all say the scarce resource remains human review and specification; therefore the Supervisor's value is mostly in (a) status aggregation, (b) queueing decisions/approvals for batch handling, (c) enforcing verification before "done".
- Numbers like "3-5" are consistent across independent sources, but all are anecdotes/self-reports; none is a controlled measurement.

### Gaps
- No Reddit evidence (blocked). Reddit is where many "I run N Claude sessions" confessions live; expect the same 3-5 / burnout / rate-limit themes but this could not be checked.
- No controlled study comparing productivity at 1 vs 3 vs 5 sessions; all limits are self-reports.
- The "CMU 80% switching overhead" figure is unsourced.

## 2. What do people report about actually using an orchestrator/supervisor agent that talks to other sessions (Gas Town, Claude Code Agent Teams, tmux orchestrators, custom scripts, Pi/OMP setups, Codex)?

### Takeaway
Success stories cluster around (1) *independent, well-specified tasks with a strong automatic oracle* (tests/CI), (2) supervisors that only route and verify and never implement, and (3) durable external state (files/issue tracker) rather than chat memory. Failure reports cluster around fabricated/stale status, lost or misrouted messages, orphaned processes, cost blow-ups (5-10x tokens), and supervisors that cannot distinguish "working", "stuck" and "rate-limited". Several practitioners argue a flat peer/lock-file design or no orchestrator at all beats a hierarchy for some work; others say a hierarchy with a verify-before-believe supervisor is what makes long-horizon work reliable.

### Cited Findings

**Gas Town (Yegge; Mayor -> Polecats/Refinery/Witness/Deacon, "Beads" work items)**
- Design: you talk to the Mayor, "who never writes code", creates work and assigns it to workers; Witness/Deacon/"Boot the Dog" nudge workers; a single Refinery lands merges; work state persists in git-backed Beads/hooks so a stuck or dead worker can be replaced ("polecats are disposable"), and a "seance" can resume a predecessor's session. [S] — [Yegge](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04), [Appleton](https://maggieappleton.com/gastown)
- DoltHub, "A Day in Gas Town" (15 Jan 2026): 60 minutes cost about $100 in Claude tokens, "about 10X the cost of a normal Claude Code session per unit time"; the first PR was merged autonomously *despite failing integration tests*, and the author had to shut Gas Town down and have a colleague reset and force-push. **Measured (self-reported) + anecdote.** [S] — [DoltHub](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/)
- DoltHub, "A Week in Gas Town" (24 Mar 2026): the Mayor was "the right abstraction"; polecats merged directly to master and the author fixed that by talking to the Mayor; with minimal prompting Gas Town committed for ~4 hours until all 87,000 SQLite acceptance tests passed; whole run cost about $3,000; newer Claude sometimes used its own tasks/subagents instead of Beads/Polecats unless told explicitly. **Measured (self-reported).** [S] — [DoltHub](https://www.dolthub.com/blog/2026-03-24-a-week-in-gas-town/)
- DoltHub, "Two Weeks in Gas Town" (16 Apr 2026): ~$6,000 in Claude API calls, built "DumboDB", a MongoDB clone on Dolt; author's "new skill set": how to verify agents' work reliably while "reading a vanishingly small percentage of the code". [S] — [DoltHub](https://www.dolthub.com/blog/2026-04-16-two-weeks-in-gastown/)
- Mark Atwood's review: the novelty phase did not pay off once the project moved past API parity into Dolt-specific features with no MongoDB analogue. [S] — [Review Commit](https://reviewcommit.substack.com/p/gas-town-a-review)
- Tenzin Wangdhen, "The Good, The Bad, The Ugly": submitted 7 beads before dinner and returned to 6 merged PRs — but ended with "three mayors, 141 orphaned Claude Code processes"; works when tasks are independent with clear specs, "falls apart" when work is ambiguous or heavily human-in-the-loop. **Anecdote.** [S] — [Tenzin's blog](https://tenzinwangdhen.com/posts/gastown-good-bad-ugly/)
- HN reactions (Jan 2026 onward): cost ("cash guzzler"; "the better comp is how much gastown would cost if it weren't subsidized"), auditability (an FDA-audit comment), some read it as speculative fiction about cheap inference. Only titles/summaries seen. [S] — [HN 46673683](https://news.ycombinator.com/item?id=46673683), [HN 46784492](https://news.ycombinator.com/item?id=46784492), [HN 46458936](https://news.ycombinator.com/item?id=46458936)
- Operational bugs still being filed in Sep 2026 show the supervisor-layer failure modes concretely: "Idle reaper kills a freshly-slung polecat 1s after dispatch" (#4890, 29 Sep 2026), a stale "PENDING_MR" check-recovery status that makes "every polecat unreusable" (#4889), "Usage/session-limit block is indistinguishable from a hang" so healthy workers get killed (#4887), orphaned patrol wisps (#4870). [F] — [gastownhall/gastown issues](https://github.com/gastownhall/gastown/issues)

**Claude Code Agent Teams (lead + teammates; experimental, Feb 2026)**
- Official limitations: "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks"; the lead "can stop early too, deciding the team is finished before all tasks are actually complete"; teammates "may stop after encountering errors instead of recovering"; no session resumption of in-process teammates (lead may message teammates that no longer exist); one team per session; no nested teams; lead is fixed; agent teams do *not* isolate teammates in worktrees so you must partition files; orphaned tmux sessions after exit; "Letting a team run unattended for too long increases the risk of wasted effort". [F] — [agent-teams docs](https://code.claude.com/docs/en/agent-teams)
- Cost: docs say teams use "significantly more tokens"; costs page states "approximately 7x more tokens than standard sessions when teammates run in plan mode"; each active teammate keeps consuming until it exits. [F] — [costs docs](https://code.claude.com/docs/en/costs)
- Open GitHub bugs (Sep 2026) from real use: teammate message/idle_notification delivered to the lead up to 4x with the same timestamp (#92244); lead session exits cleanly seconds after a teammate approves shutdown (#96226); `git commit --amend` in a shared working tree "can silently rewrite a concurrent teammate's commit" (#91513); read-only teammates self-claim tasks they cannot do (#93668); "Subagent silently deadlocks: ... no stall detection wakes an idle multi-agent pipeline" (#92410); teammates inherit `--settings` but not `--channels` and steal a plugin's single poller so messages are dropped (#97102). [F] — [issue search](https://github.com/anthropics/claude-code/issues?q=is%3Aissue%20agent%20teams%20teammate%20lead)
- Proposal #91541 (2 Sep 2026) lists failure modes of agent messaging in production: "notify-without-persist race" (message reported sent that was never delivered), "tag-based routing drift" (`->` vs `→` delimiters caused multi-hour silent gaps), ambiguous cross-machine timestamps (clock drift reordered a conversation), implicit repo-root inference; proposes store-before-notify, durable append-only transcript. **Anecdote from one heavy user.** [F] — [issue #91541](https://github.com/anthropics/claude-code/issues/91541)
- Issue #25818 (14 Feb 2026): when a Task subagent fails the orchestrator gets almost no diagnostics and either "blind resubmission" (re-dispatching the same task, burning context) or "confident fabrication" ("The agent encountered an issue, but based on what I know..." then presents hallucinated results); closed as not planned. [F] — [issue #25818](https://github.com/anthropics/claude-code/issues/25818)
- Positive framing from bloggers: "feels like managing junior engineers: you write tasks, check their work, tell them when they're going down a rabbit hole"; best for parallel review, competing-hypothesis debugging, multi-file features. Explicit file ownership per teammate and "delegate mode" (lead can only coordinate) are the most repeated tips. [S] — [30 Tips for Claude Code Agent Teams](https://getpushtoprod.substack.com/p/30-tips-for-claude-code-agent-teams), [Cobus Greyling](https://cobusgreyling.substack.com/p/claude-code-agent-teams)

**Claude Code's first-party answer to "one supervisor over many sessions"**
- "Projects" (public beta): one ongoing conversation; Claude starts a "thread" per task and reports each thread as a card with title+status; the conversation "works from recent messages, recent threads, and project memory rather than its full history" (an explicit supervisor-context-bloat mitigation); you can ask "Give me a status update on every thread"; a documented troubleshooting recipe for when threads come back "having assumed something wrong": ask the supervisor to "list what you asked it to do, what it assumed or couldn't reach, and what it's waiting on", fix the setup gap once, then send one thread before resending the rest. Caveats: "Run at most two threads at a time" is a preference not a cap; you cannot adopt a session you started yourself; a follow-up routed to a thread idle beyond the cache lifetime re-reads its whole conversation (cost). [F] — [Projects docs](https://code.claude.com/docs/en/claude-projects)
- Cross-session messaging (v2.1.224+): Claude discovers your other sessions with `ListAgents` and messages with `SendMessage`; sessions answer to a `/rename` name; when a name is duplicated Claude Code renames yours to a variant and, if several live sessions share a name, Claude "adds a short identifier to each row of its listing and uses the identifier in the address"; messages are plain text only, cannot approve permissions or change config, are refused/throttled in bursts and loops (repeated identical messages dropped, max 50 queued); `notify_when_idle` lets one session ask to be told once when another goes idle (expires after 12 h). Cost note: a message delivered to an idle session starts a new turn "sending your full context each time". [F] — [cross-session messaging docs](https://code.claude.com/docs/en/cross-session-messaging), [costs docs](https://code.claude.com/docs/en/costs)
- Agent view: background sessions report results *only to you* (not to other sessions); "running ten agents in parallel uses quota roughly ten times as fast as running one." [F] — [agent view docs](https://code.claude.com/docs/en/agent-view), [Run agents in parallel](https://code.claude.com/docs/en/agents)

**tmux-based and custom orchestrators**
- Tmux-Orchestrator (Orchestrator -> Project Managers -> Engineers; 1.8k stars): agents message via a `send-claude-message.sh session:window "..."` script; self-scheduled check-ins (`schedule_with_note.sh 30 "..."`); rules "commit after every step", auto-commit every 30 min, one task per agent, written specs; lists pitfalls "vague instructions, no git commits, too many tasks, missing checkpoints, no specifications". [F] — [Tmux-Orchestrator](https://github.com/Jedward23/Tmux-Orchestrator)
- claude-team / "Maniple" (manager Claude spawns worker Claude sessions in tmux/iTerm): rationale "managing that parallelism is difficult for humans with limited attention spans"; workers get fresh context while the manager's context stays free; workers addressed by short hex ID, terminal ID, or themed name ("all tools accept any of these"); non-blocking `check_idle_workers`, blocking `wait_idle_workers` (all/any), `poll_worker_changes` with a stale threshold (default 20 min); idle detected via stop-hook markers in JSONL; worktree per worker named `{issue_id}-{badge}`; `spawn_workers` takes 1-4 configs; after an MCP-server restart you must `discover_workers`/`adopt_worker` orphaned sessions. [F] — [Martian-Engineering/claude-team](https://github.com/Martian-Engineering/claude-team)
- Reliability of tmux `send-keys`/`capture-pane` as the message bus: reported as "approximately 70 to 80 percent reliable" (send-keys injects text regardless of whether the agent is mid-thought), prompts >2,000 chars get corrupted, some runtimes mangle multi-line input, capture-pane returns spinner/ANSI frames not structured state; several projects moved to file-based JSONL protocols. **Anecdote from issue trackers.** [S] — [AgentWrapper/agent-orchestrator #853](https://github.com/AgentWrapper/agent-orchestrator/issues/853) (page returned 404 when fetched; content from search summary), [crystl.dev](https://crystl.dev/guides/tmux-for-ai-agents/)
- "Chief of Staff" pattern (long-lived coordinator session + short-lived executor sessions + durable board): the coordinator "writes briefs, verifies claims, and reads diffs. It does not write the implementation, because a session that is implementing has stopped verifying"; rules: "a message is a nudge, a file is a contract; silence is not agreement"; every executor claim is re-run before it is believed ("OBSERVE the diff not the story"); session ID recorded as first comment on the card; status flips atomically; 15-30 min check-ins armed with a scheduler. Failure modes it targets: false completion claims, stale state, accepting narrative over evidence, archiving before verification. [F for the rule set in the PR; S for the blog] — [claude-starter PR #692](https://github.com/cardinalconseils/claude-starter/pull/692), [asyncdot blog](https://asyncdot.com/blog/chief-of-staff-pattern-orchestrating-claude-code-sessions/)
- OpenClaw-style front-ends (chat via Telegram/Discord -> gateway maps each channel/thread to a Claude Code session ID via `--resume`, spawns agents in detached tmux with approval-bypass flags): described as convenient but effectively autonomous with permissions bypassed. [S] — [MindStudio: Channels vs OpenClaw](https://www.mindstudio.ai/blog/claude-code-channels-vs-openclaw-mobile-agent-control)
- OpenAI Symphony (27 Apr 2026): Linear issue = unit of work, one isolated workspace/agent per active issue, supervisor restarts crashed/stalled agents; tickets move Todo -> In Progress -> Review -> Merging; "landed PRs up 500% in first three weeks among some teams" (**vendor claim**); repo itself says "low-key engineering preview for testing in trusted environments" and "works best in codebases that have adopted harness engineering". [F for repo; S for numbers] — [openai/symphony](https://github.com/openai/symphony), [Help Net Security](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/)
- Steinberger (2026, second-hand): The Decoder reports ~100 Codex instances in the cloud reviewing PRs/finding bugs at ~$1.3M of tokens per 30 days (603B tokens, 7.6M requests); he reportedly runs an orchestrator loop every five minutes to triage repos and direct threads. **Reported figures, second-hand.** [S] — [The Decoder](https://the-decoder.com/for-1-3-million-a-month-openclaw-founder-peter-steinberger-runs-100-ai-agents-that-code-review-prs-and-find-bugs/)

**Large "no-human" multi-agent experiments (relevant to supervisor design)**
- Carlini/Anthropic C compiler (5 Feb 2026): 16 parallel Claude agents, ~2,000 Claude Code sessions over ~2 weeks, ~2B input / 140M output tokens, just under $20,000; *no orchestrator* — each agent picked "the next most obvious problem", claimed tasks by writing text files in `current_tasks/` (git sync forced second claimants to choose another); "merge conflicts are frequent, but Claude is smart enough to figure that out"; failures: agents kept breaking existing features (needed stricter CI), and on a monolithic task (Linux kernel build) "every agent would hit the same bug, fix that bug, and then overwrite each other's changes" until GCC was used as an oracle to partition work; "Claude can't tell time" so the harness printed sparse progress; "the task verifier [must be] nearly perfect, otherwise Claude will solve the wrong problem". **Measured (author's own).** [F] — [Anthropic engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Cursor (Jan 2026, planners/workers/judge): flat self-coordination with locks failed — agents held locks too long or forgot to release; "twenty agents would slow down to the effective throughput of two or three"; with no hierarchy agents became risk-averse and made small safe changes; optimistic concurrency was simpler but not enough; an "integrator" role for quality control "created more bottlenecks than it solved"; fresh restarts each cycle combated drift; results: ~1M lines / 1,000 files browser over ~a week, a 3-week React migration. **Vendor anecdote.** [S] — [Cursor blog](https://cursor.com/blog/scaling-agents), [ZenML summary](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems), [Willison](https://simonwillison.net/2026/jan/19/scaling-long-running-autonomous-coding/)
- Anthropic's multi-agent Research system: lead + 3-5 parallel subagents beat single-agent Opus 4 by 90.2% on an internal eval but at ~15x the tokens of chat (agents ~4x); early failure: vague delegation ("one subagent explored the 2021 chip crisis while 2 others duplicated work investigating 2025 supply chains"); the lead waits synchronously for subagents so it cannot steer mid-flight; subagents write outputs to persistent artifacts so the lead does not relay them through the conversation ("game of telephone"). **Measured (vendor).** [F for token multiples, delegation failure, sync bottleneck and artifact pattern; S for the 90.2% and "3-5 subagents" figures] — [Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- Anthropic "when to use multi-agent systems": multi-agent typically uses 3-10x tokens; decomposing by *role* (planner/implementer/tester/reviewer) makes a "telephone game" where each handoff degrades fidelity (one example spent more tokens on coordination than work); split by *context boundary* instead; the most reliably useful multi-agent piece is a verification subagent that black-box tests without the build history; warning against "marking outputs as passing without thorough testing". [F] — [Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Cognition ("Don't Build Multi-Agents", 12 Jun 2025): sub-agents lack each other's intermediate decisions, "actions carry implicit decisions, and conflicting decisions carry bad results"; share full traces, avoid splitting decision-making. Its April 2026 revision, Walden Yan's "Multi-Agents: What's Actually Working": the narrow class that works is where "there is only one writer, and only intelligence is bundled" (three patterns: Code-Review-Loop, Smart Friend, map-reduce-and-manage); parallel-writer swarms are still discouraged and "most of the sexy ideas ... still don't see meaningful adoption". Vendor experience (Devin). [S] — [Cognition 2025](https://cognition.com/blog/dont-build-multi-agents), [Cognition 2026](https://cognition.com/blog/multi-agents-working), [Yan on X](https://x.com/walden_yan/article/2047054401341370639)
- IndyDevDan "Pi to Pi" (May 2026): drop the orchestrator, give agents two-way peer channels ("coms"/"coms-net"); argues "the best information is almost always on the worker level, but in a hierarchy it has to climb several layers (and survive several rewrites) before it shapes a decision" while admitting "for some shapes of work an orchestrator is still the right tool". [F for repo README; S for video summary] — [disler/pi-vs-claude-code](https://github.com/disler/pi-vs-claude-code), [Sparse Notes](https://sparsenotes.com/posts/2026/05/2026-05-23-pi-to-pi-agent-orchestration/)

**Status honesty / hallucinated success (cross-cutting)**
- Multiple tool trackers report failed delegations surfaced as successes: "A delegation that fails comes back as a successful MCP result... anything acting on the result programmatically cannot [tell]" (codex-subagent-mcp #23, 12 Sep 2026) [F] — [issue #23](https://github.com/parisbs/codex-subagent-mcp/issues/23); an orchestrator "shipped a failing test and reported success" [S] — [digital-chip-design-agents #75](https://github.com/hdl-tools/digital-chip-design-agents/issues/75).
- A dev.to essay claims "44-76% of agent task failures involved the agent confidently reporting success" across unnamed benchmarks — **low confidence, benchmarks not identified.** [S] — [dev.to](https://dev.to/rishi_g_25/your-coding-agent-tells-you-all-tests-pass-sometimes-thats-not-true-i32)

### Inferences
- The most credible "orchestrator works" reports share four traits: the supervisor does not implement; each worker has an isolated workspace and one work item; state lives in files/issues rather than chat; and *done* is decided by an external check (CI, oracle, re-running commands), not by the worker's self-report.
- The Mayor-style pattern "talk only to the supervisor" is reported as pleasant (DoltHub) but *expensive* and needs guardrails on merge (auto-merge of a PR with failing tests happened in the first day).
- Supervisor-status accuracy is mostly an unsolved plumbing problem in the reports: messages lost or duplicated, "idle" mistaken for "rate-limited/hung", stale task flags, and LLM one-line summaries used as status. Nothing found measures how often supervisor answers to "what is the progress of X?" are wrong.

### Gaps
- No Reddit/HN comment-level accounts of people using a custom Claude/Codex/Pi supervisor for months; HN threads (e.g. "Ask HN: Is it actually possible to run multiple coding sessions in parallel?" [item 47573483](https://news.ycombinator.com/item?id=47573483), "I built an agent orchestrator within tmux" [47561147](https://news.ycombinator.com/item?id=47561147), "Claude Code Orchestrator" [46578028](https://news.ycombinator.com/item?id=46578028)) were unreachable beyond titles.
- Second-hand cost numbers (Steinberger/OpenAI) and the "$47K two-agent loop" story I saw cited on Medium/dev.to could not be verified against primary sources and are non-coding contexts.
- No quantitative data on how often supervisor status reports are wrong.

## 3. Which concrete practices do people report (worktrees, branches, status files, naming/IDs, handoffs, check-ins, report-back prompts, notification hooks, review gates, WIP limits)?

### Takeaway
The practices with the most agreement: one isolated workspace (worktree/clone/container) + one branch per session; a durable written state (progress file / issue / board) that a fresh session or supervisor can read; explicit stable session identifiers (name + short ID + working directory, and ticket ID in the branch/worktree path); "report on blocked/done" as *structured* events rather than free chat; verification by an independent check before believing "done"; and small WIP. A minority successfully run same-folder agents with no worktrees (Steinberger) at the cost of discipline.

### Cited Findings

**Isolation: worktrees, branches, ports**
- Cherny/Claude Code team: 3-5 git worktrees at once, one Claude each; Cherny personally prefers multiple checkouts; some teammates name worktrees and alias `za/zb/zc` to hop between them. [S] — [Cherny on X](https://x.com/bcherny/status/2017742743125299476), [XDA](https://www.xda-developers.com/set-up-claude-code-like-boris-cherny/)
- Claude Code docs: "Worktrees give each session a separate git checkout, so parallel sessions never edit the same files"; sessions dispatched from agent view move into their own worktree before editing; agent-teams teammates are *not* isolated, so "partition the work so each teammate owns a different set of files". [F] — [Run agents in parallel](https://code.claude.com/docs/en/agents), [agent-teams](https://code.claude.com/docs/en/agent-teams)
- Carlini: each agent in its own Docker container cloning a local upstream, push/pull via git; lock files in `current_tasks/`. [F] — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)
- Worktree pitfalls reported: port/database/cache collisions ("every dev server defaults to the same ports"), fix with per-worktree `.env.local`; `refs/stash` is shared so "never use stash with parallel agents"; worktrees "isolate code but not the runtime environment"; no LSP in worktrees; one measured example: a ~2 GB repo consumed 9.82 GB in 20 minutes of automatic worktrees; orphaned worktrees/tmux sessions need manual cleanup. **Anecdotes.** [S] — [Upsun](https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents), [Penligent](https://www.penligent.ai/hackinglabs/git-worktrees-need-runtime-isolation-for-parallel-ai-agent-development/), [alexlavaee.me](https://alexlavaee.me/blog/parallel-agent-sessions-infrastructure-gap/)
- Same-folder counter-example: Steinberger runs 3-8 Codex agents mostly in one folder and commits carefully. **Anecdote.** [S] — [steipete.me](https://steipete.me/posts/just-talk-to-it)
- Merge landing: local FIFO merge queue with a pre-push gate for parallel agents (Show HN, Jul 2026); Gas Town uses a single Refinery; Cursor found an "integrator" role was a bottleneck and let workers resolve conflicts themselves; Carlini: merge conflicts frequent but agents resolve them. [S/F mixed] — [claude-code-merge-queue](https://github.com/funador/claude-code-merge-queue), [Cursor via ZenML](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems), [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)

**Status / progress / handoff files**
- Anthropic "Effective harnesses for long-running agents" (26 Nov 2025): `claude-progress.txt` for handoffs, a JSON feature list with pass/fail state ("It is unacceptable to remove or edit tests"), git commits per unit of work, an `init.sh`; every session starts with `pwd`, reads git log + progress file, picks the top unfinished feature, runs init to verify the environment; failure modes fixed: premature "project complete", attempting too much per session, broken handoffs, incomplete testing. [F] — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Anthropic "Long-running Claude for scientific computing" (23 Mar 2026): CHANGELOG.md as "the agent's portable long-term memory" tracking current status, completed tasks, *failed approaches and why*, accuracy tables, known limitations; "commit and push after every meaningful unit of work"; "Ralph loop" that kicks the agent back when it claims completion. [F] — [Anthropic](https://www.anthropic.com/research/long-running-Claude)
- Zechner: keep plans/todos as real files (TODO.md, PLAN.md); do context-gathering in its own session and hand a concrete artifact to a fresh session rather than polluting context. [S] — [Zechner](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)
- Per-worker checkpoint JSON files: pi-command-centre keeps `<project>/.pi/command-centre/workers/*.json`, one supervisor per ticket, and the controller only renders those isolated stores. [F] — [pi-command-centre](https://github.com/ananth99/pi-command-centre)
- agent-fleet: "Research never enters the dispatcher context" (findings stay on disk behind paths); a "Verification Contract" ledger of checkable acceptance assertions is written *before* any builder runs; cross-model review "catches rationalization". [F] — [agent-fleet](https://github.com/chankov/agent-fleet)
- Gas Town handoff: a worker "sends itself work, then restarts its session" so context resets without losing state; Beads = version-controlled work items. [S] — [Yegge](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04)
- Carlini: progress/README files updated frequently; logs kept short and grep-friendly ("if there are errors, Claude should write ERROR and put the reason on the same line"); test harness deliberately terse to protect context. [F] — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)

**Naming / task IDs / never confusing sessions**
- Claude Code: sessions addressed by `/rename` name; duplicates are auto-renamed to a variant; ambiguous names resolved with a short identifier per listing row; `/list-agents` (alias `/peers`) shows working directories to tell same-named sessions apart. [F] — [cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- claude-team: three interchangeable identifiers (short hex ID, terminal ID like `tmux:%1`, themed worker name) plus `{issue_id}` in the worktree path. [F] — [claude-team](https://github.com/Martian-Engineering/claude-team)
- pi-intercom: explicit `/alias`, stable session IDs in the roster, collision-resistant runtime aliases, cwd targeting ("the sole live peer in that directory"); safety guards: during an `ask`-triggered turn a non-reply `send` to a different target is rejected "to prevent accidental parent targeting"; inferred replies need exactly one pending ask; reconnect requires matching both ID *and* directory so a new session cannot inherit queued messages. [F] — [pi-intercom](https://github.com/nicobailon/pi-intercom)
- agent-fleet: identify a pane by the `(project, name)` pair it advertises, "not by cwd". [F] — [agent-fleet](https://github.com/chankov/agent-fleet)
- agentctl: unique session ID printed at spawn; children get `AGENTCTL_SESSION_ID` and `AGENTCTL_DEPTH` env vars; `--notify-session <id>` for completion callbacks. [F] — [agentctl](https://github.com/joargp/agentctl)
- pi-messenger: memorable auto-assigned names (SwiftRaven...), file reservations "Other agents get blocked with a clear message telling them who to coordinate with", reservations auto-release on exit. [F] — [pi-messenger](https://github.com/nicobailon/pi-messenger)
- Chief-of-Staff: session ID is the first comment on the issue card; issue body is the build contract. [F] — [PR #692](https://github.com/cardinalconseils/claude-starter/pull/692)
- Meta-observation from a heavy user: no inter-agent messaging primitive existed (before Claude's inbox); tmux naming is the DIY substitute. [S] — [alexlavaee.me](https://alexlavaee.me/blog/parallel-agent-sessions-infrastructure-gap/)

**Periodic check-ins and "report back when done/blocked"**
- Tmux-Orchestrator: agents self-schedule 30-minute check-ins; Chief-of-Staff: 15-30 min; claude-team: stale threshold 20 min; Claude Code agent teams: "check in on teammates' progress... unattended for too long increases risk of wasted effort"; Claude Code `notify_when_idle` (one-shot, 12 h expiry). [F] — sources above.
- Structured escalation: pi-subagents/pi-intercom give children a restricted `contact_supervisor` tool with three reasons `need_decision` (blocking ask), `interview_request`, `progress_update` (fire-and-forget). [F] — [pi-intercom](https://github.com/nicobailon/pi-intercom)
- Interactive-vs-autonomous subagent nuance: pi-interactive-subagents does *not* wake the parent on `stalled/recovered` for long-running user-driven subagents because "the user is working directly in the subagent's pane"; liveness is tracked from child-written runtime snapshots, not merely file growth, with a fixed internal watchdog marking `stalled`. [F] — [pi-interactive-subagents](https://github.com/HazAT/pi-interactive-subagents)
- Pi-supervisor: a goal-oriented supervisor checks after each turn, nudges when the agent drifts, uses a cheaper model than the worker, and after 5 consecutive steering messages switches to lenient mode (accept at 80%) to avoid endless loops. [F] — [pi-supervisor](https://github.com/tintinweb/pi-supervisor)

**Review gates / verification**
- Anthropic best-practices: give Claude a check it can run ("the difference between a session you watch and one you walk away from"); Stop hook as deterministic gate; "have Claude show evidence rather than asserting success"; writer/reviewer in separate sessions; adversarial-review step with warning that a reviewer told to find gaps will report some even when the work is sound (tell it to flag only correctness/requirement gaps). [F] — [best practices](https://code.claude.com/docs/en/best-practices)
- Cherny (via Kilo): giving an agent a way to verify its work makes final quality "2-3x better"; separate reviewer agent because "the person who wrote the code is the worst person to review it". **Anecdote.** [S] — [Kilo blog](https://blog.kilo.ai/p/how-7-kilo-code-engineers-run-up)
- Symphony proof-of-work; Chief-of-Staff "red gate" (proving check must fail first); Cursor judge agent per cycle; Carlini "nearly perfect verifier". [F/S as above]

**Notification hooks**
- Hook events (Notification, Stop, PermissionRequest) + ntfy/Tailscale/Pushover push notifications with phone Allow/Deny; "Claude Code Notifier" tracks all sessions and says which one needs you. [S] — [claude-ntfy-hook](https://github.com/nickknissen/claude-ntfy-hook), [tonydehnke.com](https://tonydehnke.com/blog/claude-code-notifications-ntfy-hooks/)
- IndyDevDan's observability dashboard: Python hook scripts -> Bun server + SQLite -> WebSocket -> Vue 3 client, capturing agent lifecycle events across concurrent agents with session tracking and live streaming (per-agent swim lanes and early surfacing of failures/permission requests per search summary). [F for architecture; S for swim lanes] — [disler hooks observability](https://github.com/disler/claude-code-hooks-multi-agent-observability)

### Inferences
- For an SLP design the recurring identity rule is: never address a session by display name alone; use (stable ID, human name, cwd/worktree, task/ticket ID), reject sends whose target is ambiguous, and record the session ID on the task card.
- "Report on blocked/done" works best as a *typed event written to a file/board* (need_decision / progress_update / done-with-evidence), not as prose the supervisor must interpret from a terminal screen.
- Verification-before-belief is the practice most consistently tied to fewer failure reports; it is also the one that costs extra tokens.

### Gaps
- No credible numbers on how often worktree-per-session breaks (ports/DB) in practice beyond individual anecdotes.
- Naming-convention advice is scattered in tool READMEs; no practitioner essay dedicated to session/task naming schemes was found.

## 5. What is reported specifically about Pi / Oh My Pi multi-session, subagent or supervisor use?

### Takeaway
Pi's author deliberately ships *no* sub-agent tool and pushes "run pi in tmux / separate session, pass artifacts". A large third-party extension ecosystem has grown around that gap (peer messaging, supervisors, session hubs, worktree side-agents), and OMP ships built-ins (task/subagents, Agent Hub, IRC, steering). ## 6. Most frequently recommended practices (synthesis across sources above)

### Takeaway
Ranked roughly by how many independent sources recommend each.

### Cited Findings
1. **Isolate every session's workspace and branch** (worktree/clone/container; one task = one branch); if you share a folder, partition files explicitly. — Cherny [S], Anthropic docs [F], Carlini [F], claude-team [F], Kilo [S]. Counter-view: same-folder works for careful solo users (Steinberger [S]).
2. **Keep a small number of foreground sessions (2-5) and push the rest to background/async with a board.** — Kilo [S], Osmani [S], Anthropic "3-5 teammates" [F], OpenAI/Symphony 3-5 [S], Willison [S].
3. **Give every task an automatic check and gate "done" on it (tests/CI/oracle/evidence), ideally re-run by someone other than the worker.** — Anthropic best practices [F], Carlini [F], Chief-of-Staff [F], Symphony [F], Cherny via Kilo [S], Claude "when to use multi-agent" [F].
4. **Persist state outside the chat: progress file / feature list / issue-tracker card / checkpoint JSON per worker; keep detailed research on disk, not in the supervisor's context.** — Anthropic harness [F], long-running Claude [F], agent-fleet [F], pi-command-centre [F], Zechner [S].
5. **Supervisor routes/verifies, never implements; talk to it, not to workers; workers stay inspectable (attach/peek/transcript).** — Gas Town/DoltHub [S], Chief-of-Staff [F], claude-team [F], agent view [F], OMP Agent Hub [F], Zechner's visibility argument [S].
6. **Stable, unambiguous session addressing (ID + name + cwd + ticket) and reject ambiguous sends.** — Claude cross-session docs [F], pi-intercom [F], claude-team [F], agent-fleet [F].
7. **Structured escalation instead of free chat: "needs decision / progress / blocked / done" events; notify only on needs-you.** — pi-command-centre [F], pi-intercom [F], agent view [F], Cherny notifications [S].
8. **Notify the human (system/mobile push) when a session needs input; batch decisions.** — Cherny [S], ntfy hooks [S], Projects [F].
9. **Split work by context boundary and independence; make tasks small and self-contained (5-6 per teammate); start with read-only research/review tasks.** — Anthropic multi-agent blog [F], agent-teams docs [F], Willison [S], Carlini's oracle partitioning [F].
10. **Use cheaper models for supervision/monitoring; Sonnet/Haiku for routine workers.** — pi-supervisor [F], costs docs [F], Steinberger's planner-vs-workhorse split [S].
11. **Periodic check-ins with stale/idle thresholds (15-30 min) rather than continuous polling; one-shot idle notifications.** — Tmux-Orchestrator [F], Chief-of-Staff [F], claude-team [F], Claude docs [F].
12. **Write lessons/failed approaches into a durable file and update CLAUDE.md/AGENTS.md after each correction.** — Cherny [S], Anthropic long-running [F], Klaassen/Every [S].

### Inferences
- Items 3, 4, 6 and 7 are precisely the requirements of the user's SLP need ("accurate progress on task C" and "never confuse sessions").

### Gaps
- Ranking is by my count of sources in these notes, not a systematic survey.

## 7. Most frequently reported failure modes (synthesis)

### Takeaway
Ranked roughly by frequency across sources.

### Cited Findings
1. **Human review/attention becomes the bottleneck; review quality degrades ("just accepting output"); burnout.** — Willison, Osmani, Ronacher, Zechner, Axios, Symphony, Superset HN [S]; Tuddenham [S].
2. **False, fabricated or stale status**: workers declare done without passing tests; orchestrator "confidently fabricates" results after a subagent failure; failed delegation returned as success; task flags not updated; lead ends early. — Claude issue #25818 [F], codex-subagent-mcp #23 [F], Agent Teams docs [F], Chief-of-Staff PR [F], Gas Town #4889 [F].
3. **Cost and quota blow-ups**: Gas Town ~10x normal per unit time and $3k-$6k runs [S]; agent teams ~7x [F]; Anthropic multi-agent ~15x chat, 3-10x vs single agent [F]; ten background agents = ten times the quota [F]; Carlini ~$20k [F]; second-hand $1.3M/month [S]; idle-session wakeups resend full context [F].
4. **Agents stepping on each other**: same-file overwrites, all agents fixing the same bug, `git commit --amend` rewriting a teammate's commit, shared ports/DB/stash. — Carlini [F], Claude issue #91513 [F], worktree guides [S], Cursor lock contention (20 agents -> throughput of 2-3) [S].
5. **Merge/landing problems**: PR auto-merged with failing integration tests, polecats merging directly to master, monolithic tasks that can't be parallelized; integrator role as bottleneck. — DoltHub [S], Cursor [S], Carlini [F].
6. **Lost, duplicated, mis-routed or unreliable messages**: send-keys 70-80% reliability, 4x duplicate delivery, multi-hour silent gaps from delimiter drift, messages dropped when teammates steal a poller, no persistence before notify. — tmux issue #853 [S], Claude #92244/#97102/#91541 [F].
7. **Telephone-game information loss and decision conflicts between sub-agents**: role-based decomposition, missing shared traces, vague delegation → duplicated work. — Anthropic [F], Cognition [S], IndyDevDan [F].
8. **Supervisor cannot tell "working" from "stuck" from "rate-limited"; silent deadlocks and 30-minute stalls; idle reaper killing healthy workers; no stall detection.** — Gas Town #4887/#4890 [F], OMP #13513 [F], Claude #92410 [F], OMP #3815 [F].
9. **Orphaned processes/worktrees/tmux sessions and lost sessions on restart** ("141 orphaned Claude Code processes", no `/resume` for in-process teammates, orphaned tmux). — Tenzin [S], Agent Teams docs [F], claude-team [F].
10. **Runaway or looping behaviour**: reviewer/critic ping-pong, blind resubmission, endless steering (pi-supervisor added a 5-message stagnation cutoff), "time blindness" spending hours on tests; Claude throttles message loops. — Claude #25818 [F], pi-supervisor [F], Carlini [F], Claude cross-session docs [F]. (The oft-cited "$47K two-agent loop" is from non-primary blog posts, unverified [S].)
11. **Supervisor/lead context bloat or lead doing the work itself**: lead exits/declares done early, mega-orchestrator hits context limits; mitigations are delegate mode, artifacts on disk, thin-context dispatchers, "recent messages + project memory rather than full history". — Agent Teams docs [F], agent-fleet [F], Projects docs [F], Vincent via Pulumi [S].
12. **Over-parallelizing tasks with a critical path / ambiguous work**: more agents ≠ faster; Gas Town "falls apart" on ambiguous human-in-the-loop work. — AkitaOnRails [S], Tenzin [S], Atwood [S].
13. **Permission/safety erosion when unattended**: approval-bypass flags for orchestrated agents, teammates inheriting the lead's permission mode, claims relayed by other agents treated as untrusted. — OpenClaw pattern [S], Agent Teams docs [F], cross-session docs [F].

### Inferences
- Failure modes 2, 6, 8, 9 are *plumbing* issues (typed events, IDs, heartbeats, persistence) and are addressable in an SLP design; modes 1, 3, 12 are inherent limits of human attention and cost and can only be managed by WIP limits, verification and task selection.

### Gaps
- Frequencies are counts of anecdotes/issues in this note, not incident rates.
- No systematic data on how often each mode occurs per hundred agent-hours.
