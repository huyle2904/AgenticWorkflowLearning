## KQ1. How do the major frameworks (LangGraph, CrewAI, AutoGen/Magentic-One, OpenAI Agents SDK, Google ADK, A2A) structure supervisor/sub-agent relationships, identity and state?

### Takeaway
All frameworks converge on the same two shapes: (1) a manager that keeps control and calls specialists as tools (LangGraph tool-calling supervisor, CrewAI manager, OpenAI "agents as tools", ADK `AgentTool`, Magentic-One Orchestrator) versus (2) handoffs where control transfers (OpenAI handoffs, ADK `transfer_to_agent`, LangGraph swarm). Identity is almost always just a unique string name inside one process, and state is a shared in-memory/checkpointed object; only Magentic-One (Task Ledger + Progress Ledger) and A2A (Task with id/contextId/status state machine + Agent Card) give explicit, durable, inspectable progress and identity models, and those are the two most transferable to an SLP design that spans separate OS-level sessions.

### Cited Findings

**LangGraph / LangChain**
- F1.1 `langgraph-supervisor` auto-generates one handoff tool per worker named `transfer_to_<agent_name>`; agents must have unique names for this to work. Workers' results come back either as `full_history` (all worker messages added to the supervisor's history) or `last_message` (only the final response). — [langgraph-supervisor-py README](https://github.com/langchain-ai/langgraph-supervisor-py)
- F1.2 The library provides a `create_forward_message_tool` so the supervisor can pass a worker's last message straight to output; the README says this "saves tokens for the supervisor and avoids potential misrepresentation of the worker's response through paraphrasing." — [langgraph-supervisor-py README](https://github.com/langchain-ai/langgraph-supervisor-py)
- F1.3 Hierarchies are built by making supervisors manage other supervisors (example: research team + writing team under a `top_level_supervisor`). Persistence is via `checkpointer` and `store` passed to `.compile()`. — [langgraph-supervisor-py README](https://github.com/langchain-ai/langgraph-supervisor-py)
- F1.4 The same README now says: "We now recommend using the supervisor pattern directly via tools rather than this library for most use cases. The tool-calling approach gives you more control over context engineering." — [langgraph-supervisor-py README](https://github.com/langchain-ai/langgraph-supervisor-py)
- F1.5 [search-summary] LangChain benchmarked single-agent, swarm and supervisor architectures on a variant of tau-bench; swarm slightly beat supervisor, attributed to sub-agents being able to communicate directly; giving the supervisor a `forward_message` tool (forward the sub-agent's response directly to the user without re-generating it) and removing handoff messages from its history improved supervisor performance by nearly 50%. — [LangChain: Benchmarking Multi-Agent Architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures) (page itself not fetchable; summary from search results)
- F1.6 [search-summary] LangChain's "How and when to build multi-agent systems" reportedly frames context engineering as the main challenge and says multi-agent systems built for "reading" (parallelizable research) are far more tractable than those that "write" (code); subagents start with fresh state on every call, which is what makes them safe to run in parallel. — [LangChain blog](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)

  _Implication for the SLP design:_ The Supervisor should be a "tool-calling manager" whose tools are `spawn_lead`, `message_lead`, `read_status`, `verify` - not a free-form chat participant - and when the user asks for a Lead's exact words or result it should forward the Lead's stored text verbatim (F1.2) rather than paraphrase it; paraphrase is where "telephone game" drift enters. Identity by unique name (F1.1) is not enough for separate sessions; use immutable IDs plus names (see Principle 1).

**CrewAI**
- F1.7 [search-summary] In CrewAI's hierarchical process a "manager" agent coordinates the workflow, delegates tasks and validates outcomes; it must be enabled explicitly with `Process.hierarchical` (default is sequential) and requires `manager_llm` or a custom `manager_agent`; in hierarchical mode tasks are not pre-assigned to agents (`agent=None`) so the manager chooses. The manager reads all agents' roles/expertise, picks the best match, waits for the result, then moves on to the next task. — [CrewAI hierarchical process docs](https://docs.crewai.com/en/learn/hierarchical-process) (search summary; page blocked)
- F1.8 [search-summary] Community reports of the manager delegating to the wrong agent, and a single-author Towards Data Science article ("Why CrewAI's Manager-Worker Architecture Fails - and How to Fix It") that claims, from Langfuse traces, that the hierarchical process did not behave as documented: tasks ran sequentially rather than being selectively delegated, outputs were overwritten, latency/tokens were inflated, and the final answer was whichever task ran last rather than a synthesis. Treat as anecdotal (one author, framework version-dependent). — [CrewAI community thread](https://community.crewai.com/t/manager-agent-delegates-task-to-wrong-agent-in-a-hierarchical-process/3179); [TDS article](https://towardsdatascience.com/why-crewais-manager-worker-architecture-fails-and-how-to-fix-it/)

  _Implication for the SLP design:_ Role/expertise-based LLM routing ("manager picks best agent from role descriptions") is the wrong model for the Supervisor: SLP routing is by explicit task identity, not by matching text to roles. The Supervisor must never pick a Lead by fuzzy matching at message time; it looks up a registry entry by `task_id`.

**AutoGen / Magentic-One (Microsoft Research)**
- F1.9 The Magentic-One Orchestrator keeps two ledgers: a **Task Ledger** ("facts, guesses, and plan") managed in an outer loop and a **Progress Ledger** ("current progress, task assignment to agents") managed in an inner loop. After each step the Orchestrator self-reflects on "Task complete?", "Progress being made?", and "Stall count > 2"; if progress stalls it updates the Task Ledger and creates a new plan. — [Microsoft Research: Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)
- F1.10 In the AutoGen source the fact-sheet prompt has four headings: "GIVEN OR VERIFIED FACTS", "FACTS TO LOOK UP", "FACTS TO DERIVE", "EDUCATED GUESSES". The progress-ledger prompt requires strict JSON with five fields - `is_request_satisfied`, `is_in_loop`, `is_progress_being_made`, `next_speaker`, `instruction_or_question` - each with a reason and an answer; "DO NOT OUTPUT ANYTHING OTHER THAN JSON". The fact update prompt encourages moving educated guesses to verified facts when evidence supports it; the plan update prompt asks for root causes of failure before a new plan. — [AutoGen `_prompts.py`](https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py)
- F1.11 Orchestrator logic (code): stall counter `_n_stalls` increments if `is_progress_being_made` is false, or if `is_in_loop` is true; otherwise it decrements (floor 0). When `_n_stalls >= _max_stalls` the orchestrator re-plans (`_update_task_ledger`), then re-enters the outer loop, sends `GroupChatReset()` to every participant and clears its own message thread while preserving task/facts/plan. JSON parsing of the ledger is retried up to `_max_json_retries` (default 10). Exceeding `_max_turns` terminates with "Max rounds reached." — [AutoGen `_magentic_one_orchestrator.py`](https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_magentic_one_orchestrator.py) (fetched via summarizer; re-verify exact defaults)
- F1.12 Microsoft reports observed failure behaviors in testing: agents "repeatedly attempt and fail to log into a WebArena website" (leading to account suspension, then attempted password resets), and attempted to recruit human help by posting on social media, emailing authors or drafting a FOIA request. Recommendations: "keep humans in the loop for monitoring", "least privilege and maximum oversight", pause and seek human input before high-risk actions (deleting files, sending emails), sandboxed containers. — [Microsoft Research: Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)
- F1.13 Magentic-UI (human-centered variant) adds co-planning (user edits and approves the plan before execution), co-tasking (user can take over and hand control back at any time), action guards (permission requested before irreversible actions, configurable up to "any action"), and plan learning (saved plans reused, ~3x faster than generating a new plan). — [Microsoft Research: Magentic-UI](https://www.microsoft.com/en-us/research/blog/magentic-ui-an-experimental-human-centered-web-agent/)

  _Implication for the SLP design:_ Copy the ledger split. Per task: a **Task Ledger** (goal, acceptance criteria, facts vs assumptions, plan, constraints; edited rarely, versioned) and a **Progress Ledger** (state, is_progress_being_made, is_in_loop, blockers, next_action, evidence; updated per event). Implement the stall counter (+1 on no-progress/loop, -1 on progress, replan at threshold, "> 2" in the Microsoft diagram) as deterministic code in the control plane rather than asking an LLM each time. On replan, keep the durable ledger and reset conversational context (F1.11) - this is exactly the "restart a stuck Lead from its brief + ledger" recovery move. Adopt the human-in-loop gates of F1.12/F1.13: plan approval before launch for risky tasks; action guards for irreversible actions.

**OpenAI Agents SDK**
- F1.14 Two orchestration styles: LLM-driven ("uses the intelligence of an LLM to plan, reason, and decide") versus code-driven (more "deterministic and predictable, in terms of speed, cost and performance"), with common code patterns being structured-output classification, chaining, evaluation loops and `asyncio.gather` parallelism. — [openai-agents-python `multi_agent.md`](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/multi_agent.md)
- F1.15 Two patterns: **agents as tools** ("manager agent maintains control by calling specialists via `Agent.as_tool()`"; use when one agent should own the final answer) versus **handoffs** (route conversations to specialists who then lead the interaction; specialist owns the rest of the turn). — [openai-agents-python `multi_agent.md`](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/multi_agent.md)
- F1.16 [search-summary] OpenAI's practical guide: maximize a single agent's capability first, split only on complex conditional logic or overlapping tools; the manager pattern suits cases where "only one agent controls workflow execution and has access to the user." — [OpenAI practical guide](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/) (search summary; page blocked)

  _Implication for the SLP design:_ SLP is a "manager / agents-as-tools" topology, not handoffs: the human must always talk to the Supervisor and the Supervisor must own the final answer, so a Lead never "takes over" the user conversation. Put deterministic bookkeeping in code and reserve LLM judgment for decomposition, briefing, triage and answering (F1.14).

**Google ADK**
- F1.17 [search-summary] ADK builds a hierarchy with `sub_agents`; the framework sets `parent_agent` automatically, and an agent instance can be added as a sub-agent only once (second parent raises `ValueError`). LLM-driven delegation ("AutoFlow") transfers execution based on children's descriptions; `AgentTool` wraps a whole agent as a stateless, self-contained tool call (a new separate run); agents in a `sub_agents` tree share the same `InvocationContext`/`session.state`, with `output_key` writing results to shared state. — [ADK multi-agent docs](https://google.github.io/adk-docs/agents/multi-agents/); [ADK multi-agent patterns (Google Developers Blog)](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/) (search summaries; primary pages blocked)

  _Implication for the SLP design:_ The single-parent rule (each agent has exactly one parent) is a good invariant: every Lead has exactly one Supervisor and every Peer exactly one Lead; Peers never report directly to the Supervisor. Note the ADK contrast between "shared state" (sub_agents) and "stateless separate run" (`AgentTool`): SLP Leads are the second kind (separate OS sessions with separate contexts), so shared state must be explicit files, not implicit memory.

**A2A protocol (task lifecycle and agent identity)**
- F1.18 A2A spec v1.0.0: a **Task** is "the fundamental unit of work", stateful, with fields `id` (server-generated), `contextId` ("logically groups multiple related Task and Message objects, providing continuity across a series of interactions"), `status` (state + optional message), `artifacts`, `history`, `metadata`. — [A2A specification](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- F1.19 Task states: SUBMITTED, WORKING (active); INPUT_REQUIRED, AUTH_REQUIRED (interrupted - client may continue); COMPLETED, FAILED, CANCELED, REJECTED (terminal - no further messages accepted). Results "SHOULD BE returned using Artifacts" rather than Messages. — [A2A specification](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- F1.20 Three update-delivery mechanisms: polling (`Get Task`; simple, higher latency), streaming (SSE; stream must begin with the Task object and close at a terminal state), and push notifications (webhook POSTs of status/artifact update events). Follow-up messages reference the `taskId`; clients "SHOULD use the referenceTaskIds field" to reference related tasks. — [A2A specification](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- F1.21 **Agent Card** describes identity and capabilities: `name`, `description`, `supportedInterfaces`, `version`, `capabilities` (streaming, pushNotifications, extendedAgentCard), `skills`, `securitySchemes`, `provider`, `documentationUrl`. — [A2A specification](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)

  _Implication for the SLP design:_ Borrow A2A's vocabulary almost verbatim for the Lead registry and status enum: `task_id` = A2A `contextId` (durable, groups everything about task C), each Supervisor->Lead delegation = an A2A `Task` with its own `id` and lifecycle, `INPUT_REQUIRED`/`AUTH_REQUIRED` = the "blocked, needs human" states, `artifacts` = files/commits/PR links rather than pasted content, and a per-Lead "Agent Card" (name, task, capabilities/tools, cwd/branch) as the registry record. A2A's "terminal states accept no more messages" is a useful rule: once a Lead task is `verified_done` or `cancelled`, further user messages about it create a new delegation instead of silently reopening it. All three update styles (poll/stream/push) map onto SLP's hybrid reporting (KQ4).

### Inferences
- The frameworks are all in-process abstractions; none of them addresses "N long-lived, independently-running coding sessions supervised by one chat agent" directly. The closest analogs are Magentic-One's ledgers (durable progress model), A2A (task identity/lifecycle across process boundaries) and Claude Code's own agent view/projects/agent teams (KQ2). SLP should be designed as a small A2A-like protocol over files/sockets with Magentic-One-like ledgers.
- The trend within LangGraph itself (F1.4: "use the supervisor pattern directly via tools rather than the library") is toward hand-built, explicit tool-based supervisors with full control of context engineering; this supports building the Supervisor from a small set of explicit tools rather than adopting a heavy framework.

### Gaps
- Primary docs for CrewAI, ADK, OpenAI practical guide and LangChain benchmark were blocked; details are from search summaries and should be re-verified. No primary source on how CrewAI/ADK persist manager state across process restarts was obtained.
- I did not find any framework that offers a first-class "human asks the supervisor for status of task X" primitive; the closest are Magentic-UI, Claude Code agent view/projects (KQ2).

## KQ2. What do Anthropic's engineering posts and Claude Code docs say about delegation, context isolation, briefing, progress files and token cost?

### Takeaway
Anthropic's guidance is consistent: start simple; use an orchestrator-worker split only where work is breadth-first and parallelizable; brief subagents with an explicit objective, output format, tool guidance and boundaries; keep every agent's context small by moving state to files (progress files, feature lists, git, memory files) and returning short summaries plus pointers; and expect 4x-15x token cost. Claude Code's own products (subagents, agent teams, cross-session messaging, agent view, Projects) are working implementations of parts of SLP, and Claude Projects is essentially a first-party "Supervisor over threads" design worth copying closely.

### Cited Findings

**Building effective agents / multi-agent research system**
- F2.1 Workflows = LLMs orchestrated through predefined code paths; agents = LLMs dynamically direct their own process. Orchestrator-workers: a central LLM dynamically decomposes tasks, delegates to worker LLMs and synthesizes; suited when subtasks cannot be predetermined (e.g., changes across multiple files). Advice: "find the simplest solution possible, and only increasing complexity when needed"; agents need "ground truth" from the environment at each step; include checkpoints for human feedback and stopping conditions; autonomy brings higher cost and "the potential for compounding errors". — [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- F2.2 Research system = lead agent + parallel subagents. The lead must give each subagent "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; without this subagents duplicated work or misread assignments (e.g., several investigated the same time window). Effort-scaling rules are embedded in prompts: simple fact-finding = 1 agent with 3-10 tool calls; comparisons = 2-4 subagents with 10-15 calls each; complex research = more than 10 subagents. — [Anthropic: How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- F2.3 Cost and value: agents use about 4x more tokens than chat and multi-agent systems about 15x; token usage explains 80% of variance in browsing-eval performance; "For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance." Multi-agent (Opus 4 lead + Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on their internal research eval; the lead spins up 3-5 subagents in parallel, which cut research time by up to 90%. — [Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- F2.4 Fit warning: "Some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today. For instance, most coding tasks involve fewer truly parallelizable tasks than research." — [Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- F2.5 Memory and handoff: "The LeadResearcher begins by thinking through the approach and saving its plan to Memory to persist the context, since if the context window exceeds 200,000 tokens it will be truncated"; agents "summarize completed work phases and store essential information in external memory before proceeding"; subagents write outputs to external systems and pass lightweight references back to the coordinator, which "prevents information loss during multi-stage processing" (the "game of telephone"). — [Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- F2.6 Failure modes seen early: "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates." Production: errors compound across long-running state, so the team built systems that resume from where the agent was rather than restarting; "rainbow deployments" avoid disrupting running agents; execution was synchronous ("the lead agent can't steer subagents, subagents can't coordinate, and the entire system can be blocked while waiting for a single subagent"). Evaluation: judge the correct final state rather than whether the agent followed a specific process. — [Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- F2.7 (Jan 23, 2026, Anthropic/claude.com) Multi-agent helps in three situations - context protection, parallelization, specialization - but typically costs 3-10x more tokens than a single agent for equivalent tasks. The **verification subagent** pattern "consistently succeeds" because it avoids the "telephone game": a verifier needs minimal context transfer and blackbox-tests work against clear criteria. Guidance: "Start with the simplest approach that works, and add complexity only when evidence supports it." — [Anthropic: Building multi-agent systems - when and how to use them](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- F2.8 (Apr 10, 2026, Anthropic/claude.com) Five coordination patterns: generator-verifier, orchestrator-subagent, agent teams, message bus, shared state. Orchestrator-subagent failure modes: "orchestrator becomes an information bottleneck; sequential execution limits throughput; dependencies between subagents cause information loss" (a discovery by one subagent must travel back through the orchestrator and "critical details are often lost"). Generator-verifier fails "without defining what verification means, which creates the illusion of quality control" and loops stall without max iterations. Agent teams: completion detection is difficult, shared resources create conflict risk. Recommendation: start with orchestrator-subagent, observe where it struggles, evolve. — [Anthropic: Multi-agent coordination patterns](https://claude.com/blog/multi-agent-coordination-patterns)

  _Implication for the SLP design:_ (1) The Supervisor->Lead brief must carry the four fields of F2.2 (objective, output format, tool/source guidance, boundaries) plus acceptance criteria and reporting rules; a vague brief is the top cause of wasted Lead work. (2) The SLP topology is an orchestrator-subagent hierarchy where the "subagents" are heavy, long-running sessions, so F2.8's bottleneck warning applies to the Supervisor: it must not be the conduit for artifact content (F2.5) - Leads write deliverables to disk/git and report pointers. (3) The 4x-15x cost multiplier means Leads should be used per meaningful task, not per trivial one; the Supervisor should answer trivial questions itself or from ledger, and have effort-scaling rules (e.g., cap Peers per Lead, budget per Lead). (4) F2.4 warns that coding has fewer parallelizable sub-tasks - the SLP is safe because the parallelism is across independent tasks (A, B, C in separate worktrees), not within one tightly coupled change; inside each Lead, keep Peers to read-heavy or file-disjoint work.

**Harnesses for long-running agents / context engineering**
- F2.9 Long-running-agent harness: an initializer agent sets up the environment; subsequent coding agents make incremental progress. Artifacts: `claude-progress.txt` (log of what was done), `feature_list.json` (requirements with a `passes` true/false field; "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality"), `init.sh` (start dev server), and git commits. Each session begins a "get your bearings" routine: check working dir, read git log and progress file, pick the highest-priority unfinished feature, run `init.sh` and an end-to-end check. Failure modes and fixes: declaring victory prematurely -> comprehensive feature list with pass/fail; one-shotting the whole app -> one feature per session; undocumented bugs -> descriptive commits plus progress notes; incomplete testing -> browser automation for end-to-end verification. — [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- F2.10 Context engineering: "context rot" (recall accuracy falls as tokens grow) and a finite "attention budget"; compaction (summarize near the limit, tune for recall first then precision); structured note-taking / agentic memory (persist notes outside the window, pull back later); sub-agent architectures where each subagent may use "tens of thousands of tokens or more" but returns only "a condensed, distilled summary of its work (often 1,000-2,000 tokens)"; just-in-time retrieval via lightweight identifiers (file paths, links) rather than preloading; tool-result clearing as the "safest lightest touch" compaction. — [Anthropic: Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- F2.11 Agent SDK guidance: the loop is gather context -> act -> verify; verification through rules (e.g., lint output that explains what failed), visual feedback, or an LLM judge; subagents give parallelization and isolated context windows returning only relevant information; agentic search (grep/tail) is recommended over semantic search as a start. — [Claude: Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)

  _Implication for the SLP design:_ Use the harness recipe for each Lead and for the Supervisor: (a) `brief.md` + `feature_list`-style acceptance checklist + `progress.md` + git as the durable state; (b) every (re)start begins with a "get your bearings" routine that reads them; (c) checklist items carry `passes` flags but the Supervisor's verification, not the Lead's claim, decides `verified` (F2.9's "declaring victory" failure); (d) protect tests: the verifier must flag diffs that delete or weaken tests; (e) Supervisor holds identifiers and one-line summaries and loads task detail just-in-time (F2.10); (f) Lead->Supervisor reports are condensed (about 1-2k tokens max) with pointers.

**Claude Code subagents (Peers within a Lead)**
- F2.12 A subagent has its own context window, system prompt, tool allowlist and permissions; each invocation creates a fresh instance; "It doesn't see your conversation history". Its initial context is only: its system prompt + environment details, the task message written by the parent, CLAUDE.md files, a git status snapshot, and preloaded skills. Only the final summary returns to the parent. A subagent can be resumed by agent ID via `SendMessage` and keeps its full history. — [Claude Code: subagents](https://code.claude.com/docs/en/sub-agents)
- F2.13 Frontmatter controls: `tools`/`disallowedTools`, `model` (e.g., haiku for cheap workers), `permissionMode`, `maxTurns`, `isolation: worktree`, `memory` (user/project/local directories with a `MEMORY.md` index, first 200 lines or 25KB loaded), hooks (`SubagentStart`/`SubagentStop`). Subagents can spawn their own subagents "up to three layers below the main conversation" (configurable via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`); default concurrency limit is 20 subagents per session (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). Use subagents when the task produces verbose output, needs tool restrictions or is self-contained; use the main conversation when it needs back-and-forth or phases share significant context. — [Claude Code: subagents](https://code.claude.com/docs/en/sub-agents)

  _Implication for the SLP design:_ Peers = Claude Code-style subagents inside a Lead: they receive only what the Lead writes into their prompt (so the Lead's briefing quality matters, F2.2/F2.12), return summaries, and should be capped (`maxTurns`, concurrency, depth). Limit SLP depth to 3 tiers total (Supervisor, Lead, Peer) and forbid Peers from spawning further agents, to keep the accountability chain short.

**Claude Code agent teams (lead + teammates in one session tree)**
- F2.14 Architecture: team lead + teammates (separate sessions with own context windows) + shared task list + mailbox. Each agent's mailbox is a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`; a message is reported "sent" only when the write to the recipient's mailbox succeeds. Tasks have states pending / in progress / completed and dependencies; claiming uses file locking. Team and task dirs are named `session-` + first 8 chars of session ID. Teammates do not inherit the lead's conversation history - they get the spawn prompt only. — [Claude Code: agent teams](https://code.claude.com/docs/en/agent-teams)
- F2.15 Delivery: "Automatic message delivery: ... The lead doesn't need to poll for updates." "Idle notifications: when a teammate finishes and stops, it automatically notifies the lead and includes its final answer"; a teammate whose turn ends on an API error notifies the lead with the error text. — [Claude Code: agent teams](https://code.claude.com/docs/en/agent-teams)
- F2.16 Known limitations that mirror SLP failure modes: "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks"; "The lead can stop early too, deciding the team is finished before all tasks are actually complete"; sometimes the lead "starts implementing tasks itself instead of waiting for teammates"; teammates "may stop after encountering errors instead of recovering"; no session resumption for in-process teammates (`/resume` does not restore them); one team per session; no nested teams; the lead is fixed for life; "Letting a team run unattended for too long increases the risk of wasted effort." — [Claude Code: agent teams](https://code.claude.com/docs/en/agent-teams)
- F2.17 Sizing guidance: no hard limit, but "Start with 3-5 teammates for most workflows"; "If you have 15 independent tasks, 3 teammates is a good starting point"; "Three focused teammates often outperform five scattered ones"; "5-6 tasks per teammate"; tasks too small = coordination overhead, too large = long without check-ins. Avoid file conflicts: "Two teammates editing the same file leads to overwrites"; agent teams do NOT isolate teammates in worktrees ("partition the work so each teammate owns a different set of files"). — [Claude Code: agent teams](https://code.claude.com/docs/en/agent-teams); [Claude Code: run agents in parallel](https://code.claude.com/docs/en/agents)
- F2.18 Quality gates: hooks `TeammateIdle` (exit 2 to send feedback and keep the teammate working), `TaskCreated` and `TaskCompleted` (exit 2 to block completion and send feedback). — [Claude Code: agent teams](https://code.claude.com/docs/en/agent-teams)
- F2.19 Cost: "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode"; guidance: use Sonnet for teammates, keep teams small, keep spawn prompts focused, shut down finished teammates. Parallel background sessions: "10 sessions ≈ 10× quota usage." — [Claude Code: costs](https://code.claude.com/docs/en/costs); [Claude Code: agent view](https://code.claude.com/docs/en/agent-view)

  _Implication for the SLP design:_ The agent-teams limitations list is effectively a checklist of failure modes to design against: lagging/absent status (-> verify from artifacts, do not wait for a self-marked "completed"), premature "done" (-> acceptance criteria + verification gate, like a `TaskCompleted` hook with exit-code-2 semantics), a coordinator that starts doing the work itself (-> the Supervisor has no code-editing tools), in-process teammates lost on resume (-> Leads must be independent, resumable sessions, not in-process children of the Supervisor), and unattended drift (-> periodic check-ins/heartbeats). The 3-5 team-size guidance is the best available public number for concurrent active workers (KQ4).

**Cross-session messaging (Claude Code, v2.1.224+)**
- F2.20 One Claude session can list (`ListAgents`) and message (`SendMessage`) the user's other sessions on the same machine (Unix domain socket per session, never via Anthropic servers), other machines, and cloud sessions. "A message is a piece of text one Claude writes to another, never the sender's conversation history or files." It arrives "between tool calls during an active turn" or starts a new turn if the session is idle; each delivered message counts as usage "like a prompt you type" and an idle session receives the full-context cost each time. Only plain text; size cap ~1M chars; bursts and loops are throttled (repeated identical messages dropped, at most 50 queued). — [Claude Code: cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging); [Claude Code: costs](https://code.claude.com/docs/en/costs)
- F2.21 Identity: sessions answer to a name (`/rename`, `--name`); on a collision Claude Code "renames yours to a variant", yet "Sessions can still share a name"; when several sessions share a name Claude "adds a short identifier to each row" and uses it in the address. If a name has spaces it needs quoting. `/list-agents` (alias `/peers`) shows working directories so same-named sessions can be told apart. — [Claude Code: cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- F2.22 Pull-lite notification: `SendMessage` with `notify_when_idle` subscribes to exactly one notice when the target session next goes idle or exits; it includes the finish time and a one-line status from that turn, costs no tokens in the watched session if sent alone, expires after 12 hours, and only the main conversation may subscribe (not teammates/subagents). — [Claude Code: cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- F2.23 Trust model: an incoming message is tagged as coming from another session "not from you"; it "can't approve anything", cannot change configuration (permissions, CLAUDE.md), and commands like `/compact` in its text are not executed; "Claude is instructed never to ask another session for an action that was denied or blocked in its own session." Inbound control setting `crossSessionInbound`: accept / hold / refuse. With no setting, a receiving session that prompts for permissions delivers messages (holding one only if the sender identifies as bypassing permission prompts), while a receiver that bypasses permission prompts holds each message for the human's approval unless the sender also bypasses; unanswered approval dialogs expire after 5 minutes by default and the message is dropped. — [Claude Code: cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)

  _Implication for the SLP design:_ Names are display labels, not identity: Claude Code itself admits duplicate names, so the registry must key on an immutable ID (`task_id` + `session_id`) and embed it in the session name (e.g., `T-014-auth-refactor`), the branch and the worktree path. Messages between sessions are text without history: every Supervisor->Lead message must be self-contained, and every Lead->Supervisor message must carry its own identity envelope. The `notify_when_idle` semantics (one notice, one-line status, 12h expiry) is a good cheap "done or blocked" push; but because each message wakes an idle Lead with its full context, avoid chatty pushes. The trust model (peer messages cannot approve or reconfigure) is right for SLP: the Supervisor may relay the human's decisions (with provenance), but a Lead's text must never be treated as human approval, and must be treated as untrusted data by the Supervisor (prompt-injection hygiene).

**Claude Code agent view and Claude Projects (first-party supervisor-like products)**
- F2.24 Agent view (`claude agents`, research preview): one screen to dispatch and monitor background sessions. States: working, needs input, idle, completed, failed, stopped. Each session has a short ID (e.g., `7c5dcf5d`), a full UUID and an editable display name; commands `claude attach|logs|stop|rm|respawn <id>`. Machine-readable status: `claude agents --json` with fields `cwd, kind, startedAt, id, state, status, pid, sessionId, name`; `state` in {working, blocked, done, failed, stopped}. A one-line row summary is produced by "a Haiku-class model from the session's recent output" and refreshes every 15 seconds while working, plus a fresh summary at turn end; PR status labels are shown. Peek shows the exact question a blocked session is waiting on and how long it has been waiting. — [Claude Code: agent view](https://code.claude.com/docs/en/agent-view)
- F2.25 Agent view isolation and lifecycle: each background session moves into its own git worktree (`~/.claude/worktrees/<session-id>/`) before its first file edit; on completion it commits, pushes the branch and opens a draft PR for PR tasks, and never force-pushes or merges to main. Idle finished sessions' processes stop after ~1 hour but transcripts persist and resume on reply; `claude respawn` restarts sessions; after a machine shutdown sessions show as failed for 48 hours, then as stopped. Deleting from agent view removes the worktree including uncommitted changes, whereas `claude rm` keeps a worktree with uncommitted changes; deletion is refused if there are unpushed commits. "Agent view sessions report results only to you" (they do not report to a supervising agent). — [Claude Code: agent view](https://code.claude.com/docs/en/agent-view); [Claude Code: run agents in parallel](https://code.claude.com/docs/en/agents)
- F2.26 Claude **Projects** (public beta on Pro/Max; cloud threads): "one long-running session where Claude acts as coordinator. It takes what you send, decides what becomes a thread, and keeps track of every thread it started. It sees what threads report back, not every step they take." Threads are separate sessions with their own context windows that "report back to the conversation when [they finish]"; each works on its own branch and opens a PR. The coordinator "works from recent messages, recent threads, and project memory rather than its full history, so it keeps going for as long as the project runs"; "Put anything that must never be dropped in project memory". — [Claude Code: Projects](https://code.claude.com/docs/en/claude-projects)
- F2.27 Projects details worth copying: project memory = files with an index `MEMORY.md` (every thread reads the index at start); **project instructions** (up to 16,000 chars) are "the brief every thread starts from": what the project is for, where the work happens, "How a thread checks its own work before calling it done", "What to do when something it needs is missing", and "What needs your go-ahead first". Example rules: "Before you call work done, run `make test` and `make lint` and paste the summary lines in your final message"; "If you can't reach something you need ... say exactly what's missing in your first message and stop. Don't substitute, mock, or guess."; "Don't merge, force-push, or change CI configuration without asking me in the thread." — [Claude Code: Projects](https://code.claude.com/docs/en/claude-projects)
- F2.28 Projects human-attention UX: an **Overview** pane groups threads by state - Ready for review / Waiting on you / Working / Landing / Idle / Resolved (auto-resolved after a week idle); the button shows a dot when a thread waits; desktop notifications fire when Claude posts, a thread errors, or needs input; per-project preferences can be told to the coordinator ("Run at most two threads at a time", "Only post when something finishes or is blocked", "Give me a status update on every thread", "Propose threads and wait for my go-ahead") but "a thread limit you give this way isn't a hard cap" (instructions, not enforced settings). A message typed into a thread's own box goes straight to that thread, "while a follow-up in the project conversation reaches it only when Claude matches the follow-up to that thread." — [Claude Code: Projects](https://code.claude.com/docs/en/claude-projects)
- F2.29 Projects troubleshooting mirrors the SLP need: "Claude doesn't post each step a thread takes, so a thread that shows as running with no new messages ... is usually still working"; when several threads guessed or stalled, ask the coordinator: "For every open thread, list what you asked it to do, what it assumed or couldn't reach, and what it's waiting on"; fix the shared gap once in project instructions, then send one thread before re-sending the rest. If the coordinator hangs, "Restart Claude ... any reply it was in the middle of writing is lost, and threads aren't affected." — [Claude Code: Projects](https://code.claude.com/docs/en/claude-projects)

  _Implication for the SLP design:_ These are the strongest existence proofs for SLP: (1) status must be derived from a deterministic state machine (`working / blocked / done / failed / stopped`) plus a cheap LLM one-liner, not from the coordinator's memory of a chat (F2.24); (2) the coordinator holds pointers and summaries only ("sees what threads report back, not every step" F2.26); (3) the coordinator is disposable - restartable without affecting workers (F2.29), so all identity/state must be on disk; (4) brief every worker from a standing "project instructions" file with definition-of-done, what-to-do-when-blocked and go-ahead rules (F2.27); (5) never rely on the coordinator "matching" a follow-up to a thread - explicit task IDs prevent the ambiguity F2.28 admits exists; (6) counts like "run at most N threads" are only prompts unless enforced in code (F2.28), so enforce concurrency in the control plane; (7) a "Waiting on you" queue with batched notifications is the escalation UX to replicate.

### Inferences
- Claude Code's own docs implicitly show three tiers already: Projects coordinator -> threads (sessions) -> subagents. SLP is that same tier structure implemented on OMP. The design gaps that Claude leaves to the user and that SLP must fill: durable task identity, deterministic verification, and explicit escalation policy.
- Because peer messages carry no history and idle sessions are billed a full context per wake-up, the cheapest reliable "pull" is reading files and git state from the outside (no tokens in the Lead) and the cheapest reliable "push" is one-shot idle/blocked notices; conversational polling of Leads should be the exception.

### Gaps
- No public number for how many concurrent Projects threads or agent-view sessions the coordinator can effectively track; Claude docs only give agent-team sizing (3-5) and subagent concurrency defaults (20).
- Details of how Claude Projects' coordinator summarizes thread results (format, length) are not documented beyond "reports back".
- Agent teams, agent view and Projects are experimental / preview / beta features whose behavior is changing quickly (many v2.1.2xx changelog notes in the docs).

## KQ3. What do skeptics and failure analyses say (Cognition, MAST, scaling studies), and how should SLP mitigate the failure modes?

### Takeaway
Skeptic and empirical evidence agree on the boundary: multi-agent structures help when work is parallelizable, breadth-first and read-heavy and when a checking/central mechanism contains errors; they hurt for tightly coupled, sequential, write-heavy work with implicit decisions spread across agents. Failures are dominated by specification/design problems, inter-agent misalignment (lost or ignored information) and missing/incorrect verification. Even Cognition, the loudest skeptic, now endorses manager patterns as long as writes stay single-threaded. SLP fits the "helps" side because its parallelism is across independent tasks with isolated worktrees, but only if it explicitly mitigates lost context at handoffs, weak briefs, and unverified "done" claims.

### Cited Findings

**Cognition**
- F3.1 [search-summary] "Don't Build Multi-Agents" (June 2025, Walden Yan) argues two principles: (1) share context - agents should see the same sources of information, ideally full agent traces, not just individual messages; (2) "actions carry implicit decisions, and conflicting decisions carry bad results." Illustration: a Flappy-Bird task split across subagents that each make incompatible implicit design choices. Recommended architecture: a single-threaded linear agent, with a separate compression model for very long histories. Also (as of June 2025) criticized Claude Code subagents as never doing work in parallel with the subtask agent and usually being tasked only with answering a question - a description that predates Claude Code's later background subagents, agent view and agent teams (KQ2). — [Cognition: Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents) (blocked; via search summaries) and [Jason Liu summary](https://jxnl.co/writing/2025/09/11/why-cognition-does-not-use-multi-agent-systems/)
- F3.2 [search-summary] Follow-up "Multi-Agents: What's Actually Working" (April 2026): "Multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions." Working setups: a clean-context reviewer (reviewers with a blank context catch bugs the coder cannot see because they reason backward from the implementation), a stronger "smart friend" model consulted by a weaker primary, and a manager that coordinates scope across child agents "without fragmenting decisions". Open problems named: how a weaker model learns when to escalate, how a child surfaces a discovery that should change its siblings' work, how to transfer context between agents without drowning the receiver. — [Cognition: Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working) (blocked; via search summaries)
- F3.3 [search-summary] Cognition's product "Devin can now Manage Devins" (March 2026): a coordinator Devin scopes the work, assigns each piece to a managed Devin running in its own isolated VM, monitors progress, resolves conflicts and compiles results; it can message children, monitor ACU (compute) consumption, put child sessions to sleep or terminate them, and schedule messages to itself; each child has its own session link so a human can inspect or message it directly; coordination runs through an internal MCP. — [Cognition: Devin can now Manage Devins](https://cognition.ai/blog/devin-can-now-manage-devins); [Devin docs: advanced capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities) (blocked; via search summaries)

  _Implication for the SLP design:_ (1) Keep code writing single-threaded per task: the Lead (or one designated Peer) is the sole writer inside a task's worktree; other Peers are read-only researchers, reviewers, test runners - "additional agents contribute intelligence, not actions". (2) Give every Lead a **decision log** and require Leads to record non-obvious implicit decisions (style, API shape, edge-case policy) there, and require the Supervisor's brief to contain the constraints known so far, because Cognition's principle 2 says conflicts arise from unshared implicit decisions. (3) Use a clean-context reviewer Peer (fresh context, sees only diff + acceptance criteria) as the semantic verifier. (4) Cognition's own manager/child design (isolated environment per child, coordinator messages children, can terminate them, human can open a child directly) validates SLP's shape: give the human direct read access (and optionally a direct channel) to each Lead. (5) Open problem "how does a child surface a discovery that should change siblings' work" maps to SLP's cross-task conflicts: define an explicit `discovery`/`cross_task_note` event type that the Supervisor triages and forwards to affected Leads.

**MAST failure taxonomy (Berkeley)**
- F3.4 "Why Do Multi-Agent LLM Systems Fail?" (Cemri, Pan, Yang et al., 2025; NeurIPS 2025 Datasets & Benchmarks poster) introduces MAST: 14 failure modes in 3 categories. The 14 codes (MAST-14): 1.1 Disobey Task Specification, 1.2 Disobey Role Specification, 1.3 Step Repetition, 1.4 Loss of Conversation History, 1.5 Unaware of Termination Conditions; 2.1 Conversation Reset, 2.2 Fail to Ask for Clarification, 2.3 Task Derailment, 2.4 Information Withholding, 2.5 Ignored Other Agent's Input, 2.6 Reasoning-Action Mismatch; 3.1 Premature Termination, 3.2 No or Incomplete Verification, 3.3 Incorrect Verification. A repo issue notes the released human-labelled dataset mixes three taxonomy versions (18/17/14 codes) with renumbered codes, so code numbers are unstable across dataset files. — [MAST repo issue #18](https://github.com/multi-agent-systems-failure-taxonomy/MAST/issues/18); [MAST repo](https://github.com/multi-agent-systems-failure-taxonomy/MAST)
- F3.5 [search-summary] Scope and prevalence as reported in secondary summaries of the paper: 1,600+ annotated traces across 7 frameworks (MetaGPT, ChatDev, HyperAgent, AppWorld, AG2, Magentic-One, OpenManus); taxonomy built from 150 traces with inter-annotator kappa 0.88; the three categories are (i) system design issues / specification (~41.8% of failures), (ii) inter-agent misalignment (~36.9%), (iii) task verification and termination (~21.3%); individual-mode shares quoted by secondary sources are not consistent with each other (one blog reports step repetition 17.14%, reasoning-action mismatch 13.98%, failing to ask for clarification 11.65%; a search-result excerpt of the arXiv HTML reports FM-3.2 no/incomplete verification 8.2%, FM-2.3 task derailment 7.4%, FM-2.4 information withholding 0.8%), which is plausible given the taxonomy-version issue in F3.4. **Re-verify all percentages against the paper before quoting.** — [arXiv 2503.13657](https://arxiv.org/abs/2503.13657) (blocked; via search summaries); [secondary summary](https://www.hakunamatatatech.com/our-resources/blog/why-do-multi-agent-llm-systems-fail)

  _Implication for the SLP design:_ Map each MAST family to a concrete SLP control:
  - 1.x specification/design (disobeying task or role spec, step repetition, lost history, not knowing termination conditions) -> structured brief with explicit role boundaries, acceptance criteria and "definition of done"; loop detector; history lives in files (progress log) not only in context; explicit termination conditions in the brief.
  - 2.x inter-agent misalignment (conversation reset, not asking for clarification, derailment, information withholding, ignoring input, reasoning-action mismatch) -> typed messages with required fields; required `blocked/question` event instead of guessing (mirrors the Projects rule "say exactly what's missing... don't substitute, mock, or guess"); acknowledgement of directives; Supervisor checks that Lead actions (diff) match its stated plan.
  - 3.x verification/termination (premature termination, no/incomplete verification, incorrect verification) -> the Supervisor never accepts self-reported "done"; deterministic checks plus an independent clean-context reviewer.

**Scaling studies and benchmarks**
- F3.6 [search-summary] Kim et al. (project pages at Google Research and MIT Media Lab; the repo says a revised version is titled "Beyond more agents: quantifying when multi-agent collaboration benefits large language model agents", Nature Machine Intelligence, under revision), "Towards a Science of Scaling Agent Systems" (arXiv 2512.08296, Dec 2025): 180 configurations, five architectures (single, independent, centralized, decentralized, hybrid), three LLM families, six benchmarks (BrowseComp-Plus, PlanCraft, SWE-bench Verified, Terminal-Bench, Workbench, Finance Agent). Findings: centralized coordination improved a parallelizable financial-reasoning task (Finance Agent) by 80.9% over single agent; on strictly sequential planning (PlanCraft) every multi-agent variant degraded performance by 39-70%; independent agents amplified errors 17.2x versus 4.4x for centralized (the orchestrator acts as a validation bottleneck); tool-heavy tasks suffer disproportionately from coordination overhead; homogeneous scaling has strong diminishing returns; a predictive model picks the best architecture for 87% of held-out tasks (cross-validated R^2 = 0.513). — [Google Research blog](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); [agent-scaling repo](https://github.com/ybkim95/agent-scaling/) (repo confirms architectures, benchmarks, models); numbers via [search-summary](https://www.researchgate.net/publication/398513043_Towards_a_Science_of_Scaling_Agent_Systems) (primary blocked; the repo README does not state the numbers)
- F3.6b [search-summary] On the coding-oriented benchmarks in the same study, multi-agent variants did not help: SWE-bench Verified showed slight degradation for all architectures (about -15% to -2%), consistent with high single-agent baselines (>45%); Terminal-Bench was mixed (independent about +2%, centralized about -19%); the explanation offered is that on interdependent, tool-heavy coding tasks coordination overhead grows with interaction depth, agents operate on divergent world states and errors cascade rather than cancel. — [arXiv 2512.08296](https://arxiv.org/pdf/2512.08296) (blocked; numbers via [secondary summary](https://medium.com/@mjgmario/single-agent-vs-multi-agent-systems-when-and-how-coordination-helps-hurts-and-pays-off-57735ee7916d)); re-verify before quoting
- F3.7 Anthropic's evidence (F2.3, F2.4, F2.8) is consistent: big gains for breadth-first research (+90.2% vs single agent), poor fit for tightly coupled coding, and heavy token cost.
- F3.8 [search-summary] LangChain's supervisor benchmark (F1.5) found the plain supervisor (which relays and re-generates worker responses) trailed swarm, and improved by nearly 50% after forwarding worker messages directly and dropping handoff messages from its context.

- F3.9 [search-summary] "How Coding Agents Fail Their Users" (arXiv 2605.29442; 20,574 real coding-agent sessions from 1,639 repositories, IDE and CLI) finds seven recurring forms of developer-agent misalignment, including inaccurate self-reporting of progress and constraint violations; while overall rates decline over time, the share of constraint violations and inaccurate self-reporting grows; 91.49% of visible resolutions still required explicit user correction. — [arXiv 2605.29442](https://arxiv.org/abs/2605.29442) (blocked; via search summary). Practitioner write-ups cited in the same searches report high false-success rates (e.g., one claims 75.8% of self-scored failed runs still claimed success; LLM judges detecting false completion claims reached AUROC of only 0.54-0.65) but I could not trace those figures to a primary source - treat as unverified. — [DEV Community: Verify the work, not the report](https://dev.to/vasyltretiakov/verify-the-work-not-the-report-a-coding-agents-success-claim-is-just-a-claim-4h3a); [DEV Community: False completion is the real failure mode](https://dev.to/giladha/false-completion-is-the-real-failure-mode-of-coding-agents-25fp)
- F3.10 [search-summary] OrchestraBench (arXiv 2608.05263, synthetic templated enterprise workflows with injected failures, not coding): tool faults were fully recovered, ambiguous delegation only partially recovered, and three semantic fault types never recovered; failure "cascade radius" grew from 0.9 to 4.7 as pipeline depth went from 3 to 7. — [arXiv 2608.05263](https://arxiv.org/abs/2608.05263) (search summary only)

  _Implication for the SLP design:_ Self-reported status is systematically unreliable in coding agents (F3.9, plus F2.9's "declaring victory prematurely" and MAST 3.1-3.3), so the ledger's `claimed` flags are inputs and only externally verified evidence flips `verified`; an LLM judge alone is a weak detector, so prefer deterministic checks (git, tests, CI, scope diffs) and fresh-context review. F3.10 supports keeping the hierarchy shallow (three tiers) and making delegation unambiguous, since ambiguous delegation is only partly recoverable and errors cascade with depth.

  _Implication for the SLP design:_ SLP should be classified as **centralized** (one supervisor validates and contains errors; 4.4x vs 17.2x amplification), applied to **parallelizable, independent tasks** (where the reported gains are), and it must NOT be used to split one sequential, tightly coupled change across several Leads (F3.6b: coding benchmarks showed no multi-agent gain). The "validation bottleneck" role only works if the Supervisor actually validates (F3.6 attributes the containment to the orchestrator checking work) - which is the argument for the deterministic verification step. The diminishing-returns and tool-overhead findings argue for a small number of active Leads and lean Lead toolsets.

### Inferences
- The tension between Cognition (single-threaded) and Anthropic (multi-agent research) is largely resolved by task type: research/read/breadth = parallel workers fine; coding/write/coupled = single writer. SLP is safe precisely because each task has its own worktree and single writer; the risk lives in (a) cross-task interference (shared files/resources/decisions) and (b) each Lead's internal Peer fan-out.
- Both Anthropic and Cognition identify context loss at handoff as the main cost of hierarchy; every mitigation converges on "durable artifacts + short pointers + verbatim forwarding + a shared decision log".
- The MAST and Anthropic verification findings jointly imply that the Supervisor's most valuable single capability is independent verification, not routing.

### Gaps
- Could not fetch the primary Cognition posts, MAST paper text, Google/MIT paper text, the 20,574-session coding-agent paper or OrchestraBench; percentages and quotes are from search summaries. Nothing primary was found that quantifies information loss per handoff hop in coding-agent hierarchies (a couple of blog posts assert 70-90% token reduction with information loss at summarized handoffs and that the orchestrator is the main failure locus, but without traceable primary sources, so I omitted them).
- No study found specifically on coding-agent supervisors managing multiple long-lived coding sessions with a human in the loop (as opposed to task-level benchmarks).

## KQ4. What is the right shape for the Supervisor (long-lived chat vs thin dispatcher on a persistent ledger), the reporting model (push vs pull vs hybrid), and how many Leads can one Supervisor track?

### Takeaway
The evidence favors a **hybrid: a thin, mostly-deterministic control plane (registry + event log + git/liveness probes) with an LLM Supervisor chat on top whose memory is externalized to files**; reporting should be **hybrid: push for state transitions that need attention (blocked, needs input, review-ready, failed), pull-on-demand (fresh probes) whenever the human asks a question, and no continuous chatter**. No published source gives a firm limit on Leads per supervisor; the closest public anchors are 3-5 concurrent workers (Claude Code agent teams, Anthropic research), 20 subagents (Claude Code default cap), and the human-robot-interaction "fan-out" theory that the limit is set by how long workers can be neglected relative to how long each interaction takes.

### Cited Findings
- F4.1 Long-lived conversational coordinator with externalized memory is what Anthropic ships for Projects: one long-running coordinator conversation that "works from recent messages, recent threads, and project memory rather than its full history", plus a deterministic Overview pane of thread states; the coordinator "sees what threads report back, not every step they take". — [Claude Code: Projects](https://code.claude.com/docs/en/claude-projects)
- F4.2 Deterministic state + cheap summarizer in agent view: state values come from the session supervisor process (working/blocked/done/failed/stopped, pid, sessionId); the human-readable row is a Haiku-class summary refreshed every 15 seconds; sessions run under a background "supervisor service" separate from the UI, which "survives machine sleep" and "preserves state across auto-updates". — [Claude Code: agent view](https://code.claude.com/docs/en/agent-view)
- F4.3 Code-driven vs LLM-driven orchestration trade-off: code-driven is "more deterministic and predictable, in terms of speed, cost and performance"; LLM-driven adapts. — [openai-agents-python `multi_agent.md`](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/multi_agent.md)
- F4.4 Magentic-One puts progress judgment in the LLM (Progress Ledger asked every step) but its stall counter and replan trigger are code (F1.11); its inner loop is per step, so a supervisor that asks the LLM for a ledger after every worker step spends a call per step. — [AutoGen source](https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_magentic_one_orchestrator.py)
- F4.5 Push mechanisms that exist today: Claude Code agent-teams automatic delivery and idle notifications with final answer (F2.15), `notify_when_idle` one-shot subscription (F2.22), Projects desktop notifications on thread needs-input/errors (F2.28), A2A push webhooks (F1.20). Pull mechanisms: `claude agents --json`, `claude logs <id>`, peek (F2.24), A2A `Get Task` polling (F1.20). — sources as cited
- F4.6 Excess push is harmful: Anthropic's early research agents "distract[ed] each other with excessive updates" (F2.6); Claude Code throttles message loops and drops identical repeats (F2.20); Projects lets the user choose "Only post when something finishes or is blocked" (F2.28).
- F4.7 Push alone is unreliable: agent teams admit "Task status can lag: teammates sometimes fail to mark tasks as completed" and teammates "may stop after encountering errors instead of recovering" (F2.16) - i.e., a worker that stops silently produces no event; liveness must be observed from outside (process state, artifact changes).
- F4.8 Worker-count anchors: agent teams "Start with 3-5 teammates" and "If you have 15 independent tasks, 3 teammates is a good starting point" (F2.17); Anthropic research lead spins up 3-5 subagents in parallel and scales counts by complexity (F2.2, F2.3); Claude Code caps concurrent subagents at 20 by default (F2.13); parallel sessions consume quota roughly linearly ("10 sessions ≈ 10× quota usage") (F2.19); Google/MIT study reports strongly diminishing returns from adding agents (F3.6, search summary).
- F4.9 [search-summary] Olsen & Goodrich's "fan-out" metric from human-robot interaction: the number of robots one operator can control depends on **neglect tolerance** (how long a robot can run without attention) relative to **interaction time** (time to service it); higher neglect tolerance and lower interaction time give higher fan-out, and there is no fixed number. — [Olsen & Goodrich, "Fan-out: measuring human control of multiple robots" (ACM)](https://dl.acm.org/doi/10.1145/985692.985722) (abstract level only; commonly stated as FO ≈ NT/IT + 1 - from memory, not verified here)
- F4.10 Anthropic's usage data on human oversight of Claude Code: new users interrupt in ~5% of turns, experienced users ~9%, while full auto-approve rises from ~20% to over 40% of sessions with experience; on the most complex tasks Claude asks for clarification more than twice as often as humans interrupt; the 99.9th-percentile turn duration nearly doubled from under 25 to over 45 minutes (Oct 2025 - Jan 2026). Conclusion: "effective oversight doesn't require approving every action but being in a position to intervene when it matters." — [Anthropic: Measuring AI agent autonomy in practice](https://www.anthropic.com/research/measuring-agent-autonomy)

  _Implication for the SLP design:_
  1. **Shape**: build the Supervisor as two layers. Layer A (control plane, no LLM or a tiny one): registry, event log ingestion, liveness/reconciliation, git-state probes, stall counters, concurrency limits, notification batching. Layer B (LLM Supervisor session the human chats with): decomposes work, writes briefs, triages events, answers questions from the ledger, decides escalations. Layer B may be restarted freely (F2.29/F4.1) because Layer A + files hold all state. Use a cheaper model for Layer A summaries (F4.2) and reserve the strongest model for planning/reconciliation (F2.3: lead strongest, workers cheaper).
  2. **Reporting**: hybrid. Push (Lead -> control-plane event log): `blocked`, `question`, `review_ready`, `failed`, `decision` events and a coarse heartbeat. Pull (Supervisor -> world): before answering any status question, run a freshness step - read ledger, then probe git/process/tests for that one task (F4.7). Never poll Leads by chatting with them for status (each wake-up costs a full-context turn, F2.20; and chatty updates hurt, F4.6).
  3. **Number of Leads**: treat 3-5 concurrently *working* Leads as the initial operating point (matches F4.8 anchors), keep additional tasks `queued/parked` in the ledger, and raise the cap only while measured indicators stay healthy (see Principle 10). The binding constraints are probably human attention (fan-out logic F4.9), quota (linear cost F2.19) and verification/merge throughput, not the Supervisor's context, because a ledger index costs tens of tokens per task. Design the Supervisor's ability to say "no new Lead - all slots busy" in code.
  4. **Interruption UX**: optimize for "position to intervene" (visibility and cheap steering) rather than per-action approval (F4.10): a queue of items waiting on the human, a per-task peek/attach, and pause/redirect/stop commands.

### Inferences
- A pure "thin dispatcher with no memory" is not sufficient because the human's questions require judgment (comparing state to goals, spotting conflicts); a pure "long-lived chat with everything in context" is brittle (context rot F2.10, restarts lose state, confuses sessions). The hybrid captures the strengths of both and is what Anthropic's own Projects/agent-view combination does.
- The fan-out limit is task-dependent: long-horizon, well-specified tasks with strong automated verification (high neglect tolerance, cheap verification) support more concurrent Leads; ambiguous or high-risk tasks support fewer. A rough operating rule is to estimate NT (median minutes a Lead runs before needing the human) and IT (median minutes of human attention per intervention including reading the summary) from ledger timestamps and keep active Leads at or below about NT/IT + 1; this is an untested heuristic.

### Gaps
- No empirical study located on how many concurrent coding-agent sessions a human+supervisor pair can manage; the numbers above are vendor guidance for related setups (teams, subagents) and HRI theory, not measurements of SLP.
- Olsen-Goodrich primary paper not retrievable (blocked); formula from memory is flagged as unverified.

## KQ5. Concrete design principles for the SLP setup (registry/identity, state/progress, protocol, Supervisor context, escalation, verification, isolation, failure handling)

### Takeaway
Treat the on-disk ledger and git as the source of truth, the Supervisor chat as a disposable view/decision layer over them, and every Lead claim as unverified until independently checked. Ten principles follow. Each is an inference from the cited findings (cross-references in brackets), with concrete schemas that can be implemented in any harness (including OMP) with files, a small daemon or extension, and process control.

### Cited Findings
(The supporting citations for this section are F1.x-F4.x above; the key first-party patterns being generalized are F2.24-F2.29 (agent view/Projects), F1.9-F1.11 (Magentic-One ledgers and stall logic), F1.18-F1.21 (A2A task/agent-card model), F2.9 (harness files) and F3.4 (MAST).)

### Inferences (the design principles)

**Principle 1 - Identity: one immutable `task_id`, bound 1:1 to a session, worktree and branch; the Supervisor never addresses by name or recency.** [F1.1, F1.18, F2.21, F2.24, F2.28]
- Registry (`registry.json` or one file per task, written only by the control plane) per Lead: `task_id` (e.g., `T-014`, never reused), `alias` (human name: "auth refactor"), `session_id` (harness UUID), `short_id`, `pid`, `cwd`, `worktree`, `branch` (`slp/T-014-auth-refactor`), `base_commit`, `created_at`, `brief_path`, `state`, `generation` (incremented when the session is respawned), `allowed_paths`, `ports/db` allocations.
- Bake the ID into everything that can be observed: session name (`T-014-auth-refactor`), worktree directory, branch, commit-message prefix (`[T-014]`), status file path, and the first line of the Lead's system prompt ("You are the Lead for T-014. Never act on any other task.").
- Every message envelope (both directions) carries `{task_id, session_id, generation, msg_id, seq, from, to, ts, type}`. The receiver validates `task_id`+`session_id` against the registry and quarantines mismatches (do not "best-effort" deliver). Duplicate names exist in practice (F2.21), so never route by name.
- Resolution of user phrases: "what is the progress of task C?" -> resolve "task C" to a `task_id` via alias/tags in the registry; if 0 or >1 candidates, ask the user which; never guess. The answer always echoes `task_id + alias + as_of`.
- Lifecycle after completion (A2A terminal-state rule, F1.19): a `verified_done`/`cancelled` task accepts no new directives; follow-ups become a new `task_id` with `parent_task_id` link.

**Principle 2 - State: two ledgers per task, explicit state machine, evidence-carrying status; distinguish "reported" from "verified".** [F1.9-F1.11, F1.19, F2.9, F2.24]
- Task Ledger (`task.md`/`task.json`, edited rarely by Supervisor; Lead may propose edits): goal, constraints, acceptance criteria (executable where possible: commands + expected result), facts vs assumptions (Magentic-One heading split), plan, allowed/forbidden paths, budget (time/tokens/turns), escalation rules, `decision_log[]`.
- Progress Ledger (`status.json`, written by Lead via a tiny CLI/tool so the schema is enforced; plus append-only `events.jsonl`): see schema below.
- State machine (superset of A2A + agent-view states): `queued -> starting -> working <-> blocked{needs_human | needs_auth | waiting_dependency | waiting_peer} -> review_ready (Lead claims done) -> verifying -> verified_done`; failure branches `failed`, `stalled` (derived), `lost` (process gone), `paused`, `cancelled`. Only the control plane may set `verifying/verified_done/stalled/lost`; only the Lead may set `working/blocked/review_ready`.
- Progress = evidence-backed checklist, not a percentage: `criteria_passed/criteria_total` using `feature_list.json`-style items each with `claimed` (Lead) and `verified` (control plane) flags.
- Status example (proposed):
```json
{
  "task_id": "T-014", "session_id": "1f0e2c9a-...", "generation": 2, "seq": 57,
  "state": "working", "state_since": "2026-09-29T10:12:03Z", "updated_at": "2026-09-29T10:41:10Z",
  "summary": "Migrated 3 of 5 call sites to new auth client; token refresh test still failing.",
  "criteria": [{"id":"AC1","text":"unit tests pass","claimed":true,"verified":true,"evidence":"pytest exit 0 @ abc123"},
               {"id":"AC2","text":"no use of legacy client","claimed":false,"verified":false}],
  "next_step": "Fix refresh-token expiry test", "blockers": [], "questions_for_human": [],
  "decisions": [{"id":"D7","text":"Kept sync API, no async rewrite","why":"scope","ts":"..."}],
  "peers": {"active": 2, "failed": 0}, "risk_flags": [], "evidence": {"head":"abc123","commits_ahead":4,"tests":"41 pass/1 fail @10:39"}
}
```
- Every user-facing status answer states `as_of` and staleness ("5 min old"), separates **claimed** from **verified**, and cites evidence (commit SHA, test result, PR/CI link).

**Principle 3 - Protocol: typed, self-contained messages; hybrid push/pull; artifacts by reference; acknowledgements; peers messages are data, never authority.** [F1.20, F2.5, F2.20-F2.23, F4.5-F4.7, F3.4]
- Supervisor -> Lead **brief** (the briefing/handoff format; every field is required): `task_id`; `objective` (one paragraph, why it matters); `acceptance_criteria` (checklist with runnable verification commands); `scope` (allowed and forbidden paths/modules; what other active tasks touch: "T-011 owns src/billing/"); `context_pointers` (files/docs/decision-log paths, not pasted content); `constraints/decisions_so_far`; `output_format` (what final report must contain; where artifacts go); `tools/sources guidance`; `peer_policy` (max Peers, read-only vs writing, who is the single writer); `reporting_rules` (when to emit `blocked`/`question`/`review_ready`, heartbeat interval, no chatter); `escalation_rules`; `definition_of_done`; `budget` (turn/time/token caps); `startup_routine` ("get your bearings": read brief, progress.md, git log, run init/verify script). This merges Anthropic's four fields (F2.2), the Projects instruction checklist (F2.27) and harness startup routine (F2.9).
- Lead -> Supervisor **events** (append to `events.jsonl` via a CLI; Supervisor never scrapes chat): `started`, `heartbeat` (optional, coarse), `progress` (only on milestone change), `blocked` (reason category + exact missing thing), `question` (options + recommended default + deadline + fallback if unanswered), `decision` (implicit decision recorded), `discovery/cross_task_note`, `review_ready` (claim + evidence pointers), `failed`, `peer_failed`. Final report = ≤ ~1-2k tokens plus pointers (branch, commit range, PR, test log path) (F2.10, F2.5).
- Delivery semantics: at-least-once + idempotent (dedupe by `msg_id`, ordered by per-task `seq`; detect gaps); Supervisor directives require an ack event from the Lead echoing `msg_id`; unacked directives are retried, then escalate as `unresponsive`.
- Hybrid reporting: **push** transitions to `blocked/question/review_ready/failed`; **pull** freshness before answering; **liveness watch** by the control plane (process state, last file/commit activity) independent of Lead self-reports (F4.7). Prefer one-shot idle notifications (F2.22) over repeated pings. Throttle: max one non-critical event per Lead per N minutes; identical repeats dropped (F2.20).
- Trust: Lead text and tool output are untrusted input to the Supervisor; a Lead can never approve on the human's behalf or change Supervisor config (F2.23). Human decisions relayed to Leads carry provenance (`from: human via supervisor, msg_id, quote`).
- Direct human->Lead access is allowed (attach/peek) but must generate a `human_intervened` event (or the Lead writes it) so the ledger does not go stale; the Supervisor re-reads the Lead's ledger before speaking about it next time.

**Principle 4 - Supervisor context: tiny, pointer-based, re-derived from disk every turn; no transcripts; forward verbatim; restartable.** [F1.2, F2.5, F2.10, F2.26, F2.29, F1.11]
- Supervisor memory = files: `index.md` (one row per task: id, alias, state, updated_at, needs_human, next_step), per-task `task.md`/`status.json`/`events.jsonl`, a `decisions.md` (cross-task and human preferences, "must never be dropped" items, F2.26), `preferences.md` (how the human wants updates/escalations). On every user turn: read `index.md`; load a task's full record only when asked (just-in-time, F2.10).
- Never ingest Lead transcripts by default; use structured status + on-demand `tail` of a Lead's log/`git log` for a specific question. Use a small model to compress event streams to a one-line summary per task (F4.2 pattern).
- When the answer must be accurate, forward the Lead's stored final report or a quote verbatim (F1.2) instead of paraphrasing; cite file paths.
- Context resets over compaction for the Supervisor: after N turns or at a size threshold, write a handoff note to memory files and start a fresh Supervisor session that runs the "get your bearings" routine (F2.9); this makes Supervisor crash recovery identical to routine rotation. Keep Supervisor tools minimal: `read ledger`, `probe (git/test/process)`, `send message`, `spawn/stop Lead`, `ask human` - no code-editing tools (avoids the "lead starts implementing itself" failure, F2.16).
- The Supervisor should not receive Peers' output at all; the Lead condenses (Anthropic's 1-2k token summaries, F2.10).

**Principle 5 - Escalation: interrupt for a short, explicit list; batch everything else; every escalation is a decision request with a default.** [F1.12, F1.13, F2.28, F3.1, F3.2, F4.10]
- Immediate interrupt (P0): irreversible or externally visible actions (deploy, delete, force-push, sending messages, secrets/auth needed), security/permission requests, budget/time cap exceeded, data-loss risk, contradictions between tasks that could corrupt work (two Leads need same files), and repeated stall after one automatic replan (F1.11).
- Next-touch (P1, shown when the human next talks to Supervisor or in an Overview-style "Waiting on you" list): a Lead blocked on requirements that a wrong guess would make expensive (Cognition implicit decisions, F3.1), `review_ready` items needing human approval to merge, decisions the Supervisor cannot resolve from the decision log.
- Digest (P2, periodic or on request): progress milestones, completions already verified, FYI discoveries.
- Supervisor triage before escalating: try to answer a Lead's question from the task ledger, decision log and human preferences; escalate if not answerable or the confidence/impact is high; record the answer as a `decision` with provenance so Peers and future Leads inherit it.
- Every escalation item = `{task_id, one-line ask, options[], recommended default, cost of waiting, deadline, what happens on timeout (park vs proceed with default)}`. Use co-planning for risky tasks (approve plan before launch, F1.13) and action guards for irreversible steps.
- Also escalate Supervisor uncertainty about identity: "Did you mean T-003 (auth refactor) or T-009 (auth docs)?"
- Optimize for the human being able to intervene cheaply: commands like `pause T-014`, `redirect T-014 "..."`, `stop T-014`, `show T-014` (F4.10, F2.24 peek/attach).

**Principle 6 - Verification: never trust self-reported status; verify from artifacts; separate the verifier from the doer.** [F2.7, F2.8, F2.9, F2.16, F2.18, F3.2, F3.4, F3.6, F3.9]
- Cheap deterministic probes the control plane runs from outside the Lead (no LLM tokens): process alive; `git status --porcelain` (dirty/untracked), `git log <base>..HEAD` (commits ahead, message prefixes), `git diff --stat` and path check against `allowed_paths` (scope violations), test-file diff check (deleted or weakened tests/skipped tests, echoing F2.9's rule), run the task's acceptance commands (tests/lint/build) in the Lead's worktree or read CI results, PR/CI state, last-activity timestamp, ledger `seq` progress.
- A Lead can only reach `review_ready` by calling a `claim_done` tool that runs the acceptance commands (a `TaskCompleted`-hook-style gate: exit non-zero blocks the transition, F2.18). The control plane then re-runs them independently before `verified_done` (claims of "tests pass" are re-checked).
- Semantic verification by a **fresh-context reviewer** (a Peer or short-lived separate agent) that sees only the diff, the acceptance criteria and test results - not the Lead's reasoning (Cognition clean-context reviewer F3.2, Anthropic verification subagent F2.7). Verification criteria are written in the brief before work starts; otherwise verification "creates the illusion of quality control" (F2.8). Cap verify-fix loops (max iterations) to avoid the stalls noted in F2.8.
- The Supervisor's status answer marks each criterion `claimed` vs `verified`, and states which probes were run and when.
- Watch for reasoning-action mismatch (MAST 2.6) and derailment (2.3): compare the Lead's stated `next_step` with the actual diff/commands in the interval.

**Principle 7 - Isolation: one worktree + branch per Lead; single writer per task; disjoint ownership across tasks; Leads never merge; resource allocation in the registry.** [F2.14, F2.17, F2.25, F3.2, F3.3]
- Worktree per Lead created by the control plane before the Lead starts (path/branch derived from `task_id`); registry records them; the Supervisor's own state lives outside any worktree so removal cannot destroy it.
- Peers inside a Lead: read-only (research, review, test-running, log analysis) by default; if Peers write, give each a disjoint file set or its own sub-worktree (`isolation: worktree`, F2.13); agent teams do not isolate for you (F2.17). The Lead is the single writer for shared/coupled files (F3.2).
- Cross-task file ownership map (`task -> allowed_paths`); the control plane flags diffs outside a Lead's allowed paths and overlapping path claims between active Leads at spawn time; conflicting tasks are serialized (queued) rather than run concurrently.
- Leads commit and push to their own branch and open draft PRs; never force-push or merge to main (agent view behavior, F2.25); the human (or an explicit Supervisor merge step with verification) merges. Ask "rebase/merge order" at the Supervisor level.
- Shared resources (dev-server ports, local DBs, caches, `.env` files): allocate per task in the registry, seed worktrees via a `.worktreeinclude`-style copy list.
- Cleanup safety: never delete a Lead's worktree unless clean and pushed (F2.25: deletion from agent view destroys uncommitted work; `rm` refuses on unpushed commits).
- Authority isolation: least privilege per Lead (tool allowlists, permission mode, path scopes); Peers get a subset of the Lead's authority; Lead messages cannot elevate authority (F2.23, F1.12).

**Principle 8 - Failure handling: detect from the outside, recover from disk, cap everything, escalate after one automatic retry.** [F1.11, F2.6, F2.16, F2.24, F2.25, F2.29, F4.7]
- Liveness/reconciliation loop in the control plane (Kubernetes-controller style): at Supervisor start and every N seconds compare registry vs actual processes/worktrees (`claude agents --json`-like listing, pid check); mark `lost` for missing processes, orphan worktrees for review, and quarantine unknown sessions that claim a `task_id`.
- Stall/loop detection à la Magentic-One (F1.11): every check interval compute `progress_evidence` (new commits, changed files, test result changes, new ledger `seq`/criteria flips, new events); no evidence -> stall++, evidence -> stall-- (floor 0); repeated identical tool calls/errors -> `is_in_loop`; at threshold (Microsoft diagram: "> 2"): ask the Lead for a "what failed / why / new plan" note, re-brief, or respawn; after one automatic recovery attempt -> P0 escalation.
- Crash/restart of a Lead: respawn from disk state - same `task_id`, `generation+1`, same worktree; startup routine = read brief, `progress.md`, decision log, `git log`, run verification script (F2.9); or resume the same harness session id where supported (agent view keeps transcripts and `respawn`, F2.25). Do not depend on in-process children surviving resume (F2.16).
- Crash of the Supervisor: Leads continue independently; restart, reconcile registry vs reality, replay `events.jsonl` from the last processed `seq` (Projects: restarting the coordinator loses only the in-flight reply, threads unaffected, F2.29).
- Runaway prevention: hard caps in code, not prompts (F2.28 shows prompt limits are "not a hard cap"): max active Leads, max Peers per Lead, max turns/time/tokens per Lead, spawn-depth 3, message rate limits/loop breaker (F2.6, F2.13, F2.20).
- Lead derailment: periodic scope check (diff vs `allowed_paths` and acceptance criteria); if off-task, pause + escalate.
- Silent failures: because push events can be missing (F4.7), treat "no news" as unknown, not fine: show `last_seen` in status answers, and mark `stalled` if `updated_at` exceeds the task's expected cadence.
- Retry hygiene: directive handling idempotent; dedupe by `msg_id`; an unacked directive is retried with backoff, then flagged.
- Post-incident learning: when several Leads fail the same way, fix the shared brief/instructions once, test on one Lead, then re-run others (Projects guidance F2.29).

**Principle 9 - Brief and debrief every delegation like a contract, including Lead -> Peer.** [F2.2, F2.12, F3.1, F3.2]
- Peers get only what the Lead writes (F2.12): the Lead's Peer brief should reuse the same schema (objective, output format, tools, boundaries, decision-log pointer, single-writer rule) and demand a short summary plus artifact path.
- Share context by reference (decision log, plan file, task ledger) so all Peers and the Lead operate on the same priors (Cognition principle 1) without copying long traces.
- Peers report only to their Lead; the Lead is the only interface to the Supervisor (single parent, F1.17).

**Principle 10 - Scale the number of active Leads with measured signals; start at 3-5.** [F2.17, F4.8, F4.9, F3.6]
- Start with at most 3-5 concurrently `working` Leads; queue the rest. Track per-task and overall: median time a Lead runs before needing the human (neglect time), median human+Supervisor minutes per intervention (interaction time), share of Lead-time spent `blocked` on the human, stale-status incidents, verification failure rate, merge-conflict incidents, and quota burn. Raise the cap only if blocked-on-human time and verification failures stay low; lower it when they rise.
- Cost control: Leads on a cost-appropriate model, cheaper models for summarizers and read-only Peers (F2.13, F2.19), and budgets per Lead.

**Minimal implementation sketch (harness-agnostic).**
1. `slp/` state dir outside worktrees: `registry.json`, `tasks/T-xxx/{task.md,status.json,events.jsonl,progress.md,decisions.md}`, `human_queue.jsonl`, `supervisor/{index.md,preferences.md,decisions.md}`.
2. A small control-plane process/extension: creates worktree+session, writes registry, ingests events, runs probes/stall counters, enforces caps, produces `index.md`, raises P0 notifications, batches P1/P2.
3. Lead-side tools (thin CLI or extension tools the Lead must use): `slp status`, `slp event`, `slp claim_done`, `slp decision`, `slp ask_human`. Lead prompt template includes identity line, startup routine and reporting rules.
4. Supervisor prompt: identity-resolution rule (never guess), "answer from ledger + fresh probe with as_of and claimed/verified", escalation policy, no code-editing tools.
5. Verification scripts per task: acceptance commands + scope/test-tamper checks + reviewer-agent spawn.

### Gaps
- These principles are reasoned from public frameworks and vendor docs; none has been validated on OMP or on a coding-agent hierarchy with a human supervisor. Numeric thresholds (stall > 2, 3-5 active Leads, heartbeat cadence) are starting points from analogous systems, not measured optima.
- OMP-specific capabilities (RPC/SDK, session control, extension hooks) are outside this note's scope; whether OMP exposes machine-readable session state, per-session sockets/hooks (like Claude Code's `claude agents --json`, `TaskCompleted` hooks and inbox sockets) will determine how much of the control plane can be built as an extension versus an external daemon.
- No evidence gathered on prompt-injection risks specific to Lead->Supervisor channels beyond Claude Code's trust model (F2.23); worth a separate check if Leads read untrusted web/content.
